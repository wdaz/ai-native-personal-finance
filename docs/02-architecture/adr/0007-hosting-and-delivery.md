Six lines, each with its reason and what it costs:
  1. **Region `fra1`** (`vercel.json` `regions`). The owner created the Neon project in Frankfurt (`aws-eu-central-1`, 2026-09-25, "close to me") and a Neon region cannot change; Vercel's default is `iad1`. Alternative: leave the default — measured before the change, a request reached the function as `x-vercel-id: fra1::iad1::…`, every query then crossing the Atlantic. Consequence: functions sit next to the database (`vercel inspect` of the preview lists them in `fra1`); the build machines still run in `iad1` (the build logs of the CLI production deployment, the preview and a scratch deployment all say "Washington, D.C., USA (East) – iad1"; whether that can be changed on Hobby was not checked).
  2. **Previews' Neon branches come from the Neon-managed Vercel integration**, not "created by the CI workflow and deleted on PR close". The integration creates `preview/<git-branch>` from its parent with the parent's data (measured: created five seconds before the preview's build) and, with "Automatically delete obsolete Neon branches" on (the owner's setting; per Neon's documentation, not yet observed here), deletes it at the *next* preview deployment after the Git branch is gone; a `vercel-dev` branch keeps Vercel's Development values off `production`. Alternatives: a GitHub Actions job calling Neon's REST API and the Vercel CLI (a `NEON_API_KEY` and a `VERCEL_TOKEN` secret, special handling of fork and Dependabot pull requests, more code); previews sharing production's database (rejected: a preview's secret would then reach production's data). Consequences: no Neon or Vercel action and no new secret in CI; a merged pull request's branch lingers until the next preview; the Free plan's 10 branches are `production`, `vercel-dev` and one per Git branch that has a preview deployment — Vercel previews every pushed non-production branch (vercel.com/docs/environment-variables, read 2026-09-26), not only pull requests, so a Dependabot branch counts too, and the clean-up above is the only thing that frees a slot; what happens at the limit was not tried.
  3. **Migrations run in the Vercel build**: `buildCommand` = `npx prisma migrate deploy && npm run build`, through `DATABASE_URL_UNPOOLED` (Neon's direct connection; its pooler is PgBouncer in transaction mode and has no session-level advisory locks), with `installCommand` `npm ci`. Alternative: by hand from a laptop after each merge — a pull request that adds a migration would preview against an old schema. Consequence: each deployment migrates its own database before it builds, and a failed migration fails the build, so no deployment runs against the wrong schema; a rollback does not undo a migration (SPEC-reset-and-test-support §2.5, v1.7; runbook, "Rollback").
  4. **The first-deploy invariant.** The first deployment of a new Vercel project is always production, from whatever branch (vercel.com/docs/deployments/environments), so the production database holds no seed data until the pull request that first deploys with a database has merged and passed its checks on its own preview; the first production deployment therefore ran data-free, without environment variables, from a clean export of `main` (`vercel deploy --prod`: Vercel's import screen had pre-filled `.env.example`'s 13 names as variables, which were deleted first, and the dashboard's empty state offered only "push to main, or run vercel --prod"). Consequence: `/login` answers 500 on that deployment until the merge (the login page prints the demo credentials, which are unset); nobody redeploys it by hand meanwhile.
  5. **Deployment Protection stays Standard, with a bypass secret for automation.** Vercel Authentication covers every deployment URL and the team alias `personal-finance-ruslan-496a.vercel.app`; only the project's own domain is public (measured: the alias answers 302 to `vercel.com/sso-api`, the project domain does not). The secret is sent as `x-vercel-protection-bypass` by the runbook's checks, never by CI. The public production URL is the project domain `https://personal-finance-cyan-kappa.vercel.app` because `personal-finance.vercel.app` was taken; no custom domain in Release 1. The origin-trial token is bound to exactly that origin (`vercel.app` is on the Public Suffix List, so there are no subdomain tokens).
  6. **Node 24.x** (PR #57): Vercel's builds and functions offer 24.x, 22.x and 20.x, not the Node 26 the repository pinned; `.nvmrc`, `engines.node` and `@types/node` follow, and a unit test fixes the list of deployable majors. Back to 26 once Vercel offers it (untracked).

## Context
Solo owner, free tiers, public URL required, reset job required, WebMCP origin-trial token bound to an origin.

## Decision
- **Production:** Vercel project connected to the GitHub repo, `main` → production, in region `fra1` on Node 24.x (amendment 2026-09-25, lines 1 and 6); production env holds `DATABASE_URL` (Neon pooled) and `DATABASE_URL_UNPOOLED` (direct, for migrations) — both set by the Neon-managed integration — `SESSION_SECRET`, demo credentials, `RESET_SECRET`, `CRON_SECRET`, `WEBMCP_ORIGIN_TRIAL_TOKEN`, `WEBMCP_MODE=polyfill` (native is opportunistic when the browser has it). Custom domain optional (none in Release 1); the public URL is the project domain (amendment, line 5), and the OT token is registered for that hostname. The production database holds no seed data until the pull request that first deploys with a database has merged (amendment, line 4).
- **Previews:** every PR gets a preview deployment pointing at a Neon **branch** ~~created by the CI workflow and deleted on PR close~~ `preview/<git-branch>`, created by the Neon-managed Vercel integration from its parent and deleted at the next preview after the Git branch is gone (amendment, line 2); `WEBMCP_MODE=polyfill`, no OT token.
- **Migrations:** `prisma migrate deploy` runs in the Vercel build through `DATABASE_URL_UNPOOLED`, before `next build` (amendment, line 3). **Deployment Protection:** Standard, with a bypass secret for automation (amendment, line 5).
- **CI (GitHub Actions):** on PR — install, lint, typecheck, unit + component, API tests and E2E against a local Postgres service container with `next build && next start`, axe, traceability script; on `main` — the same plus Lighthouse CI against the production URL after deploy (warm-up request first) — implemented by `.github/workflows/lighthouse.yml` (T-14) on `deployment_status`, not a required check. ~~visual snapshots~~ (withdrawn, see amendment).
- **Cron:** `vercel.json` cron ~~`0 3 */10 * *`~~ `0 3 * * *` (daily, amendment 2026-09-23) → `/api/admin/reset` with the secret header; the route resets when `RESET_INTERVAL_DAYS` have passed since the last reset. Hobby-plan cron granularity (daily) is sufficient.
- **Runbook** (`docs/04-process/runbooks/deploy.md`, written in Phase 5): env setup, first seed, rotating secrets, renewing the OT token before Chrome 156, headed native-mode check, relay demo.

## Alternatives considered
**A. Vercel + Neon — chosen.** Native Next.js support, cron, previews, free tier that does not sleep the web tier.
**B. Fly.io or Render with a Docker image + managed Postgres.** Full control, one container; free tiers sleep (cold starts of seconds vs P1), cron needs an extra service, previews are manual.
**C. Cloudflare Pages/Workers + D1.** Attractive edge latency; Next.js support via adapters is less complete, Prisma on D1 is limited, and D1 size limits complicate the reset threshold.
**D. Self-hosted VPS.** Cheapest long-term, most operational work for one person; no.

## Consequences
Easier: push-to-deploy, PR previews for review, cron for free. Harder: vendor lock for cron and env (mitigated: reset is a plain HTTP route; env is a `.env.example`). To watch: Neon branch quota on the free tier (~~delete branches on PR close~~ the integration deletes them at the next preview; a branch per Git branch with a preview counts, Dependabot's included — amendment 2026-09-25, line 2), Vercel hobby limits on build minutes.
