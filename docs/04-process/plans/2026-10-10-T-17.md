content-type (415) refusals for every write path, the `forbidden` code in the error envelope, the issue mapper by

## Findings — read or run 2026-10-10 on `origin/develop` `0c2e2a9`

- **F1. A lower-case method never reaches the proxy.** `write-path.md` §6 "API" and 7.3 say the write predicate
  matches a method of any letter case, "since `fetch` does not upper-case `patch`", and 7.3 asks for "a lower-case
  method is refused the same way" at API level. Measured with a bare `node:http` server (Node 22.22.0, the
  container's; CI runs 24.x, whose parser is the same llhttp): a request line `patch / HTTP/1.1` — and `post`,
  `Patch` — is answered **400 Bad Request by Node itself**, before any JavaScript runs; `PATCH` reaches the handler.
  `fetch(url, { method: "patch" })` sends the lower-case method and gets that 400. So under `next start` no
  lower-case request can reach `proxy.ts`, and 7.3's row cannot be shown as written. → **Q1**.
- **F2. Zod's issues do not carry the input, and an enum reports `invalid_value` even when the field is missing.**
  Probed against the installed `zod@4.6.5` with an amount `z.int().min(1).max(99_999_999_999)`, a name
  `z.string().trim().min(1).max(30)`, an enum and `z.uuid().max(36)`: a missing or `null` amount or name is
  `invalid_type`, a missing or `null` enum is `invalid_value` (the same code as a value outside the enum), and no
  issue has an `input` property (Zod's `reportInput` is off). `1.5` is `invalid_type` (`expected: "int"`), `0` is
  `too_small` (`origin: "number"`), `100000000000` is `too_big` (`origin: "number"`), `"   "` is `too_small`
  (`origin: "string"`, `minimum: 1`), 31 characters is `too_big` (`origin: "string"`), `"x"` as an id is
  `invalid_format`. `2 ** 60` gives **two** issues on `amount` (`too_big` with origin `int`, then `number`). So the
  mapper for the write family takes the parsed input as well as the error (to tell absent or `null` from a wrong
  type, as 2.7 says), and keeps one issue per path (the first), so a field carries one code.
- **F3. The proxy cannot import `schemas.ts` at run time.** `src/server/env.ts` imports it as a type only, because a
  runtime import "would pull zod and copy.ts into the proxy bundle" (PR #20 review, finding 8). The 403 and 415
  bodies are therefore literals typed with `import type { ErrorEnvelope }`, built in a new `src/server/write-rules.ts`
  that imports no Zod; a unit test parses each with `ErrorEnvelopeSchema`.
- **F4. The client-IP reader is private.** `clientIp` (first `x-forwarded-for` entry, else `"local"`) is a local
  function of `src/server/auth.ts`. The write limiter keys on the same value (2.10), so it moves to
  `src/server/client-ip.ts` and both import it; login's behaviour does not change.
- **F5. The test server has no write limit.** `playwright.config.ts`'s `webServer.env` is `{ APP_ENV: "test" }`. 2.10
  wants the API and E2E suites to run with a high finite limit (1,000 per window); the rule "rules about how tests run
  live in the tool's config" (`governance.md`) puts `WRITE_RATE_LIMIT_MAX: "1000"` there, not in an npm script.
- **F6. No write route exists for `guardedWrite` to serve yet.** Its own order of work (2.2 steps 5–10) is therefore
  tested by calling it directly against the API suite's database, as `tests/api/threshold.spec.ts` calls
  `checkThreshold`; the rows of 7.2 that name a route stay with T-23 and T-25. The route-table guard (7.4) passes on
  today's routes (every non-`GET` handler is exempt: login, signup, logout, admin reset, `/api/test/[...path]`) and
  proves itself on one violating fixture per rule.
- **F7. The refusal log line has no reader in the API suite.** 2.12 adds one structured line per 403 and 415,
  `{ requestId, status, method, route }`, and 7.3 lists "the refusal log line" among the API assertions. The via log
  is readable through `GET /api/test/log` (a ring buffer in test mode); stdout of the `next start` that Playwright
  launches is not readable from a test. → **Q2**.
- **F8. The proxy's own API 401 carries no `no-store`.** `proxy.ts` sets `Cache-Control: no-store` only on
  authenticated page responses (line 195). 2.2 step 10 wants it on every refusal of steps 2–4; the plan sets it on
  every answer the proxy itself builds for an `/api/*` path (its 401, the new 403 and 415, logout's 403), which a
  `GET` 401 shares — harmless, and simpler than a method test in the 401 branch.
- **F9. T-17 names US-40 in a test title.** The via log's `method` is US-40 AC3's marker (backlog row "Stories").
  Under the owner's answer (a), a build task removes the ids its own tests name, so US-40 leaves the list with this
  task: **19 ids remain** (US-09, 10, 12–26, 29, 30). US-31, US-36 and US-37 are Release 1 ids, already named.
  Today `run(root, false, 2)` prints `1 20` and the 20 ids of the backlog note (run 2026-10-10).
- **F10. Two line numbers in `write-path.md` have moved.** 2.2 step 10 cites the re-issue at `proxy.ts` 173–186;
  it is 170–186 today. 2.6's 141–149 for logout's 403 is still right. No amendment for this; the code comments cite
  the spec section, not a line.

## Decisions taken in the plan (the spec leaves them to the build)

- **D1. The write predicate and the exempt list** live in `src/server/write-rules.ts` (pure, no Zod):
  `isWriteRequest(method, pathname)` — upper-cases the method and refuses `GET`, `HEAD`, `OPTIONS`; path under
  `/api/`; not on `WRITE_EXEMPT` (exact paths `/api/auth/login`, `/api/auth/signup`, `/api/auth/logout`,
  `/api/admin/reset`, and the `/api/test/` prefix). `crossSiteRefused(headers)` (exactly `cross-site`) and
  `contentTypeRefused(method, headers)` (2.4: media type before `;`, trimmed, compared case-insensitively to
  `application/json`; a `DELETE` with no header passes). The case-insensitive method match stays in the predicate
  whatever Q1's answer: it costs nothing and holds behind a server that does pass `patch` through.
- **D2. In `proxy.ts`**, after the 401 branch and before the auth-page redirect: write request + cross-site → 403
  `{ error: "forbidden", message: "This request must be same-origin" }`; else write request + refused type → 415
  `{ error: "validation", issues: [{ path: [], code: "invalid_format" }] }`. Logout's existing 403 answers the same
  `forbidden` body (2.6, `auth.md` v1.0.10). The three refusals join `skipsReissue`; every proxy-built `/api/*`
  answer gets `no-store` (F8); the security headers are already set on every response.
- **D3. `ErrorEnvelope`**: `forbidden` joins `ERROR_CODES`; `VALIDATION_ISSUE_CODES` gains `too_small`,
  `too_large`, `exceeds_balance`, `exceeds_total`, `taken` (`auth.md` v1.0.10). `validationErrorResponse(issues,
  status = 400)`; `errorResponse`, `validationErrorResponse` and `rateLimitedResponse` set `no-store` on every answer
  (2.2 step 10).
- **D4. The issue mapper.** `toErrorIssues(error)` keeps today's auth mapping unchanged and stops throwing on
  `invalid_value` (it maps to `invalid_format`); a new `toWriteIssues(error, input)` maps the write family to 2.7's
  table exactly (F2): absent or `null` at the path → `required`; `too_small` on a string → `required`, on a number →
  `too_small`; `too_big` on a string → `too_long`, on a number → `too_large`; every other code → `invalid_format`;
  one issue per path. A body that is not JSON or not an object → `[{ path: [], code: "invalid_format" }]` (4.4).
- **D5. The write limiter** (`src/server/write-limit.ts`): `evaluateWrites(countInWindow, oldestAt, now, max,
  windowMs)` is pure; `checkWriteLimit(db, ip, now, max, windowMs)` deletes the rows older than the window, counts
  the IP's rows in it (aggregate, as the login limiter) and, when under the limit, inserts this request's row —
  a refused request writes no row. Two requests racing at the edge can both pass; accepted for a public demo, the
  spec asks for no stricter count. `WRITE_RATE_LIMIT_MAX` (default 30) and `WRITE_RATE_LIMIT_WINDOW_SECONDS` (default
  60) are read with `env.ts`'s `positiveInt`. `WriteAttempt` (`id`, `ip`, `at`, `seeded`, `createdAt`, `updatedAt`,
  `@@index([ip, at])`, the `LoginAttempt` shape) with its migration; added to `RESET_TABLES`.
- **D6. The threshold as one query.** `checkThreshold` runs one `$queryRaw`: the three `count(*) … WHERE seeded =
  false` as scalar sub-selects summed, with `pg_database_size(current_database())`; `evaluateThreshold` is
  unchanged, so `threshold.spec.ts` still passes as written.
- **D7. `guardedWrite(request, { schema, id, run })`** in `src/server/write.ts`, in 2.2's order: the limiter (429)
  → the path `id` with `z.uuid().max(36)` when the route has one (400 on `id`) → for a non-`DELETE`, the body read as
  JSON and parsed with `schema` (400 by D4) → `run(tx, input)` inside one `db.$transaction`, where `run` returns a
  tagged result (`ok` with status and body, `not_found`, or `validation` with issues), and a unique-constraint error
  (Prisma `P2002`) maps to `taken` on the field the route names → `checkThreshold` after the commit (a throw is
  logged and the write's answer stands; `exceeded` → `resetToSeed(db, "threshold")` and 409 `conflict`, "Data was
  reset"; a throw there → 500) → the answer, every one with `X-Request-Id` (from the proxy's forwarded
  `x-request-id`) and `no-store`. The exact names of `run`'s result are working names (`write-path.md` §8).
- **D8. The client and the tools.** `apiSend(method, path, schema, { body, signal, headers })` in
  `src/shared/api-client.ts`: the method upper-cased, `Content-Type: application/json` on `POST`, `PUT`, `PATCH`,
  a 204 read as success with no body, otherwise the same `ApiOutcome` as `apiGet`. The tool side: `forbidden` in
  `TOOL_ERROR_CODES`, its `DEFAULT_TOOL_MESSAGE` "This request must be same-origin" (the 403 body's own, so no new
  text); 403 → `forbidden`, 415 → `validation` with the body's `issues` (`webmcp-tools.md` §2.5).
- **D9. The via log** entry becomes `{ requestId, via, method, route }`, `method` as `request.method` (2.12,
  `webmcp-tools.md` §2.8); the proxy passes it. The refusal line is built by `refusalLogLine(...)` in
  `write-rules.ts` and written with `console.log` like the via entry; how it is tested is **Q2**.
- **D10. Copy (H10).** A new table "### R2 additions (2026-10-04, owner-approved with `write-path.md`)" at the end of
  the copy appendix of `user-stories.md` — "Budget | record gone (404) | This budget no longer exists", "Pot | record
  gone (404) | This pot no longer exists", "Any write | rate limited (429) | Too many changes. Try again in {N}
  seconds", "Category or theme | already used | Already used" — and `COPY.budgetGone`, `COPY.potGone`,
  `COPY.writeRateLimited(seconds)` (singular at 1, as the appendix's footnote says), `COPY.alreadyUsed`, with
  `copy.test.ts`'s rows. The wording is the owner's (§9 Q5); the amendment of the Approved `user-stories.md` is
  approved by the merge of this task's pull request.
- **D11. The traceability flip (H4, answer (a)).** `RELEASE_BEING_BUILT = 2`; `NOT_YET_BUILT` in
  `scripts/traceability.ts` holds the 19 ids of F9; `run()` and the live "this repository" test skip them; an id on

## Questions for the owner

**Q1. The lower-case method (F1).** The spec asks the API tests to show that a request whose method is written in
small letters (`patch` instead of `PATCH`) is refused like any other write. In practice the Node server refuses such
a request itself with a plain 400 before our code ever runs, so our 403/415 can never be shown for it.
- **(a)** Keep our check case-insensitive (it is free), test that at unit level, and in the API test assert what
  really happens: Node's 400, with nothing written. `write-path.md` 7.3 and §6 get one sentence each saying so, as an
  amendment in this task's pull request, approved by your merge. `apiSend` always sends upper-case methods.
  **Recommended:** the protection is the same and the spec then says what is true.
- **(b)** Leave the spec as it is and drop that one API row without a spec change. Not recommended: the spec would
  promise a test that does not exist.

**Q2. The refusal log line (F7).** For each 403 and 415 the server prints one log line. The spec wants the API tests
to check it, but those tests cannot read the server's printed output.
- **(a)** Test the line at unit level (the function that builds and writes it), and check at API level only that the
  refusal happened (status, body, headers). `write-path.md` 7.3 moves "the refusal log line" to its 7.1 unit row, one
  sentence in the same amendment as Q1. **Recommended:** small, and the line's content is fully tested.
- **(b)** In test mode also keep refusal lines in memory and let `GET /api/test/log` return them, so the API test
  reads the real line. This changes the test-support contract (`reset-and-test-support.md` §2.7) too: more code and a
  second spec amendment, for the same certainty about the line's content.

**Q3. One pull request or two.** T-17 is large (about 15 files of code, 6 test files, a migration, 3 document
amendments).
- **(a)** One pull request for the whole task, with one commit per task A–G above. **Recommended:** every earlier
  build task was one pull request, and the parts depend on each other (the `forbidden` code is used by the proxy, the
  envelope and the tools at once).
- **(b)** Two pull requests: first A, E and F (contracts, route guard, traceability: no database change), then B, C
  and D (the proxy, the limiter with its migration, the wrapper). Easier to review each, but twice the CI and Copilot
  cycles, and the second waits for the first's merge.
