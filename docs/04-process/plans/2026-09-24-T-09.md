**Architecture.** Everything `getOverview` needs already exists except the wiring itself:
`src/domain/overview.ts`'s `overviewSummary` (T-03), the DTO schema `OverviewDtoSchema` (T-04,

client spelling (`DiningOut`, `NavyGrey`) to data-model.md's own spelling (`Dining Out`, `Navy
Grey`) through two lookup tables, `CATEGORY_LABEL` and `THEME_LABEL` (the T-04 hand-off's "one

actual member of the generated Prisma `Category`/`Theme` object — so there is no second,
independently-typed table a swap could silently pass through; a genuine mismatch (a category or
theme documented in `src/shared/enums.ts` but absent from `prisma/schema.prisma`, or the

happens to exercise the specific pair. The same `categoryLabel()` call maps both budgets' and
transactions' `category` before either reaches `overviewSummary`, so `budgetSpent`'s `===`

## Pre-execution review (advisor)

Before writing any code, a stronger reviewer checked this plan's first draft against the
repository's own conventions and found five defects, corrected here:

1. **Task 2's steps ran in the wrong order** (create the route, then a step claiming to "see it
   fail"). TDD requires the test written and seen to fail *before* the code that makes it pass.
   Task 2 below is reordered; the "Expected" lines that describe a command nobody has run yet
   are marked *prediction* (governance.md, "Plans mark predictions"), and are corrected to the
   real, mixed outcome — the 401 test already passes today (the middleware answers it with no
   route handler at all), only the authenticated tests fail (404) until the route exists.
2. **The two label maps could not have caught a swapped entry.** The first draft hand-typed
   `CATEGORY_LABEL`/`THEME_LABEL` as two literal tables and tested them with set comparisons
   (do the values, as a set, match `CategorySchema.options`?) — a table with two entries
   swapped (say, `Green` mapped to `Navy` and `Navy` to `Green`) passes a set comparison, passes
   `OverviewDtoSchema` (both are valid themes), and the planned API test would have computed its
   *expected* theme through the very same hand-typed table, proving nothing. The fix, described
   in Architecture above: both maps are now *built* from `src/shared/enums.ts`'s
   `CATEGORIES`/`THEMES` by a rule (remove the space, look up the generated Prisma enum),
   checked against the live Prisma enum object at import time — there is no second table left
   to swap.
3. **The `empty-all` seed variant was missing**, and `few-transactions`' expected order was
   asserted only by name, not tied to an independent computation. Task 2's redesigned test
   (below) now runs against all six `SEED_VARIANTS`, computing each variant's *entire* expected
   Overview independently (`overviewSummary(applyVariant(seedRows(), variant), clock)`) rather
   than hand-asserting a shape per variant — stronger than the fix the review asked for.
4. **Two statements in the first draft were false.** The variant-loop's login-ordering note said
   a reset "would not affect an existing session cookie either way" — wrong: `resetToSeed`
   writes a new `ResetLog` row, which invalidates any session sealed before it (US-03 AC3,
   `isSessionValid`'s `resetEpoch` check, exercised end to end in T-08); logging in *after*
   seeding is required, not a style choice, and the corrected test does so. Review Focus 1's
   worked-out number was also wrong: mapping only budgets' categories (not transactions')
   through `categoryLabel` does not zero every budget — `Entertainment` and `Bills` have no
   space and still match by accident, so only `Dining Out` and `Personal Care` mismatch:
   `$338.00` becomes `$165.00`, not `$0.00`. Corrected below.
5. **The DoD checklist needed an explicit scope note** so a reviewer does not read "no E2E, no
   axe, no screenshots" as skipped work — added to the Goal paragraph above.

The review also suggested a pure/impure split (`toOverviewDto` / `getOverview`) so the strict
DTO mapping is unit-testable without Postgres — adopted, described in Architecture and Task 1.
It flagged, as a check rather than a defect, whether importing `scripts/seed-figures.ts` (which
uses `import … with { type: "json" }` and `import.meta.main`) inside a Playwright API test is
proven to work in this repository; no existing `tests/api` spec does that. Task 2's redesigned
test avoids the question entirely: it computes each expected Overview from `seedRows()` and
`applyVariant()` (`src/server/seed.ts`, `src/server/variants.ts`) plus the domain's own
`overviewSummary`/`fixedClock` — imports `tests/api/reset.spec.ts` already proves safe in this
runner — rather than from `scripts/seed-figures.ts`'s wrapper.

## Review Focus

1. **A category-spelling mismatch silently shrinks every affected budget's `spent`.** Expected:
   the seed's `budgets.spent` is `$338.00` (SPEC-overview §4.3: Entertainment `$15.00`, Bills
   `$150.00`, Dining Out `$133.00`, Personal Care `$40.00`). → The seed-variant API test (below)
   for the plain `"seed"` variant; the mutation is applying `categoryLabel()` to budgets but
   handing transactions their raw Prisma category string. `Entertainment`/`Bills` have no space
   and still match by accident, so only `Dining Out` and `Personal Care` lose their `spent`:
   the total becomes `$165.00`, not `$338.00` — still a mismatch the exact-equality assertion
   catches, just not the number a first guess suggests (pre-execution review, finding 4).
2. **A missed `BigInt`→`Number` conversion turns a 200 into a 500.** `sumCents` throws on
   anything that is not a safe-integer `Number` (`src/domain/money.ts`), so a raw `BigInt`
   reaching it fails loudly rather than silently. Expected: every seed-variant test gets 200.
   → The mutation is removing one `Number(...)` call (say, `pot.total`) and watching every
   variant's response turn into a 500 instead of a passing 200.
3. **`getOverview` fabricates zeros when `Balance` is missing.** Expected: with the `Balance`
   table emptied after a normal reset, `GET /api/overview` is a 500 `server_error`, not a 200
   full of zeros — the same shape `tests/api/meta.spec.ts` already proves for an empty
   `ResetLog` (T-08). → A dedicated API test; the mutation is `getOverview` defaulting to
   `{ current: 0, income: 0, expenses: 0 }` instead of throwing, and watching the test's
   `expect(response.status()).toBe(500)` fail against a `200`.
4. **A leaked `seq`/`category`/`recurring` reaches the DTO.** Expected: `toOverviewDto`'s output
   objects have exactly the keys `OverviewDtoSchema` allows — nothing more. → A unit test on
   `toOverviewDto` (no database needed) that hands it a hand-built `OverviewSummary` whose
   transaction/budget/pot items carry extra fields (`seq`, `category`, `recurring`) and asserts
   they are absent from the result (`Object.keys`, not just "the schema happens to still
   parse" — a `.safeParse` failure could otherwise be misread as some unrelated field being
   wrong); the mutation is spreading `...pot`/`...transaction`/`...budget` into the mapping
   instead of naming each field, and watching an extra key appear.
5. **`no-store` regressed to a framework default.** Expected: the header is the exact string
   `no-store`, not Next's own dynamic-route default (`private, no-cache, no-store, max-age=0,
   must-revalidate` — the literal T-07's D17 finding pinned down, `tests/api/app-pages.spec.ts`).
   → An API test asserting the header's exact value; the mutation is deleting the route's own
   `Cache-Control` header-set call.
6. **A swapped `CATEGORY_LABEL`/`THEME_LABEL` entry.** Cannot happen by construction (D2/finding
   2) — there is no hand-typed table left to swap; a documented category or theme with no
   matching Prisma enum member throws at import time instead, in every environment. → Covered
   by Task 1's unit test that the map's construction succeeds and, directly, by a test that a
   deliberately unknown label throws (DoD v1.1's violation-fixture rule for the guard).

const documentedList = (name: "Category" | "Theme") =>
  (new RegExp(`\`${name}\` = ([^.]+)\\.`).exec(read("docs/02-architecture/data-model.md"))?.[1] ??

describe("toOverviewDto (SPEC-overview §6: strict — no seq, no category/recurring on transactions)", () => {

import { overviewSummary, type OverviewSummary } from "@/src/domain/overview";
import type { Clock } from "@/src/domain/clock";
import { CATEGORIES, THEMES, type Category, type Theme } from "@/src/shared/enums";
import type { OverviewDto } from "@/src/shared/schemas";
import type { Db } from "./db";
import { Category as PrismaCategoryEnum, Theme as PrismaThemeEnum } from "./generated/prisma/enums";

type PrismaCategory = (typeof PrismaCategoryEnum)[keyof typeof PrismaCategoryEnum];
type PrismaTheme = (typeof PrismaThemeEnum)[keyof typeof PrismaThemeEnum];

/**
 * data-model.md spells these with a space; Prisma's client identifier drops it
 * (`prisma/schema.prisma`'s `@map`). Built, not hand-typed (T-09 plan D2 — a hand-typed
 * reverse table could swap two entries without any test noticing): one entry per name in
 * `src/shared/enums.ts`, which `tests/unit/shared/enums.test.ts` already holds to
 * data-model.md, checked here against the *live* generated Prisma enum, so a name this
 * project documents but `prisma/schema.prisma` does not (or the reverse) throws at import
 * time rather than passing silently. Keys are plain `string`, the same loose-key convention
 * `seed.ts`'s own `CATEGORY_BY_NAME`/`THEME_BY_HEX` already use — `categoryLabel`/`themeLabel`
 * below are the precisely-typed accessors production code calls.
 */
function despacedCategory(label: string): PrismaCategory {
  const key = label.replaceAll(" ", "");
  if (!(key in PrismaCategoryEnum)) {
    throw new Error(`"${label}" (src/shared/enums.ts) has no matching Prisma Category "${key}"`);
  }
  return key as PrismaCategory;
}

function despacedTheme(label: string): PrismaTheme {
  const key = label.replaceAll(" ", "");
  if (!(key in PrismaThemeEnum)) {
    throw new Error(`"${label}" (src/shared/enums.ts) has no matching Prisma Theme "${key}"`);
  }
  return key as PrismaTheme;
}

export const CATEGORY_LABEL: ReadonlyMap<string, Category> = new Map(
  CATEGORIES.map((label) => [despacedCategory(label), label]),
);

export const THEME_LABEL: ReadonlyMap<string, Theme> = new Map(
  THEMES.map((label) => [despacedTheme(label), label]),
);

export function categoryLabel(category: PrismaCategory): Category {
  const label = CATEGORY_LABEL.get(category);
  if (!label) throw new Error(`Unmapped category "${category}" — CATEGORY_LABEL needs an entry`);
  return label;
}

export function themeLabel(theme: PrismaTheme): Theme {
  const label = THEME_LABEL.get(theme);
  if (!label) throw new Error(`Unmapped theme "${theme}" — THEME_LABEL needs an entry`);
  return label;
}

type OverviewRow = { id: string };
type PotRow = OverviewRow & { name: string; total: number; theme: Theme };
type TransactionRow = OverviewRow & { name: string; avatar: string; amount: number; date: Date };
type BudgetRow = OverviewRow & { category: Category; maximum: number; spent: number; theme: Theme };

/**
 * SPEC-overview §6: `OverviewDtoSchema` is strict. Pure (T-09 plan D7 — T-08's D2 precedent):
 * every field is named explicitly, so `seq`/`category`/`recurring` on the caller's rows never
 * reach the DTO no matter what extra fields `overviewSummary`'s generic result happens to carry.
 */
export function toOverviewDto<T extends TransactionRow, B extends BudgetRow, P extends PotRow>(
  summary: OverviewSummary<T, B, P>,
): OverviewDto {
  return {
    balance: summary.balance,
    pots: {
      total: summary.pots.total,
      items: summary.pots.items.map((pot) => ({
        id: pot.id,
        name: pot.name,
        total: pot.total,
        theme: pot.theme,
      })),
    },
    transactions: summary.transactions.map((transaction) => ({
      id: transaction.id,
      name: transaction.name,
      avatar: transaction.avatar,
      amount: transaction.amount,
      date: transaction.date.toISOString(),
    })),
    budgets: {
      spent: summary.budgets.spent,
      limit: summary.budgets.limit,
      items: summary.budgets.items.map((budget) => ({
        id: budget.id,
        category: budget.category,
        maximum: budget.maximum,
        spent: budget.spent,
        theme: budget.theme,
      })),
    },
    bills: summary.bills,
  };
}

/**
 * SPEC-overview §2.1, §6: the one place an Overview DTO is assembled from the database.
 * `Balance` is a singleton seeded by `resetToSeed`; its absence means the database was never
 * seeded, a configuration fault like `latestReset`'s (T-08 D1). No `seeded` filter (T-09 plan
 * D4). Both budgets' and transactions' `category` go through the same `categoryLabel` before
 * `overviewSummary` runs, so `budgetSpent`'s `===` compare never mismatches on spelling (D3).
 */
export async function getOverview(db: Db, clock: Clock): Promise<OverviewDto> {
  const [balance, transactions, budgets, pots] = await Promise.all([
    db.balance.findFirst(),
    db.transaction.findMany(),
    db.budget.findMany(),
    db.pot.findMany(),
  ]);
  if (!balance) {
    throw new Error("No Balance row exists: the database was never seeded (README, db:reset)");
  }
  const summary = overviewSummary(
    {
      balance: {
        current: Number(balance.current),
        income: Number(balance.income),
        expenses: Number(balance.expenses),
      },
      transactions: transactions.map((row) => ({
        id: row.id,
        name: row.name,
        avatar: row.avatar,
        category: categoryLabel(row.category),
        date: row.date,
        amount: Number(row.amount),
        recurring: row.recurring,
      })),
      budgets: budgets.map((row) => ({
        id: row.id,
        seq: row.seq,
        category: categoryLabel(row.category),
        maximum: Number(row.maximum),
        theme: themeLabel(row.theme),
      })),
      pots: pots.map((row) => ({
        id: row.id,
        seq: row.seq,
        name: row.name,
        total: Number(row.total),
        theme: themeLabel(row.theme),
      })),
    },
    clock,
  );
  return toOverviewDto(summary);
}
