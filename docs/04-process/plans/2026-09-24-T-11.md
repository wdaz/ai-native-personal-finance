## Findings — verified against the installed package, not the spec text

SPEC-webmcp-tools §2.2 and ADR-0004 were written 2026-09-13/09-20 against the *4 September 2026*
WebMCP draft (research note `webmcp-status.md`, F1–F2), which the research note itself flagged as
certain to move ("re-check before Phase 3 and again before deployment"). This plan re-checked it
against `@mcp-b/webmcp-polyfill@5.1.0` — the only published version this task can actually
install, and the one whose README states it "implements the current core WebMCP API" — and found
two places where the real package's API no longer matches what the spec text describes. Both are
read from the installed package's own `dist/index.js`/`dist/schema.js` and README (evidence below);
the upstream spec page itself (`webmachinelearning.github.io/webmcp`) could not be re-checked from
this session — outbound access to that host is blocked by the network egress proxy — so the
package is the primary source here, not a secondary one.

**Q1 — `unregisterTool(name)` does not exist.** SPEC §2.2: "`unregisterAll()` bumps the
generation... and calls `unregisterTool(name)` for every registered name." The installed
polyfill's compatibility-boundary section says plainly: "`unregisterTool()`, `provideContext()`,
and `clearContext()` are not exposed." Its `registerTool(tool, { signal })` instead ties a tool's
whole lifetime to an `AbortSignal` passed at registration (`dist/index.js:717-736`: the signal is
stored, an `abort` listener removes the tool; `dist/index.js:794-801`, `#removeTool`); calling
`registerTool` with an already-aborted signal throws before the tool is added
(`signal?.throwIfAborted()` at line 721, before `this.#tools.set(...)` at line 725). There is no
name-based counterpart to call instead.
**Recommendation (Q1):** replace the name-based unregister with one `AbortController` per
registration generation: `register(tools)` creates a fresh controller, awaits the polyfill if
needed, then calls `registerTool(def, { signal: controller.signal })` for each tool; `unregisterAll()`
is exactly `controller.abort()`. This gives the "drop a stale, still-pending generation" behaviour
SPEC §2.2 asks for **for free** — `throwIfAborted()` already rejects a registration whose
generation was cancelled while the polyfill import was still in flight — without a separate
generation-number comparison before each `registerTool` call. ADR-0004's own text ("Exposes
`register(tools)`, `unregisterAll()`, `mode()`") does not name `unregisterTool` itself, so this
is a SPEC-webmcp-tools §2.2 correction, not an ADR-0004 rewrite: this plan proposes a v1.0.3
changelog line (like T-04's F1 → v1.0.2) rather than a new ADR alternative.

**Q2 — the registered tool's `execute` receives one positional argument, not `{ input, signal }`.**
`#invokeToolByName` (`dist/index.js:802-819`) calls `tool.execute(args)` where `args` is only the
parsed JSON input; the *caller's* `signal` (from `executeTool(tool, json, options)`) is used to
race the returned promise externally (`withAbortSignal`) and is never handed to `execute` itself.
SPEC-webmcp-tools's own header already anticipated this: "`execute(input, signal)` is the draft's
callback shape (research note F2); **the adapter wraps whatever the runtime passes and exposes
`{ input, signal }` to our tools**." So this is not a new mismatch to resolve at the spec level —
the spec already delegated the wrapping to the adapter — but concretely, against this runtime,
there is no real signal to forward: `defineTool`'s generated descriptor `execute(rawArgs)` parses
`rawArgs` with the tool's Zod schema and calls the tool author's `execute({ input, signal:
undefined })`. Noted here so T-12 does not expect a working `signal` to pass to `fetch` from a
tool's `execute` body until the runtime actually offers one (a Chromium `AbortSignal` extension,
if one ships, would let `defineTool` forward it the same way).

**The go-ahead can answer Q1/Q2 "as recommended" (T-04/T-07's own pattern) or say "start"; neither
blocks the rest of this plan, which assumes the recommendations above.**

## Architecture

**Module layout** (`src/webmcp/`, ADR-0002: imports only `src/shared`, itself, or external
packages):

| File | Responsibility |
|------|-----------------|
| `types.ts` | `ToolDefinition` (SPEC §6: `name, title?, description, inputSchema, annotations?, execute`); a minimal ambient `ModelContext`/`Document.modelContext` type (the DOM lib ships none yet) |
| `adapter.ts` | `getModelContext()` (native/polyfill/off detection, SPEC §2.2), `register(tools)`, `unregisterAll()`, `mode()`, `onStatus(cb)`; the generation `AbortController`, the readiness attribute + `toolchange` dispatch, the idle-callback-scheduled lazy polyfill import |
| `defineTool.ts` | Builds a `ToolDefinition`'s registrable descriptor: validates name/description/annotations, converts `input` with `toolInputJsonSchema` (T-04, throws on an empty or unbounded-string schema), wraps `execute` per Q2 |
| `WebMcpProvider.tsx` | Client component, mounted once in `app/(app)/layout.tsx`; runs `getModelContext()` on mount, exposes `register`/`unregisterAll`/live status via two React Contexts (below); sets `window.__pf.webmcp` under `NEXT_PUBLIC_APP_ENV === "test"` |
| `WebMcpTools.tsx` | Client component, `{ tools: ToolDefinition[] }`; effect calls the provider's `register(tools)` on mount, `unregisterAll()` on unmount (SPEC §2.3 — page-scoped, remounts per route segment) |
| `AgentToolsStatus.tsx` | The four-state indicator (SPEC §2.7), `variant: "sidebar" \| "compact"` |

**Crossing the `src/ui` ⇎ `src/webmcp` boundary (Decision D1).** `eslint.config.mjs`'s
`boundaries/dependencies` only lets `ui` import `ui` or `shared` (line 114-117) — it cannot import
`src/webmcp`, and `src/ui/Shell.tsx`'s own T-11 comment already says so ("`src/ui` may not import
`src/webmcp`"). But the indicator has to render *inside* `Sidebar.tsx` and `PageHeader.tsx` — both
`src/ui`, and `PageHeader` is rendered per-page (`overview/page.tsx` etc.), not by `Shell`. The
seam that is allowed to import both layers is `app/**` (`app` → `anyOf: [app, domain, shared,
server, webmcp, ui]`). So `app/(app)/layout.tsx` renders the two indicator variants from
`AgentToolsStatus` (`src/webmcp`) and hands each down through a plain `ReactNode` slot defined in
`src/ui` (no WebMCP-specific knowledge in it):

```tsx
// app/(app)/layout.tsx (composition only — this file already imports both layers today)
<WebMcpProvider>
  <AgentToolsIndicatorContext value={{
    sidebar: <AgentToolsStatus variant="sidebar" />,
    compact: <AgentToolsStatus variant="compact" />,
  }}>
    <Shell meta={meta}>{children}</Shell>
  </AgentToolsIndicatorContext>
</WebMcpProvider>
```

`src/ui/agent-tools-indicator.ts` exports only the Context object and its type
(`{ sidebar: ReactNode; compact: ReactNode } | null`, default `null`) — `Sidebar.tsx` reads
`.sidebar` above `<LogoutButton variant="sidebar" .../>`, `PageHeader.tsx` reads `.compact` before
`<LogoutButton variant="icon" />`. Rendering `<Sidebar />`/`<PageHeader title=.../>` with no
provider in scope (every existing unit test does this today) yields `null` from the context and
renders nothing extra — **no existing `Sidebar.test.tsx`/`PageHeader` test needs to change.**
`AgentToolsStatus` itself stays the only file that knows about `mode()`/tool counts/`COPY.agentTools*`,
satisfying the Definition of Done's "WebMCP code lives only in `src/webmcp`" literally: the two
`src/ui` files gain a slot, not WebMCP knowledge.

**Status state.** `WebMcpProvider` holds `{ status: "checking" | "native" | "polyfill" |
"unavailable"; count: number }` in `useState`, seeded `"checking"`/`0`. On mount it calls
`getModelContext()` (native/off resolved synchronously; polyfill's dynamic `import()` resolves
async) via the idle-callback scheduler (NFR-P3) and calls `onStatus` internally whenever `mode()`
settles or a completed `register`/`unregisterAll` changes the tool count, re-rendering the two
context values. `AgentToolsStatus` itself reads this via a small internal context
`WebMcpStatusContext` (defined in `src/webmcp`, consumed only inside `src/webmcp` —
`AgentToolsStatus` and `WebMcpProvider` are the only two readers, so it never needs to leave the
module).

**`register`/`unregisterAll` (Q1's `AbortController` design).**

```ts
let generation: AbortController | null = null;

async function register(tools: ToolDefinition[]) {
  generation?.abort();              // a register() without an intervening unregisterAll
  const controller = new AbortController();
  generation = controller;
  const context = await getModelContext();   // awaits the lazy polyfill import if needed
  if (context === null || controller.signal.aborted) return;   // off, or cancelled while awaiting
  await Promise.all(
    tools.map((tool) => context.registerTool(tool, { signal: controller.signal }).catch(() => {})),
  );
  if (controller.signal.aborted) return;      // cancelled mid-registration
  document.documentElement.dataset.webmcp = "ready";
  dispatchReadyEvent(context);                // one `toolchange` on document, and on context if it's an EventTarget
  notifyStatus({ count: tools.length });
}

function unregisterAll() {
  generation?.abort();               // removes every tool registered with this generation's signal
  generation = null;
  delete document.documentElement.dataset.webmcp;
  notifyStatus({ count: 0 });
}
```

A `registerTool` call that individually throws (a duplicate name, an aborted signal) is caught
per-tool rather than failing the whole batch — SPEC §2.4/§7 already makes `defineTool` the gate
for a malformed descriptor (thrown at *build* time, not registration time), so a `registerTool`
rejection at runtime should not be reachable in practice; it is still caught defensively so one
bad tool cannot block its page's other tools from registering.

**Mode detection (`getModelContext`, SPEC §2.2, unchanged from the spec text — this part matches
the installed package).**
`WEBMCP_MODE` is read once, client-side, as `NEXT_PUBLIC_WEBMCP_MODE` (already exposed by
`next.config.ts`, T-08) through `WebMcpModeSchema.catch("polyfill")` (empty/unset → "polyfill",
matching `configuredWebmcpMode`'s server-side rule — `tests/unit/next-config.test.ts` already pins
the two agree, T-08). `off` → `register` a no-op, `mode() = "unavailable"`, nothing imported.
Otherwise: `"modelContext" in document` checked **before** anything is imported → `native`; else
`await import("@mcp-b/webmcp-polyfill")` once, call `initializeWebMCPPolyfill()` → `polyfill`;
import (or init) failure → `unavailable`, `console.warn`. **`meta.webmcp.configuredMode` (T-08's
`GET /api/meta`) is not read here** — the T-08 hand-off note already says the indicator "stays
independent of it", and `next-config.test.ts` proves the client env var and that server value are
always identical, so there is nothing `meta` would add and no need to thread `meta` through the
provider.

**Readiness + `toolchange`.** After a `register` batch completes (not per-tool — SPEC §2.2 "one
`toolchange` ... per completed batch"; the polyfill's own `registerTool` fires its own internal
`toolchange` per call, which is harmless noise the readiness attribute does not depend on): set
`dataset.webmcp = "ready"`, `document.dispatchEvent(new Event("toolchange"))`, and — only if
`context instanceof EventTarget`, true for both the polyfill's `StrictWebMCPContext` and (per the
spec) native — dispatch the same on `context` too. `unregisterAll()` deletes the attribute; it
does not dispatch `toolchange` itself (SPEC never asks it to — only a completed `register` does).

**Lazy loading (NFR-P3, unchanged from spec text).** The whole detection dance (`getModelContext`
called by the provider's mount effect) is scheduled with
`typeof requestIdleCallback === "function" ? requestIdleCallback(cb, { timeout: 2000 }) :
setTimeout(cb, 0)` so it runs after hydration, never blocking first paint. jsdom (the unit-test
environment) has no `requestIdleCallback`, so the `setTimeout` branch is what the unit tests
exercise; a fake-timer test advances it explicitly.

**Test hook (SPEC §6).** `WebMcpProvider`'s mount effect additionally sets, only when
`process.env.NEXT_PUBLIC_APP_ENV === "test"`: `window.__pf = { ...window.__pf, webmcp: { mode,
tools: () => registeredNames } }` — `mode` is the adapter's own `mode()` function (not a snapshot),
`tools()` returns the current generation's registered names, useful for a `WEBMCP_MODE=off` E2E
run where `document.modelContext` never exists at all and the test cannot otherwise ask the page
"did you try to register anything".

## Review Focus

1. **A stale registration lands after `unregisterAll()` — an unmounted page's tools stay callable.**
   Expected: calling `register(tools)`, then `unregisterAll()` before the (mocked, delayed)
   polyfill import resolves, then letting the import resolve, results in zero registered tools —
   `registerTool` must never be called with an already-aborted signal reaching the mock's
   assertion. → Unit test drives a controllable `Promise` for the dynamic import and asserts the
   mock `context.registerTool` was never called for that generation.
2. **Two `register()` calls without an intervening `unregisterAll()` leave both generations' tools
   registered** (e.g., a fast route change or a React Strict Mode double-effect that this task did
   not anticipate). Expected: the second `register()` call's own internal `generation?.abort()`
   removes the first generation's tools before adding the second's — never both sets live at once.
   → Unit test calls `register(toolsA)` then immediately `register(toolsB)` without awaiting the
   first, and asserts only `toolsB`'s names remain via the mock context's tracked map.
3. **`toolchange` fires more than once per completed batch**, breaking a test that waits for
   exactly one readiness signal. Expected: one `register([toolA, toolB])` call dispatches exactly
   one `document` `toolchange` event, regardless of how many tools are in the batch. → Unit test
   with a `document.addEventListener("toolchange", spy)` and a two-tool batch, asserting
   `spy.mock.calls.length === 1`.
4. **`defineTool` accepts a tool whose input schema has an unbounded string**, silently shipping a
