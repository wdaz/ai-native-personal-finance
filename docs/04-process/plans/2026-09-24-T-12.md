## Findings — verified against the installed package and the running code, not the spec text

SPEC-webmcp-tools §7 was written on 2026-09-20 against the 4 September draft. As at T-11, this
plan re-checked what the tests would actually call. Everything below was read from the code or
the published package, not assumed. The polyfill's own source is `@mcp-b/webmcp-polyfill@5.1.0`
(fetched with `npm pack` into the job's tmp directory; `dist/index.js` and `dist/schema.js`).

**F1 — A Server Component cannot pass a tool registry to `<WebMcpTools>`.** SPEC §2.3 says each
page's own `layout.tsx` renders `<WebMcpTools tools={pageTools}/>`. `WebMcpTools` is a Client
Component; `pageTools` is an array of objects holding `execute` functions; a function is not a
serialisable prop across the RSC boundary. A `layout.tsx` is a Server Component. Written the
obvious way this compiles, type-checks and passes every unit test, then fails at render time —
the same class of defect as T-11's `.Provider` crash (process-log, T-11 entry, lesson 2).
**Resolution (D1):** `src/webmcp/tools/OverviewTools.tsx` is `"use client"`, imports the registry
itself and takes no props; `app/(app)/overview/layout.tsx` (a Server Component) renders
`<OverviewTools />` beside `children`. Only a real `next build && next start` run proves it, which
is what Task 3's smoke step and Task 4's E2E do.

**F2 — The SPEC §7 E2E call shape does not exist in the installed runtime.** §7 says
`executeTool("get_balance", {})` and "structuredContent equals …". The polyfill's
`ModelContext.executeTool(tool, inputArgsJson, options)` (`dist/index.js:757-770`) takes a
**registered-tool object** — one returned by `getTools()` — and a **JSON string**, and returns
`serializeChromeToolResult(result)` (`dist/schema.js:118-124`): a **JSON string** of the whole
`ToolResult`. The name-based `executeTool(name, json)` exists only on `navigator.modelContextTesting`
behind `installTestingShim: true` (`dist/index.js:871-875`), which is off by default and is the
deprecated `navigator` surface ADR-0004 rules out. So the E2E helper does:
`tool = (await context.getTools()).find(t => t.name === name)`, then
`JSON.parse(await context.executeTool(tool, JSON.stringify(input)))`. The same helper works against
a native Chrome's `document.modelContext`, where `executeTool` is the same Chromium extension.
**Also:** `getTools()` entries carry `window` and `origin` (`dist/index.js:743-752`), so they cannot
cross Playwright's `evaluate` boundary as returned; the helper projects them inside the page.
→ **Q1** (SPEC v1.0.4).

**F3 — `getTools()` projects annotations down to two hints.** `toWebMcpAnnotations`
(`dist/schema.js:105-109`) returns only `{ readOnlyHint, untrustedContentHint }`, each defaulting to
`false`. Consequences: `get_balance` reads back as `{ readOnlyHint: true, untrustedContentHint:
false }`; a Release 2 `consequentialHint` (NFR-W3, US-40) is **invisible through `getTools()` in
the polyfill**. So the full NFR-W3 annotation rule is asserted in a **unit test that iterates the
registry** (SPEC §7 unit row already says so), and E2E asserts only what a consumer can see. A
hand-off note for T-14/T-15 goes into the backlog (Task 6).

**F4 — `toErrorIssues` throws on `unrecognized_keys`.** Measured with the repo's Zod 4.6.5
(`z.strictObject({})` given `{ a: 1 }` → issue code `unrecognized_keys`; `z.object({})` given
`{ a: 1 }` parses and strips). `validationIssueCode` (`src/shared/schemas.ts`) has no case for
`unrecognized_keys`, so it throws `No validation code mapped …`. T-11's `defineTool` validates
outside its `try`, so routing a strict tool's failure through `toErrorIssues` unguarded would make
`execute` **reject** — breaking NFR-W6 ("errors are structured, not thrown"). `ToolResult` also has
no `issues` field, so the backlog hand-off "validation errors as `toErrorIssues`" has no home yet.
→ **Q2**.

**F5 — `X-Request-Id` is already on every response.** `middleware.ts` sets it (and forwards
`x-request-id` to handlers), and `tests/api/middleware.spec.ts` already asserts it. SPEC §7's API
row "responses carry `X-Request-Id`" needs no new production code; the new part is the *log*.

**F6 — Middleware and route handlers are separate bundles.** A module-level buffer written in
`middleware.ts` would not be the one `GET /api/test/log` reads. `src/server/db.ts` already solves
the same problem for the Prisma client by holding it on `globalThis`. The log follows that
pattern (D2), and the API test in Task 1 is the proof (an authenticated `GET /api/overview` with
`X-Via`, then `GET /api/test/log` from a different request).

**F7 — `WEBMCP_MODE` is baked in at build time.** `next.config.ts` inlines it as
`NEXT_PUBLIC_WEBMCP_MODE`, so `off` needs its own `next build`, not a runtime switch. Playwright's
`webServer` merges `process.env` into its command's environment (the CI jobs already rely on that
for `DATABASE_URL`), so the matrix leg's `WEBMCP_MODE` reaches `npm run build`. But
`reuseExistingServer: !CI` means a local run can silently reuse a build made in the other mode —
so each mode's spec self-verifies which build it is talking to (D8) instead of trusting the
environment variable.

## Open questions for the owner

**Q1 — Correct SPEC-webmcp-tools §7 (and §2.5's "the tool `execute`" wording) to what the runtime
does (F2, F3)?** §7's E2E rows say `executeTool("get_balance", {})` and "annotations"; the runtime
takes a tool object and a JSON string and returns a JSON string, and `getTools()` shows two hints.
**Recommendation: yes** — a v1.0.4 changelog line in Task 6, no ADR change (ADR-0004 names no call
signature), the same route T-04's F1 (→ v1.0.2) and T-11's Q1 (→ v1.0.3) took. Alternative: leave
the spec text and note the difference only in the E2E helper's comment — rejected because the DoD
says "the code never silently diverges" from the spec.

**Q2 — What does a tool's validation error carry, and are R1 inputs strict (F4)?**
- *(A, recommended)* Keep T-11's readable `message` and **add** `issues: ErrorIssue[]`
  (`toErrorIssues`, **guarded**: if the conversion throws — an unmapped Zod code — `issues` is
  omitted and the `message` still goes out). R1 tools declare `z.object({})` (unknown keys are
  stripped; the published schema carries no `additionalProperties: false`), so a stray key is not
  an error. A 400 from the API copies its `issues` through.
- *(B)* Fixed message + `issues` only, matching the API's "codes only" rule. Loses the readable
  text an agent can use; needs the same guard.
- *(C)* Leave T-11 as is; no `issues`. Simplest, but the T-04 hand-off (owner decision, backlog
  v1.9) is then not met.
If you choose strict inputs (`z.strictObject`) instead, the shared `VALIDATION_ISSUE_CODES` enum
gains an `unrecognized` code — a change to SPEC-auth §2.10's contract that this task would then
have to amend. Not recommended.

**Q3 — What does the `off` CI leg run?**
- *(A, recommended)* The **whole Chromium E2E suite** with `WEBMCP_MODE=off` — the strongest form
  of NFR-W2 ("the app functions identically in native, polyfill and off modes"). Cost: one more
  build and one more full Chromium run per PR (≈ the current E2E job again). Mode-specific specs
  skip themselves in the other mode.
- *(B)* Only `webmcp-off.spec.ts` (fast, the SPEC §7 "E2E (off)" row literally), and the rest of
  the suite stays polyfill-only.
Either way the polyfill leg keeps the job name `E2E (Chromium)` prefix; branch protection is not
available on this plan (403 on the API), so the rename cannot break a required check today —
T-16, which makes the repository public, sets the required checks and should list both legs.

## Review Focus

The spec is silent on these; a person or agent using the software would hit them.

1. **The registry is built in a Server Component** (Finding F1) — every authenticated page would
   crash while every unit test stays green. Expected: `/overview` renders, and `getTools()` lists
   both tools, under a real `next build && next start`. → Task 3 Step 9 (existing
   `overview.spec.ts` as the smoke) and Task 4's `US-38 AC1 AC3` test.
2. **A tool is called with input it does not declare** — `{ "a": 1 }`, `[]`, `null` or a scalar.
   Expected: the tool never rejects; an extra key is ignored, anything else is a structured
   `validation` result (the runtime itself blocks non-JSON before `execute`). → Task 2 Step 1
   (`defineTool` strict-schema case, `unrecognized_keys` must not throw) and Task 3 Step 1
   (`{a:1}`, `[]`, `null`, `"x"`, `42`).
3. **The session ended, or the API answers something that is not the DTO** — a 401, a 500, a 200
   with an HTML body, a network failure. Expected: a structured `unauthenticated` / `server_error`
   result and **no data**, never a throw (US-39 AC4). → Task 2 Step 1 (mapper), Task 3 Step 1
   (each outcome through both tools), Task 4 (`US-39 AC4` with the cookies cleared).
4. **The registry outlives its page, or exists where it should not** — tools still listed after a
   client navigation to Transactions, missing after coming back, or present on `/login`.
   Expected: `data-webmcp` absent and `getTools()` empty on Transactions; both tools again on
   return; no `document.modelContext` on `/login`. A hard `goto` would clear the registry
   trivially, so the test marks `window` first and asserts the mark survived (a *client*
   navigation). → Task 4.
5. **An `off`-mode (or `polyfill`) run that talks to the other mode's build and passes
   vacuously** (F7). Expected: a loud failure naming the mismatch. → Task 4's guard tests (D8),
   Task 5's matrix.

- [ ] **Step 2: Write the failing unit test for the log**

`tests/unit/server/request-log.test.ts`:

```ts
  REQUEST_LOG_CAPACITY,
  findViaRequest,
  recordViaRequest,
} from "@/src/server/request-log";

const TEST_ENV = { APP_ENV: "test" };

/** The buffer lives on globalThis (middleware and route handlers are separate bundles), so a
 * fresh module import does not clear it — each case starts by dropping the holder. */
beforeEach(() => {
  delete (globalThis as { __pfViaLog?: unknown }).__pfViaLog;
});

describe("recordViaRequest (SPEC-webmcp-tools §2.8)", () => {
  it("records an entry that is exactly { requestId, via, route } in test", () => {
    recordViaRequest("webmcp", "req-1", "/api/overview", TEST_ENV);
    expect(findViaRequest("req-1")).toEqual({
      requestId: "req-1",
      via: "webmcp",
      route: "/api/overview",
    });
  });

  it.each([null, "", "WebMCP", "webmcp, other", " webmcp", "browser"])(
    "ignores the X-Via value %j — only the exact marker is recorded",
    (via) => {
      recordViaRequest(via, "req-2", "/api/overview", TEST_ENV);
      expect(findViaRequest("req-2")).toBeUndefined();
    },
  );

  it("writes one JSON line to stdout and keeps nothing outside test", () => {
    const write = vi.fn();
    recordViaRequest("webmcp", "req-3", "/api/overview", { APP_ENV: "production" }, write);
    expect(write).toHaveBeenCalledTimes(1);
    expect(JSON.parse(write.mock.calls[0]![0] as string)).toEqual({
      requestId: "req-3",
      via: "webmcp",
```

```ts
import { VIA_WEBMCP } from "@/src/shared/via";
import { isTestEnv, type Env } from "./env";

/** SPEC-webmcp-tools §5: a ring buffer of 200 in test mode; structured stdout otherwise. */
export const REQUEST_LOG_CAPACITY = 200;

export type ViaLogEntry = { requestId: string; via: typeof VIA_WEBMCP; route: string };

// middleware.ts and the route handlers are compiled as separate bundles, so a module-level
// buffer written by one would not be the one the other reads. Like the Prisma client
// (src/server/db.ts), the buffer lives on globalThis. A Map keeps insertion order, so its
// first key is always the oldest entry.
const holder = globalThis as typeof globalThis & { __pfViaLog?: Map<string, ViaLogEntry> };

/**
 * SPEC-webmcp-tools §2.8: an API request a WebMCP tool made is recorded under the response's
 * `X-Request-Id`. Only the exact marker is recorded — never an arbitrary header value.
 */
export function recordViaRequest(
  via: string | null,
  requestId: string,
  route: string,
  env: Env = process.env,
  write: (line: string) => void = console.log,
): void {
  if (via !== VIA_WEBMCP) return;
  const entry: ViaLogEntry = { requestId, via: VIA_WEBMCP, route };
  if (!isTestEnv(env)) {
    write(JSON.stringify(entry));
    return;
  }
  const log = (holder.__pfViaLog ??= new Map());
  log.set(requestId, entry);
  if (log.size > REQUEST_LOG_CAPACITY) {
    const oldest = log.keys().next().value;
    if (oldest !== undefined) log.delete(oldest);
  }
}

export function findViaRequest(requestId: string): ViaLogEntry | undefined {
  return holder.__pfViaLog?.get(requestId);
}
```

```ts
import type { z } from "zod";
import { ErrorEnvelopeSchema, type ErrorEnvelope } from "./schemas";

/**
 * SPEC-webmcp-tools §2.5 / ADR-0004: the fetch wrapper WebMCP tools use to reach the same
 * authenticated API as the UI. It never throws: every way a request can end is a value, so a
 * caller (a tool's `execute`) maps it once. It keeps no opinion about tool error codes — that
 * mapping is `src/webmcp/tool-result.ts`. The login and signup forms keep their own `fetch`
 * (moving them here is a separate change).
 */
export type ApiOutcome<T> =
  | { ok: true; data: T }
  /** A non-2xx answer; `error` is its envelope, or `null` when the body was not one. */
  | { ok: false; kind: "http"; status: number; error: ErrorEnvelope | null }
  /** A 2xx answer whose body was not JSON, or did not match the schema (drift, a proxy's page). */
  | { ok: false; kind: "invalid_response"; status: number }
  | { ok: false; kind: "aborted" }
  | { ok: false; kind: "network" };

export interface ApiGetOptions {
  signal?: AbortSignal;
  headers?: Record<string, string>;
}

const isAbort = (error: unknown): boolean =>
  error instanceof Error && error.name === "AbortError";

export async function apiGet<T>(
  path: string,
  schema: z.ZodType<T>,
  options: ApiGetOptions = {},
): Promise<ApiOutcome<T>> {
  let response: Response;
  try {
    response = await fetch(path, {
      method: "GET",
      headers: options.headers,
      signal: options.signal,
      credentials: "same-origin",
    });
  } catch (error) {
    return isAbort(error) ? { ok: false, kind: "aborted" } : { ok: false, kind: "network" };
  }

  let body: unknown;
  try {
    body = await response.json();
  } catch (error) {
    if (isAbort(error)) return { ok: false, kind: "aborted" };
    body = null;
  }

  if (response.ok) {
    const parsed = schema.safeParse(body);
    return parsed.success
      ? { ok: true, data: parsed.data }
      : { ok: false, kind: "invalid_response", status: response.status };
  }
  const envelope = ErrorEnvelopeSchema.safeParse(body);
  return {
    ok: false,
    kind: "http",
    status: response.status,
    error: envelope.success ? envelope.data : null,
  };
}
```

```ts
import type { ApiOutcome } from "@/src/shared/api-client";
import type { ErrorIssue } from "@/src/shared/schemas";
import type { ToolResult } from "./types";

/** ADR-0004 / SPEC-webmcp-tools §2.5: every way a tool call can end short of success. */
export const TOOL_ERROR_CODES = [
  "validation",
  "unauthenticated",
  "not_found",
  "conflict",
  "rate_limited",
  "cancelled",
  "server_error",
] as const;
export type ToolErrorCode = (typeof TOOL_ERROR_CODES)[number];

/** Read by agents, not users: the fallback when the API's envelope carries no message. */
export const DEFAULT_TOOL_MESSAGE: Record<ToolErrorCode, string> = {
  validation: "Invalid input",
  unauthenticated: "Log in to continue",
  not_found: "Not found",
  conflict: "The data changed; try again",
  rate_limited: "Too many requests; try again later",
  cancelled: "The request was cancelled",
  server_error: "Something went wrong",
};

/**
 * SPEC-webmcp-tools §2.6: the API DTO unchanged (integer cents) plus `{ currency, unit }` at
 * the top level, mirrored as text so a consumer that reads only `content` still gets it.
 */
export function toolSuccess(data: Record<string, unknown>): ToolResult {
  const structured = { ...data, currency: "USD", unit: "cents" };
  return {
    content: [{ type: "text", text: JSON.stringify(structured) }],
    structuredContent: structured,
  };
}

export function toolError(
  code: ToolErrorCode,
  message: string,
  extra: { issues?: ErrorIssue[] | undefined; retryAfter?: number | undefined } = {},
): ToolResult {
  return {
    isError: true,
    code,
    message,
    content: [{ type: "text", text: message }],
    ...(extra.issues === undefined ? {} : { issues: extra.issues }),
    ...(extra.retryAfter === undefined ? {} : { retryAfter: extra.retryAfter }),
  };
}

function codeForStatus(status: number): ToolErrorCode {
  switch (status) {
    case 400:
      return "validation";
    case 401:
      return "unauthenticated";
    case 404:
      return "not_found";
    case 409:
      return "conflict";
    case 429:
      return "rate_limited";
    default:
      return "server_error";
  }
}

/** SPEC-webmcp-tools §2.5's mapping; the result is always a value, never a throw. */
export function fromApiOutcome<T>(
  outcome: ApiOutcome<T>,
  onSuccess: (data: T) => ToolResult,
): ToolResult {
  if (outcome.ok) return onSuccess(outcome.data);
  switch (outcome.kind) {
    case "aborted":
      return toolError("cancelled", DEFAULT_TOOL_MESSAGE.cancelled);
    case "network":
    case "invalid_response":
      return toolError("server_error", DEFAULT_TOOL_MESSAGE.server_error);
    case "http": {
      const code = codeForStatus(outcome.status);
      return toolError(code, outcome.error?.message ?? DEFAULT_TOOL_MESSAGE[code], {
        issues: outcome.error?.issues,
        retryAfter: outcome.error?.retryAfter,
      });
    }
  }
}
```

```ts
import { WebMcpModeSchema } from "@/src/shared/schemas";
import type { ToolResult } from "@/src/webmcp/types";

/**
 * The mode this Playwright run expects the app under test to have been *built* with.
 * `WEBMCP_MODE` is inlined at build time (`next.config.ts`), so the spec cannot switch it; it
 * can only say which build it expects and check (`webmcp*.spec.ts`, plan D8). Empty or unset is
 * "polyfill", as everywhere else.
 */
export const RUN_MODE = WebMcpModeSchema.catch("polyfill").parse(process.env.WEBMCP_MODE || undefined);

/** The runtime's calling convention, plan Finding F2 (`document.modelContext`, Chromium extension). */
type RegisteredTool = { name: string } & Record<string, unknown>;
type ChromeModelContext = {
  getTools(): Promise<RegisteredTool[]>;
  executeTool(tool: RegisteredTool, inputJson: string): Promise<string>;
};

export interface ListedTool {
  name: string;
  title: string;
  description: string;
  inputSchema: { type?: string; properties?: Record<string, unknown> } & Record<string, unknown>;
  annotations: Record<string, boolean>;
}

/** Waits for the adapter's readiness signal (US-38 AC3, R-13). */
export async function expectToolsReady(page: Page): Promise<void> {
  await expect(page.locator("html")).toHaveAttribute("data-webmcp", "ready");
}

/**
 * `getTools()` entries carry `window` and `origin`, which cannot be returned across
 * `page.evaluate`, so each is projected to plain data inside the page.
 */
export async function listTools(page: Page): Promise<ListedTool[]> {
  return page.evaluate(async () => {
    const context = document.modelContext as unknown as ChromeModelContext;
    const tools = await context.getTools();
    return tools.map((tool) => ({
      name: tool.name,
      title: tool.title as string,
      description: tool.description as string,
      inputSchema: tool.inputSchema as ListedTool["inputSchema"],
      annotations: (tool.annotations ?? {}) as Record<string, boolean>,
    }));
  });
}

/** Calls a tool the way a consumer does: find it in `getTools()`, pass a JSON string, parse the JSON string back. */
export async function callTool(page: Page, name: string, input: unknown = {}): Promise<ToolResult> {
  const raw = await page.evaluate(
    async ({ name: toolName, json }) => {
      const context = document.modelContext as unknown as ChromeModelContext;
      const tool = (await context.getTools()).find((candidate) => candidate.name === toolName);
      if (!tool) throw new Error(`no registered tool named ${toolName}`);
      return context.executeTool(tool, json);
    },
    { name, json: JSON.stringify(input) },
  );
  return JSON.parse(raw) as ToolResult;
}
```
