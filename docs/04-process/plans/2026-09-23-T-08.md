**Architecture:** `src/server/meta.ts` adds one function, `getMeta(db, env?): Promise<MetaDto>`,
that composes three already-scattered pieces of state into the one DTO SPEC-app-shell §5
defines: the latest reset time (a **new** `latestReset(db)` in `src/server/reset.ts`, built on
top of T-05's `latestResetAt`, per the T-05 hand-off — it throws instead of returning `null`,
because the DTO's `lastResetAt` is documented as "always present"), the configured reset
interval and WebMCP mode (new env accessors), and whether an origin-trial token is configured
(T-07's `webmcpOriginTrialToken`, already built). `app/api/meta/route.ts`'s `GET` calls the same
function directly — no HTTP self-call, per §2.1 — and so does `app/(app)/layout.tsx`, in a

`Shell`, which renders a new `ResetBanner` as the first thing inside `<main>`, above
`{children}`, only when `meta` is not null; `ResetBanner` reads its own dismissal from
`sessionStorage["pf.banner"]` after mount (plain `useState`, not the sidebar's
`useSyncExternalStore` — nothing else on the page depends on this value, so there is no tearing
concern to guard against, D8). `src/server/threshold.ts` gets its own file, split the same way
T-05 split `rate-limit.ts`: a pure `evaluateThreshold(rows, bytes, rowThreshold, byteThreshold)`
(unit-tested) and an impure `checkThreshold(db, env?)` that counts non-seed rows across
`Transaction`, `Budget` and `Pot` and reads `pg_database_size(current_database())` (API-tested
against the real database, like `checkRateLimit`). `app/api/admin/reset/route.ts` exports both
`POST` (SPEC's documented shape: optional JSON body, `reason` defaults `"manual"`) and `GET`
(Vercel's cron invocation carries no body — Q1 below — always `reason: "scheduled"`); both check
the `Authorization: Bearer` header against `RESET_SECRET` or `CRON_SECRET` with
`crypto.timingSafeEqual`, then call `resetToSeed(db, reason)` and answer 204. `middleware.ts`
already treats `/api/meta` as public and `/api/admin/reset` as session-exempt (T-05/T-07); the

`X-Request-Id` into its own log line (SPEC-reset-and-test-support §2.2).

## Questions for the owner

### Q1 — Vercel Cron sends `GET`, not the `POST` with a body the spec describes

*Plain language: SPEC-reset-and-test-support §2.3 says Vercel's cron calls `POST
/api/admin/reset` with a JSON body `{ "reason": "scheduled" }`. Vercel's Cron Jobs feature does
not work that way: it invokes the configured `path` with a plain `GET` request, no body, and
attaches `Authorization: Bearer $CRON_SECRET` itself — `vercel.json`'s `crons` entries only ever
take `path` and `schedule`, nothing about a method or a body.*

**Evidence.** This is an external platform fact, not something in this repository, and this
session's network access is restricted to an allowlist that does not include `vercel.com` or any
mirror of its docs — every fetch attempt during planning (`vercel.com/docs/cron-jobs`,
`cronuru.com`, `dev.to`) was refused by the egress proxy before it reached the network. What
follows is the agent's trained knowledge of the product (GA since 2023, materially unchanged
since), not a citation the agent could verify live in this session — flagged per governance
("record uncertainty explicitly rather than choosing silently") rather than treated as
confirmed. T-14 (Deploy) sets up the real Vercel project and the row says "cron verified" — that
is where this gets a live check, against the real dashboard, before it matters in production.

- **(a) Recommended — the route accepts both methods.** `GET /api/admin/reset` (secret check,
  then `resetToSeed(db, "scheduled")`, no body to parse) is what a real Vercel cron invocation
  hits; `POST /api/admin/reset` (secret check, optional JSON body, `reason` defaulting
  `"manual"`) is what SPEC-reset-and-test-support §2.2 already describes and what a human
  operator or a future R2 caller uses. `vercel.json`'s entry only needs `path` and `schedule`
  either way, so this costs nothing at the `vercel.json` end and is correct whichever way
  Vercel's platform turns out to behave. SPEC-reset-and-test-support gets a v1.3 changelog line
  in this task's own PR (DoD: "if the spec was wrong or incomplete, the spec is amended in the
  same PR"), not a separate gate PR. Cost: one extra exported handler, four extra API tests (GET
  with each secret, GET without one, GET with a body Vercel would never send but a test can).
- **(b) Trust the spec's `POST`-only text, fix it at T-14 if wrong.** Simpler now; if the
  agent's recollection is right, the scheduled reset silently never fires in production (a
  `GET` hits a route with no `GET` handler → Next answers 405) until T-14's "cron verified" step
  catches it — five tasks and an unknown number of days later, on a portfolio deploy nobody is
  watching closely. Rejected: SPEC-reset-and-test-support §5 ("US-37 AC1: the dataset resets
  fully to seed every 10 days") is the requirement this would quietly fail.
- **(c) Ask the owner to check Vercel's current docs directly** (a five-minute read, no
  ambiguity) before either the plan or the code commits to an answer. Cheapest way to a
  ground-truth answer; slower than (a), which is correct regardless of the answer.

## Decisions taken in this plan (the agent's, reviewable)

| # | Decision | Why | Alternative not taken |
|---|----------|-----|------------------------|
| D1 | `latestReset(db)` (new, `src/server/reset.ts`) calls T-05's `latestResetAt(db)` and **throws** if it returns `null`, instead of returning an optional date | SPEC-app-shell §5: `lastResetAt` is "always present — the first seed writes a `ResetLog` row" (SPEC-reset-and-test-support §2.5 guarantees this on every deploy and every `db:reset`). A `null` here means the guarantee was broken (a database that was never seeded), which is a configuration fault, not a normal state the DTO's type should have to represent. `getMeta` lets the throw propagate; the layout's `catch` (§3: "meta unavailable → no banner") is the one place that has to cope with it, and it already has to exist for any other failure (a DB outage) | Return `Date \| null` and push the "what if it's null" question onto `getMeta` and the route — two extra callers would need the same never-really-null check `latestReset` can do once |
| D2 | `src/server/threshold.ts` splits a pure `evaluateThreshold(rows, bytes, rowThreshold, byteThreshold): { exceeded: boolean; reason: "rows" \| "bytes" \| null }` from an impure `checkThreshold(db, env?)` that gathers the two numbers and calls it | Mirrors `src/server/rate-limit.ts`'s `evaluateAttempts`/`checkRateLimit` split exactly (T-05) — the decision logic is unit-tested without a database, the DB access is proven once against the real one (ADR-0003, T-05's own precedent: `checkRateLimit` itself has no unit test, only `evaluateAttempts` does) | One function that both queries and decides — untestable without Postgres, unlike every other piece of decision logic in `src/server` |
| D3 | `checkThreshold`'s row count is `Transaction.count({seeded:false}) + Budget.count({seeded:false}) + Pot.count({seeded:false})` — **excludes** `ResetLog` and `LoginAttempt` | US-37 AC1 says "**user-created rows**" — `ResetLog` and `LoginAttempt` are operational/audit tables, not user content, and `LoginAttempt` specifically is written by every failed login (`recordAttempt`, T-05); counting it would let an attacker force a demo reset by spamming wrong passwords, a self-inflicted denial-of-service the rate limiter (10/15 min/IP, unaffected by this choice) does not fully close on its own since many IPs could each stay under it while the *sum* crosses 2,000. | D5 | `app/api/admin/reset/route.ts` exports **both** `GET` and `POST` (Q1 (a)); `GET` never reads a body and always resets with `reason: "scheduled"`; `POST` parses an optional JSON body through `AdminResetSchema` | Q1's recommendation, made concrete: whichever method Vercel's cron actually sends, this route answers it correctly, and the documented `POST` shape keeps working for a human operator (`curl`) or a future caller | `GET`-only — would break a `curl -X POST` operator's manual "reason": "manual" call SPEC-reset-and-test-support §2.2 documents; `POST`-only — the risk Q1 (b) describes |
| D6 | The secret check is `crypto.timingSafeEqual` on the provided bearer token against `RESET_SECRET`, then against `CRON_SECRET` if that one is configured (non-empty); either match succeeds; a length mismatch on either comparison short-circuits to "no match" without calling `timingSafeEqual` (which throws on unequal-length buffers) | SPEC-reset-and-test-support §2.3: "the route accepts either secret" (no per-method restriction in the spec text, so both methods accept both secrets, D5's `GET`/`POST` split is orthogonal to which secret is valid); `bcrypt.compare`'s existing use for the login password (T-05) is this project's precedent for not doing a plain `===` on a secret. Residual signal: the length check itself is a timing side-channel on the secret's *length*, not its content — accepted, since both secrets are long, random, operator-configured strings a network attacker has no way to have already learned a prefix of, unlike a user-chosen password | A plain `===` string comparison — the T-05 precedent (bcrypt for the password compare) is exactly the "don't do this for a secret" lesson this project already learned once |
| D7 | `cronSecret(env)` returns `null` when `CRON_SECRET` is unset **or empty**, and a `null` secret can never match any bearer token, including an absent or empty `Authorization` header | An unset `CRON_SECRET` is normal locally and in every environment except a real Vercel deployment (`.env.example` ships it blank); treating `""` as a valid secret to match against would let a request with **no** `Authorization` header at all (`bearerToken()` returning `""` from a malformed header, or a client sending `Bearer ` with nothing after it) succeed against an unconfigured secret — the exact "empty equals empty" bug Review Focus 1 below tests for | Requiring `CRON_SECRET` to be set (throw like `resetSecret`) — would make every local `npm run dev` and every test run need a value nothing else uses |

## Review Focus

1. **An unconfigured `CRON_SECRET` that matches an absent header.** `cronSecret(env)` returning
   `""` instead of `null` for an unset variable, compared against a missing `Authorization`
   header read as `""`, would let every unauthenticated request into the admin endpoint the
   moment someone forgets to set `CRON_SECRET` (which is every environment except a real
   deployment, per `.env.example`). Expected: 401 on `POST /api/admin/reset` with no
   `Authorization` header at all, in an environment where `CRON_SECRET` is unset. → Task 3's
   API tests; the mutation is changing D7's `null` return to `""` and watching the "no header"
   test start passing for the wrong reason (a `""===""` match) instead of failing closed.
2. **`checkThreshold` counting `LoginAttempt`.** A self-inflicted reset via failed-login spam
   (D3). Expected: 2,001 failed `LoginAttempt` rows alone do not trip `checkThreshold`; 2,001
   non-seed `Transaction` rows do. → Task 1's API test seeds both cases against the real
   database and asserts the difference; the mutation is adding `LoginAttempt.count()` into the
   sum and watching the first case start reporting `exceeded: true`.
3. **`getMeta` fabricating a date when `ResetLog` is empty.** Expected: `getMeta` (and
   therefore `GET /api/meta`) throws when no `ResetLog` row exists; the layout's `catch` (§3)
   is what turns that into "no banner", not a made-up date. → Task 2's API test empties

```ts
import type { Db } from "./db";
import { resetBytesThreshold, resetRowThreshold, type Env } from "./env";

export type ThresholdResult = { exceeded: boolean; reason: "rows" | "bytes" | null };

/**
 * SPEC-reset-and-test-support §2.4: "> RESET_ROW_THRESHOLD" / "> RESET_BYTES_THRESHOLD" — a
 * boundary value does not trip it. Rows checked first so a row-count breach is always reported
 * as "rows" even when the database also happens to be over its byte threshold.
 */
export function evaluateThreshold(
  rows: number,
  bytes: number,
  rowThreshold: number,
  byteThreshold: number,
): ThresholdResult {
  if (rows > rowThreshold) return { exceeded: true, reason: "rows" };
  if (bytes > byteThreshold) return { exceeded: true, reason: "bytes" };
  return { exceeded: false, reason: null };
}

/**
 * SPEC-reset-and-test-support §2.4: counts non-seed rows across the three user-content tables
 * only — never ResetLog or LoginAttempt (plan D3) — and the database's total on-disk size.
 * R1 wires this but nothing calls it yet (no write endpoint exists before Release 2).
 */
export async function checkThreshold(db: Db, env: Env = process.env): Promise<ThresholdResult> {
  const [transactions, budgets, pots, [{ size }]] = await Promise.all([
    db.transaction.count({ where: { seeded: false } }),
    db.budget.count({ where: { seeded: false } }),
    db.pot.count({ where: { seeded: false } }),
    db.$queryRaw<{ size: bigint }[]>`SELECT pg_database_size(current_database()) AS size`,
  ]);
  const rows = transactions + budgets + pots;
  return evaluateThreshold(rows, Number(size), resetRowThreshold(env), resetBytesThreshold(env));
}
```

```ts
import { timingSafeEqual } from "node:crypto";
import { getDb } from "@/src/server/db";
import { cronSecret, resetSecret } from "@/src/server/env";
import { errorResponse, validationErrorResponse } from "@/src/server/http";
import { resetToSeed } from "@/src/server/reset";
import { AdminResetSchema } from "@/src/shared/schemas";
import { toErrorIssues } from "@/src/shared/schemas";

function bearerToken(request: Request): string | null {
  const header = request.headers.get("authorization");
  return header?.startsWith("Bearer ") ? header.slice("Bearer ".length) : null;
}

// Plan D6/D7: a length mismatch fails closed without calling timingSafeEqual, which throws on
// unequal-length buffers; `expected === null` (cronSecret unset) never matches anything, D7.
function matchesSecret(provided: string | null, expected: string | null): boolean {
  if (provided === null || expected === null) return false;
  const a = Buffer.from(provided);
  const b = Buffer.from(expected);
  return a.length === b.length && timingSafeEqual(a, b);
}

function authorized(request: Request): boolean {
  const token = bearerToken(request);
  return matchesSecret(token, resetSecret()) || matchesSecret(token, cronSecret());
}

async function runReset(reason: "scheduled" | "threshold" | "manual", requestId: string) {
  const { at, rows } = await resetToSeed(getDb(), reason);
  console.log(`reset reason=${reason} rows=${rows} requestId=${requestId}`);
  return at;
}

/** SPEC-reset-and-test-support §2.2. */
export async function POST(request: Request): Promise<Response> {
  if (!authorized(request)) {
    return errorResponse(401, "unauthenticated", "Invalid or missing secret");
  }
  const rawBody: unknown = await request.json().catch(() => ({}));
  const parsed = AdminResetSchema.safeParse(rawBody);
  if (!parsed.success) {
    return validationErrorResponse(toErrorIssues(parsed.error));
  }
  const requestId = request.headers.get("x-request-id") ?? "unknown";
  await runReset(parsed.data.reason, requestId);
  return new Response(null, { status: 204 });
}

/** SPEC-reset-and-test-support §2.3, plan Q1/D5: Vercel's cron sends a bare GET, no body. */
export async function GET(request: Request): Promise<Response> {
  if (!authorized(request)) {
    return errorResponse(401, "unauthenticated", "Invalid or missing secret");
  }
  const requestId = request.headers.get("x-request-id") ?? "unknown";
  await runReset("scheduled", requestId);
  return new Response(null, { status: 204 });
}
```
