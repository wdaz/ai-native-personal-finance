**Goal:** make `develop` the integration branch and `main` production-only, as `governance.md` v1.5
"Branches and releases" decided: `develop` exists and is protected like `main`, CI and CodeQL run on it,
a required check refuses any pull request to `main` whose head is not `develop` or a hotfix branch, and
AGENTS.md §2, the PR template, `governance.md` and the runbook say so — then close T-15b.

**Architecture:** GitHub has no ruleset rule that limits a pull request's **head** branch, which is why
`governance.md` chose a required status check. The check is a small POSIX script,
`scripts/check-release-source.sh`, run by a `pull_request_target` workflow. That event runs the
**default branch's** copy of the workflow and checks out the default branch, never the pull request's
files, so a pull request cannot rewrite the rule it is judged by. That is also why the default branch
matters (Q2): if it is `develop`, the check works as soon as PR A merges into `develop`. The rulesets
move from "the default branch" to explicit branch names before the default changes (F1), `develop` gets
two rulesets that copy `main`'s, and the check joins `main`'s required checks. Two work pull requests to
`develop` — **A** the workflows, the script and its test; **B** the documents and the close-out — with
the settings steps between them, and (Q4) the first `develop` → `main` release at the end. No
application code changes.

**Tech Stack:** GitHub rulesets and repository settings through `gh api` (REST), GitHub Actions
(`pull_request_target`, `actions/checkout` v7.0.1 at the pin `ci.yml` already uses), POSIX `sh`, Vitest
(`tests/unit`, run by the required `lint · typecheck · unit` check), the Vercel CLI 60.0.1 for one read.

**Spec:** T-15b has no feature spec (like T-13d, T-15a and T-16). It implements backlog T-15b's row,
`governance.md` v1.5 "Branches and releases" (the decision and its "Open at the switch" list) and
ADR-0007 (`main` → Vercel production, unchanged).

## Review Focus

The inputs and conditions the row implies but no task's tests exercise directly, most likely first.

1. **Whether a `pull_request_target` check run counts for the pull request's head commit** (*prediction*:
   it does — the run is shown on the pull request and its job name is the status context). GitHub's
   2025-11-07 changelog says the event's workflow file, `GITHUB_REF` and `GITHUB_SHA` are the default
   branch's; it says nothing about which commit the check is attached to. If the required context never
   reaches the head commit, every pull request to `main` waits forever. Task S8's probe is the test. If
   it fails, the fallback is `pull_request` (the check then runs the pull request's own copy of the
   script, which a pull request could edit — visible in its diff, and the owner merges); that fallback
   goes to the owner, not in silently.
2. **A stale AGENTS.md on `main`.** Until a release carries PR B to `main`, `main`'s AGENTS.md still says
   "start from `origin/main`". A new session in a checkout that sits on `main` reads that rule first. Q4
   (a release right after B) closes the gap; until then Task S6 asks the owner to switch the main
   checkout to `develop`.
3. **A pull request re-targeted to `main` after it was opened** (base changed from `develop`). The
   workflow listens to `edited`, which fires on a base change (*prediction*); Task A2's test pins that
   `edited` is in the list. Not probed live.
4. **A release merged by squash or rebase.** Either leaves `develop` without `main`'s new commit, so the
   next release shows old changes again and can conflict. Q5 restricts `main` to merge commits. The back
   merge of a hotfix (Q3) has the same need.
5. **`develop` deleted by the release merge.** The repository deletes a merged pull request's head branch
   (`delete_branch_on_merge: true`, *measured*). GitHub: "Branch protection rules and repository rules can
   also prevent branches being automatically deleted" (docs, read 2026-09-29) — `develop`'s ruleset
   carries the `deletion` rule (Task S3), and a default branch is not deleted either (*prediction*).
   Observed first at the release (Task R1).
6. **CodeQL's merge protection on `develop` before CodeQL has ever run there.** GitHub's documentation
   read 2026-09-29 does not say what the `code_scanning` rule does when the base branch has no analysis.
   D3 orders it so the question never arises: the rule is added to `develop`'s ruleset only after
   CodeQL's first push run on `develop` (Task S5).

  # The head-branch check behind main's required `release source` status (governance.md, "Branches and
  # releases", T-15b): main takes pull requests from this repository's develop (a release) or a
  # hotfix/<name> branch (a production fix) only. .github/workflows/release-source.yml passes the pull
