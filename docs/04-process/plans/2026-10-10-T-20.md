## Goal

The server half of the Recurring Bills page: the pure list rules in `src/domain/bills.ts` (`sortBills` with its six
orders and the name tie-break, `filterBills` for the search and the API's status, `billsTotals` for the four summary
rows; `BillStatus` becomes the type of `BILL_STATUSES`), the shared query contract (`parseRecurringBillsQuery`,
lenient for the page and strict for the API, and `BILL_STATUSES` in `src/shared/recurring-bills-query.ts`), the
ordinal due text `formatDueDay`, the strict `RecurringBillsDtoSchema`, `src/server/recurring-bills.ts`
(`getRecurringBills`, `toRecurringBillsDto`) and the read route `GET /api/recurring-bills?q&sort&status`, with the
seed's figures of `recurring-bills.md` 4.2–4.5 moved into `scripts/seed-figures.ts` (H14 (2)).

**What T-20 is not:** no page, no component, no `ResultsRegion` move, no copy strings (H14 (1)), no tool
(`list_recurring_bills`, 2.12) — all T-21. Nothing here is drawn, so no design question arises and nothing visual
changes.

## Decisions taken in the plan (the spec leaves them to the build)

- **D1. Domain** (`src/domain/bills.ts`, pure, generic over the bill as `recurringBills` is): `sortBills(bills,
  sort)` — 2.4's table: `latest` day ascending, `oldest` day descending, `a-to-z`, `z-to-a`, `highest` amount
  descending, `lowest` amount ascending; every key list ends in name A to Z with the module's
  `Intl.Collator("en")`, then UTF-16 code-unit order for two strings the collator calls equal (2.4: a total order).
  `filterBills(bills, { q, status })` — the needle trimmed and lower-cased on both sides with `includes` (no pattern
  characters), the status by `===`. `billsTotals(bills)` → `{ total, paid, totalUpcoming, dueSoon }`, each
  `{ count, amount }` in cents, through `sumCents`; `billsSummary` stays unchanged. `BillStatus` becomes
  `(typeof BILL_STATUSES)[number]`, imported from `src/shared` (allowed by `eslint.config.mjs`).
- **D2. Shared** (`src/shared/recurring-bills-query.ts`): `BILL_STATUSES = ["paid", "dueSoon", "upcoming"]`,
  `RECURRING_BILLS_Q_MAX = 60`, and `parseRecurringBillsQuery(params, { strict })` → `{ query, issues, message }`
  with `query = { q, sort, status }`: every row of 2.3, written by hand with `invalid_format` and `too_long`; the
  lenient page ignores `status` (always `undefined`); issues in the URL contract's order `q`, `sort`, `status`;
  empty values read as absent; a repeated parameter reads as its first value; the sort slugs are
  `TRANSACTION_SORTS` (F5). The helper that reads the first value moves out of `transactions-query.ts` into a small
  shared module both parsers import, so the two parsers cannot drift on 2.2's rules.
- **D3. `formatDueDay`** (`src/shared/dates.ts`, beside `formatDate`): `Monthly - {n}{st|nd|rd|th}`, with 11–13
  `th` (2.9); throws for a day outside 1–31 or not an integer, as `formatDate` throws for a bad date.
- **D4. The DTO** (`src/shared/schemas.ts`): `RecurringBillsDtoSchema`, a `z.strictObject` with strict items
  (`name` 1–60, `avatar` `AVATAR_KEY`, `day` integer 1–31, `amount` integer ≥ 0, `status` `z.enum(BILL_STATUSES)`)
  and a strict `summary` of four strict `{ count: integer ≥ 0, amount: integer ≥ 0 }` rows. No `max` on `items`:
  2.11 bounds it by the number of bills, which the schema cannot know.
- **D5. Server** (`src/server/recurring-bills.ts`): `getRecurringBills(db, clock, query)` reads
  `db.transaction.findMany` with a `select` of the fields the bills use (no `where`, no `orderBy`, 2.4), maps `BigInt`
  → `Number` and the category through `categoryLabel` (the `TransactionInput` shape `recurringBills` takes), builds
  the bills, takes `billsTotals` over **all** of them, then filter → sort, and returns `toRecurringBillsDto`, which
  names every field (the `toOverviewDto` pattern), so `latest`, ids and dates never reach the DTO.
- **D6. The route** (`app/api/recurring-bills/route.ts`): `GET` only; strict parse → 400 via
  `validationErrorResponse(issues, 400, message)`; `getRecurringBills(getDb(), fixedClock(BUSINESS_TODAY), query)` →
  `Response.json(dto)` with `Cache-Control: no-store`; a throw → `console.error("GET /api/recurring-bills failed",
  error)` and `errorResponse(500, "server_error", "The recurring bills are unavailable")`. The helpers already set
  `no-store`. T-17's route-table guard already holds a `GET` that never calls `guardedWrite`.
- **D7. Figures (H14 (2)).** `scripts/seed-figures.ts` gains `seedBills()` (the seed's transactions through
  `recurringBills` on the business day) and `billFigures()`: 4.2's per-vendor line and summary, 4.3's table
  (generated cell by cell: Latest with each day's ordinal, Highest with each amount, the rest names only), 4.3's
  tie facts, and 4.5's search and status examples, all computed with the functions of D1–D3.
  `tests/unit/seed-figures.test.ts` holds 4.3's table to the generated one (with one violation fixture: Highest
  with Spark before Aqua, the design's old order) and the prose of 4.2 and 4.5 to the generated text; the spec's
  prose is never parsed for numbers.
- **D8. One spec amendment, `recurring-bills.md` v0.7.1**, the first commit after the answers: 2.3 (the
  parser returns `message`; Q1's joined message; the cut of `q` as `transactions.md` 2.3 v1.0.17), 2.11 (the
  helpers' `no-store` sentence corrected), §7 (Q2: "500" moves from the API row to the shared-and-server row).
  It is approved by the merge of this task's pull request, as T-18's v1.0.17 was.
- **D9. Traceability** (F6): US-29 and US-30 leave `NOT_YET_BUILT`; ADR-0003's dated line gets one more sentence
  with the 12 ids.
- **D10. One pull request** for the whole task, one commit per task A–E below (the T-18 precedent).
