**Goal:** The frame every authenticated page lives in — the `(app)` layout, the desktop
sidebar with its minimise toggle (US-35), the tablet/mobile bottom bar, the page header, the
skip link, the "Log out" control with a logout that always completes (US-03 AC1–AC2), the
back/forward-cache session re-check, and the four Release 2 routes as "Coming in Release 2"

(`no-store` isolated from Next's own default), and the E2E suite for US-03 AC1–AC2, US-32,
US-33, US-34 and US-35 on these pages with axe.

**Architecture:** `app/(app)/layout.tsx` is a Server Component that calls `connection()` —
every app page then renders per request and carries T-05's CSP nonce (a prerendered page
would ship Next's inline scripts without it and never hydrate) — renders the origin-trial
`<meta>` only when `WEBMCP_ORIGIN_TRIAL_TOKEN` is set, and wraps the page in `Shell`, a client
component from `src/ui` (SPEC-app-shell §6 names every shell component there). `Shell` puts
"Skip to content" first, then `Sidebar` (≥ 1024 px), the page in `<main>`, and `BottomNav`
(< 1024 px); CSS alone switches between them, so the server renders one tree for every width.
The sidebar's minimised state is read from `sessionStorage` through `useSyncExternalStore`
after hydration. Navigation is `next/link` with `aria-current`; logout is a full page load
(`window.location.assign`) so the client router keeps no app page in memory for Back to
reveal, and a page restored from the back/forward cache asks `GET /api/auth/session` before
it stays. A failed logout request completes through `/login?reason=logout`, a same-origin
navigation the middleware answers by clearing the cookie (Q1). Page names, nav labels and the
document titles come from one object (`PAGE_NAMES` in `src/ui/nav.ts`). Design values only
from `src/ui/tokens.css` through CSS Modules; no `style` prop anywhere (ADR-0006's
`style-src`).

## Questions for the owner

*All four answered as recommended — the questions stay below as the record of what was asked.*

### Q1 — A logout whose request fails cannot reach the login page (SPEC-auth §2.7 vs §2.8)

*Plain language: the specs say the "Log out" button takes you to the login page even when
the server call fails. But the session cookie can only be removed by the server — the page's
JavaScript cannot touch it (it is `httpOnly`, on purpose). So after a failed call you still
have a valid session, and the middleware sends any logged-in visitor who opens `/login` back
to `/overview`. The user clicks "Log out" and lands on Overview, still logged in.*

**Evidence.** SPEC-auth §2.7: "The client navigates even if the request fails (logged to
console)." §2.8: "Authenticated request to `/login` or `/signup` → 302 `/overview`."
`middleware.ts` implements §2.8 (`AUTH_PAGES.test(pathname) && authenticated` → redirect).
`pf_session` is `HttpOnly` (§2.9, `src/server/session.ts:64`). US-03 AC2: "Logout always
completes client-side even if the server call fails; the failure is logged." The E2E test
T-07's row asks for (`page.route(…/api/auth/logout…).abort()`, then click "Log out") would
end on `/overview`.

- **(a) Recommended — a fallback URL the middleware honours.** When the request fails (no
  answer within 10 s, or a non-2xx answer) the client logs it and navigates to
  `/login?reason=logout`. The middleware, for that URL only **and only when the browser marks
  the navigation `Sec-Fetch-Site: same-origin`**, clears `pf_session` (`Max-Age=0`) and
  renders the login page instead of redirecting. The session really ends — on the one device
  where the user asked for it — and a link on another site cannot log anyone out (logout
  CSRF: `Sec-Fetch-Site` is `cross-site` there; a browser that sends no such header keeps
  today's redirect). Cost: ~15 lines in `middleware.ts`, seven API tests. Amends SPEC-auth
  (v1.0.6, §2.7–2.8, §7) and ADR-0006 (dated amendment).
- **(b) Accept the spec's limit and amend the story:** US-03 AC2 becomes "the failure is
  logged and the user stays logged in". Rejected by the agent: a user on a shared computer
  believes they logged out.
- **(c) Stay and say so:** a failed logout shows an error on the page ("Couldn't log out. Try
  again" — a new copy row) and keeps the session. US-03 AC2 changes; if the server is down
  the user cannot leave.
- **(d) If (a): TD-1 in the same change?** `tech-debt.md` says TD-1 (the CSP nonce reaches
  Next through an undocumented header copy) is picked up by "the first task that changes
  `middleware.ts`". With (a), that is T-07. Recommended: **yes** — three lines (set the CSP on
  the forwarded request headers as Next's own guide does, correct the comment), guarded by the
  existing nonce tests, TD-1 marked Closed in T-07's PR. TD-2 (the `proxy` rename) stays its
  own follow-up. Say "no" to keep T-07's middleware change to the logout fallback only.

```ts
/**
 * SPEC-auth §2.7 (v1.0.6), US-03 AC2: logout always completes. `POST /api/auth/logout` clears
 * the session cookie. If it fails — no answer within LOGOUT_TIMEOUT_MS, or a non-2xx answer —
 * the failure is logged and the caller goes to AFTER_FAILED_LOGOUT instead: a same-origin
 * navigation the middleware answers by clearing the cookie itself (§2.8). The cookie is
 * httpOnly, so no script can (T-07 plan Q1).
 */
export const AFTER_LOGOUT = "/login";
export const AFTER_FAILED_LOGOUT = "/login?reason=logout";
export const LOGOUT_TIMEOUT_MS = 10_000;

/** Returns the path to navigate to. Never throws. */
export async function logOut(
  fetcher: typeof fetch = fetch,
  log: (...data: unknown[]) => void = console.error,
): Promise<string> {
  try {
    const response = await fetcher("/api/auth/logout", {
      method: "POST",
      signal: AbortSignal.timeout(LOGOUT_TIMEOUT_MS),
    });
    if (response.ok) return AFTER_LOGOUT;
    log(
      `[logout] POST /api/auth/logout answered ${response.status}; completing the logout client-side`,
    );
  } catch (error) {
    log("[logout] POST /api/auth/logout failed; completing the logout client-side", error);
  }
  return AFTER_FAILED_LOGOUT;
}
```

/**
 * US-35: the sidebar's minimised state for this browser tab. `sessionStorage["pf.sidebar"]` is
 * "collapsed" while minimised and absent otherwise (SPEC-app-shell §2.3); the sidebar reads it
 * through `useSyncExternalStore`, so a write re-renders every subscriber. Storage that throws
 * (a privacy mode, a full or disabled store) must not break the toggle: from the first failure
 * on, the state lives in memory for the rest of the page.
 */
export const SIDEBAR_STORAGE_KEY = "pf.sidebar";

const listeners = new Set<() => void>();
let storageUsable = true;
let memory = false;

export function readSidebarCollapsed(): boolean {
  if (!storageUsable) return memory;
  try {
    return window.sessionStorage.getItem(SIDEBAR_STORAGE_KEY) === "collapsed";
  } catch {
    storageUsable = false;
    return memory;
  }
}

export function writeSidebarCollapsed(collapsed: boolean): void {
  memory = collapsed;
  if (storageUsable) {
    try {
      if (collapsed) window.sessionStorage.setItem(SIDEBAR_STORAGE_KEY, "collapsed");
      else window.sessionStorage.removeItem(SIDEBAR_STORAGE_KEY);
    } catch {
      storageUsable = false;
    }
  }
  for (const listener of listeners) listener();
}

export function subscribeSidebar(listener: () => void): () => void {
  listeners.add(listener);
  return () => {
    listeners.delete(listener);
  };
}

const NONCE = /'nonce-([^']+)'/;

`src/ui/session-recheck.ts`:

```ts
import { SessionResponseSchema } from "@/src/shared/schemas";

/**
 * SPEC-auth §2.9, US-03 AC1: a page the browser restores from its back/forward cache sends no
 * request, so the middleware never sees it. The shell asks `GET /api/auth/session` instead.
 * `true` means the session has ended. A failed or unreadable answer keeps the page (plan D9):
 * its next navigation goes through the middleware anyway. Parsing with the shared schema also
 * loads `schemas.ts`, which sets Zod's `jitless` on this client path (TD-5).
 */
export async function sessionHasEnded(fetcher: typeof fetch = fetch): Promise<boolean> {
  try {
    const response = await fetcher("/api/auth/session", { cache: "no-store" });
    const body = SessionResponseSchema.safeParse(await response.json());
    return body.success && !body.data.authenticated;
  } catch {
    return false;
  }
}

/**
 * Listens for `pageshow` on `target`; on a restore (`persisted`) whose session has ended, calls
 * `leave("/login")` — `location.replace` in the app. Returns the unsubscribe.
 */
export function recheckSessionOnRestore(
  target: Window,
  leave: (path: string) => void,
  fetcher?: typeof fetch,
): () => void {
  const onPageshow = (event: PageTransitionEvent) => {
    if (!event.persisted) return;
    void sessionHasEnded(fetcher).then((ended) => {
      if (ended) leave("/login");
    });
  };
  target.addEventListener("pageshow", onPageshow);
  return () => target.removeEventListener("pageshow", onPageshow);
}
```

```ts
/**
 * Presses the key that moves focus to the next control and asserts where focus landed and
 * that it is visibly indicated (NFR-A2). WebKit, like Safari with "Press Tab to highlight
 * each item" off (its default), reaches only text fields with Tab and skips buttons and
 * links; Option+Tab reaches every control, and Playwright names that key "Alt" — measured in
 * T-06 (plan Task 7, Step 3).
 */
export async function tabTo(page: Page, target: Locator): Promise<void> {
  const engine = page.context().browser()?.browserType().name();
  await page.keyboard.press(engine === "webkit" ? "Alt+Tab" : "Tab");
  await expect(target).toBeFocused();
  await expect(target).toHaveCSS("outline-style", "solid");
}
```
