`proxy.ts`'s matcher excludes only paths with a file extension; `_global-error` has none, so the
proxy runs on it exactly as on any other page — same nonce mint, same security headers, same
`X-Request-Id`. **This contradicts TD-3's current text**, "Guarded meanwhile by: nothing automatic;
it is not reachable by a normal request" — it is a plain `GET`, no session, no crash needed. Task 2,
Step 1 corrects it.

**F2 — no application-level fix exists in Next 16.3.5; the cause is unconditional, in Next's own
build code, not in this app's.** `/_global-error` is `UNDERSCORE_GLOBAL_ERROR_ROUTE`
(`node_modules/next/dist/shared/lib/entry-constants.js:33`, `'/_global-error'`), and
`isPageStatic()` special-cases exactly that route id to always return `isStatic: true`
(`node_modules/next/dist/build/utils.js:595-609`) — before it looks at `export const dynamic`,
`connection()`, or anything else in the tree. The same file also drops the route from the build's
printed table ("Hide static /_global-error from build output",
`node_modules/next/dist/build/utils.js:288-294`) and `next/dist/export/index.js:723-725` skips it
during a static export ("Skip 500.html in static export") — three independent places in Next's own
source treating this route as a fixed, build-time artifact, never a per-request render. This matches
what T-06 finding F1 already found and left as a known limitation (process log, 2026-09-23: "A trial
build with `connection()` in the root layout, reverted afterwards, still listed `/_global-error` as
prerendered"); this plan traces *why* to the exact lines.

**F3 — a custom `app/global-error.tsx` is not even used for this artifact, so it cannot be the fix
either.** Measured: added a throwaway `app/global-error.tsx`:

```tsx
"use client";
export const dynamic = "force-dynamic";

export default function GlobalError() {
  return (
    <html>
      <body>
        <p>scratch probe — should not ship</p>
      </body>
    </html>
  );
}
```

`rm -rf .next && npx next build` (clean rebuild). `.next/server/app/_global-error.meta` still reads
`"x-nextjs-prerender": "1"`; `.next/server/app/_global-error.html`'s `<title>` is still `500: This
page couldn't load` and its body is still Next's own bundled `DefaultGlobalError`
(`node_modules/next/dist/client/components/builtin/global-error.js`) byte for byte — `grep -o
"scratch probe" .next/server/app/_global-error.html` matches nothing. The custom file *is* compiled
(`.next/server/chunks/ssr/app_global-error_tsx_*.js` exists and the client bundle references it —
used for a client-side error *after* a page has already hydrated, per Next's own `error.md`: "This
file replaces the root layout … when active"), but Next's synthetic build-time `/_global-error`
route always renders its own bundled default, regardless. So there is no lever here at all, not a
partial one: TD-3's own text already anticipated a *style-attribute* partial fix ("a `global-error.tsx`
without `style` attributes still leaves the prerendered inline scripts") — the real answer is
narrower than that: a custom file is not rendered into this specific artifact in the first place.

**F4 — the exact shape of what ships**, from `.next/server/app/_global-error.html` (unmodified tree,
before F3's probe): one `<style>` with no attributes at all
(`dangerouslySetInnerHTML`, the `--next-error-*` custom properties and the dark-mode media query);
seven elements (`div`, `h1`, `p`, `form`, `button`, `svg`, `path` — counted from the source above)
each carrying a `style="…"` attribute; three inline `<script>` tags, also bare (`(self.__next_f=
self.__next_f||[]).push(...)` and the RSC payload push) — none of the four inline tags (one
`<style>`, three `<script>`) carries a `nonce` attribute of any kind, matched or not; alongside them,
external `<script src="/_next/static/chunks/….js">` tags, which `'self'` in `script-src` still
allows (a `src`-based script needs no nonce). Under this app's production policy (`style-src 'self'
'nonce-…'`, no `'unsafe-inline'`/`'unsafe-hashes'`), a real browser drops the `<style>` element (its
custom properties fall back to initial values), drops every `style="…"` attribute (`style-src-attr`
falls back to `style-src` when unset, per CSP3, and a nonce does not cover attributes — the same rule
`tests/api/proxy.spec.ts`'s `expectNotFoundUnderCsp` already asserts for `/_not-found`), and drops the
inline hydration scripts (no RSC payload reaches the already-loaded external bundle, so the page
never hydrates) while still loading the external chunks themselves. Net effect: the "Reload" button
(inside a bare `<form>`, no JS needed for a plain submit) still works; the default UI's "Back" button
(an `onClick` handler, needs hydration) would not, on the branch that shows it. `grep -rn
"_global-error" tests/ src/ app/ docs/02-architecture/` — zero hits: nothing today asserts any of this,
either the mismatch or the outcome.

```ts
// TD-3 (tech-debt.md), investigated at T-13b (2026-09-25): `/_global-error` is Next 16.3.5's own
// synthetic 500-equivalent fallback (UNDERSCORE_GLOBAL_ERROR_ROUTE,
// next/dist/shared/lib/entry-constants.js), forced static unconditionally by `isPageStatic`
// (next/dist/build/utils.js) regardless of `connection()` or `export const dynamic =
// "force-dynamic"`, and always rendered from Next's own bundled DefaultGlobalError — measured: a
// scratch app/global-error.tsx with force-dynamic still produced the stock body. No
// application-level fix exists in this Next version, so this pins the gap's exact shape rather than
// closing it: if a future Next release changes any of this, the assertions below fail first.
test("TD-3: /_global-error is reachable directly; its own CSP carries a nonce but its inline tags never do", async ({
  request,
}) => {
  const first = await request.get("/_global-error");
  expect(first.status()).toBe(500);
  const firstNonce = scriptSrcNonce(first);
  expect(firstNonce, "the response's own CSP still carries a nonce").toBeTruthy();
  expect(first.headers()["referrer-policy"]).toBe("strict-origin-when-cross-origin");

  const second = await request.get("/_global-error");
  const secondNonce = scriptSrcNonce(second);
  // The proxy runs on this path like any other — it has no file extension, so the matcher does
  // not exclude it — and mints a fresh nonce every time; only the prerendered body stays fixed.
  expect(secondNonce, "a fresh nonce on a second request").toBeTruthy();
  expect(secondNonce).not.toBe(firstNonce);

  for (const [label, response, nonce] of [
    ["first", first, firstNonce],
    ["second", second, secondNonce],
  ] as const) {
    const html = await response.text();
    const tags = inlineTags(html);
    // Next's bundled fallback UI always inlines its RSC payload push and one <style>; none at all
    // would mean this matched nothing, not that the page is fixed.
    expect(tags.length, `${label}: at least one inline tag`).toBeGreaterThan(0);
    expect(
      tags.filter((tag) => tag.includes(`nonce="${nonce}"`)),
      `${label}: none of the inline tags carry this response's nonce`,
    ).toEqual([]);
    // Next's own fallback UI still uses style="…" attributes too; style-src-attr falls back to
    // style-src, which has no 'unsafe-inline'/'unsafe-hashes' in this policy — no nonce ever
    // covers an attribute, so a browser drops every one of these regardless.
    expect(
      (html.match(/\sstyle="[^"]*"/g) ?? []).length,
      `${label}: style attributes present (none of which any nonce could allow)`,
    ).toBeGreaterThan(0);
  }
});
```
