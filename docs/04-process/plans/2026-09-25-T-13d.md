## Review Focus

The inputs and conditions T-13d's scope implies but this session's own tooling or the standard
test suites do not already exercise, most likely to bite the execution session first.

1. **The four backlog-specific items (NFR-S5 rerun, the GitHub-side settings, TD-10's stock
   Prisma commands, dependency review) do not map onto a checklist ID one-to-one.** If the
   execution session only walks the 131 fixed items mechanically, these can slip through
   uncounted, or get force-fit into a checklist item that does not really cover them (e.g. TD-10's
   `prisma migrate reset`/`db push --force-reset` gap is closer to CONF/DOS than any single VAL
   item). Task 3 gives them their own report subsection, outside the 131-item table but
   cross-referenced from it, so the report template's own self-check ("the full-checklist table
   has exactly one row per item in scope, 131 for a full run") still balances.
2. **This session's GitHub tooling cannot read repository Settings at all** — confirmed, not
   assumed (Finding F7). The main branch ruleset's exact rules, secret scanning's non-provider-
   pattern/validity-check toggles, private vulnerability reporting's on/off state, and what a
   fork's pull request can run are all facts the backlog row already asserts as if measured, but
   no tool in this session's `mcp__github__*` list (checked against the deferred-tool listing) or
   direct API access (explicitly unavailable per this session's own instructions) can confirm or
   refute them. Silently reusing the backlog row's claims would violate "evidence for every status,
   copied from the run." Q3 asks the owner how to close this gap.
3. **`npm run test:api` / `test:e2e` always force `APP_ENV=test`**
   (`playwright.config.ts:79-88`'s `webServer.env`), so neither existing suite is evidence for
   CONF-01/AUTHZ-02 in the one configuration that actually matters for a deploy: a build with
   `APP_ENV` **not** `test`. Only a separate, manual production server proves `/api/test/*`
   answers 404 there — this plan's own scratch verification did exactly that (Finding F1) and the
   execution session needs the same kind of standalone server (not the Playwright-managed one)
   running for CONF-01/AUTHZ-02 and any other item that depends on the non-test build.
4. **No deployed host exists yet.** Every TRAN item about TLS, HSTS, or cipher suites, and every
   Vercel-specific behaviour (its own default headers, the "System Environment Variables" setting
   TD-10 depends on) is **NOT TESTED by definition** this time, not a gap in this session's
   effort. The report needs to say so plainly — reading ADR-0007's stated intentions as if they
   were measured facts would be exactly the kind of unverified claim governance treats as a defect
   — and T-14's own backlog row should gain a hand-off to re-verify the TRAN category once
   deployed, the same way T-13a's `proxy.ts` hand-off already asks T-14 to check headers on the
   first preview.
5. **The disclosure ground rule names a tool this session does not have.** "An exploitable finding
   is recorded in a private GitHub security advisory draft" (backlog row's Disclosure line,
   matching the skill's own rule) assumes a way to create one; no `mcp__github__*` tool in this
   session's list does that, and this session has no direct GitHub API access at all. If a
   Critical or High finding turns up mid-review, the execution session must not route around the
   ground rule (e.g. by writing exploit detail into the public process log or a public PR) just
   because the intended channel is unavailable. Q5 asks the owner for the fallback before the
   execution session could be caught mid-review needing one.
6. **A subagent's "PASS" is a candidate, never a verdict.** The skill is explicit: subagents "run
   without write tools… cannot run tests or send requests, so what they return is a candidate
   status with its static evidence. The main session owns the running server, runs every cited
   test and every dynamic check, and only then marks an item PASS." Task 2 restates this as a
   hard rule for the dispatch, since a fast-moving session under this task's size could be tempted
   to accept a subagent's citation as already-proven.
7. **Severity is calibrated to this app, not to a generic checklist.** "This is a demo with one
   shared account and no real personal data (NFR-S1). The same bug matters differently here than
   in a production bank" (skill, step 4). A subagent unfamiliar with that framing (or with NFR-S1
   itself) could over- or under-rate a finding; Task 4 has the main session re-weigh every
   subagent-proposed severity against NFR-S1/S4 before it goes in the report, not accept it as
   handed over.

## Findings — measured 2026-09-25, `origin/main` `aad1423`, Next 16.3.5

**F1 — `/api/test/*` correctly answers 404 outside the test environment; the standard test suites
never prove this.** Manual production build (`APP_ENV="production"`, no `.env.local` value of
`test` anywhere), `npm run build && npm run start -p 3900`:

```
$ curl -sS -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3900/api/test/reset

```

Matches `src/shared/env.ts`'s `isTestEnv` (exact match on `"test"`, read at TD-10) and the skill's

checklist PASS; the Playwright-managed servers (`APP_ENV=test` always) cannot provide it.

**F2 — `POST /api/admin/reset` refuses both no secret and a wrong one, identically (401, not a
distinguishing code).**

```
$ curl -sS -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3900/api/admin/reset
401
$ curl -sS -o /dev/null -w "%{http_code}\n" -X POST -H "Authorization: Bearer wrong" http://localhost:3900/api/admin/reset

```

No oracle distinguishes "no header" from "wrong secret" — good evidence toward AUTHZ-02/CONF-01's
PASS, to be paired with the existing test the execution session cites by name (not found in this

**F3 — Unauthenticated `GET /overview` redirects (302), never serves the page.** Matches SPEC-auth

**F4 — Response headers match ADR-0006's decision on every branch probed, with one gap not

`poweredByHeader: false` (grepped: no match anywhere in `next.config.ts` or `src/`), so this is
