  and, where it concerns Release 2, as a hand-off to T-15d (Q4).
- It does not edit an older process-log entry: the log is append-only (`governance.md`, "Process log").
  This is why the 25 empty "Owner changes" fields need an answer of a different shape (Q2).

**Q1 — Where does the retrospective live?**
*What:* T-15's row says "the entry". Phase 7 separately names `docs/04-process/retrospective.md`.
*Why it matters:* a new document type is a decision (AGENTS.md §2), and a Phase 7 file written now would
be a later phase's artefact.
- (a) **One entry at the bottom of `process-log.md`, titled "Release 1 retrospective" — recommended.** It
  follows the row's wording, needs no new document, and Phase 7's file can later be built from it.
- (b) A separate `docs/04-process/release-1-retrospective.md`. Easier to read on its own; a new document type.
- (c) Both: the entry is short and links to the document.

**Q2 — How are the 25 empty "Owner changes" fields answered?**
*What:* you said they wait for the general retrospective. The log is append-only, so the agent cannot
write into those entries; the answers go in the retro entry as a table, one row per old entry (its date,
title, log line, and your answer).
*Why it matters:* 25 questions asked cold is a long session; many of those entries were "awaiting review" and
the pull request later merged, so the later entries often already show what you changed.
- (a) **The agent pre-fills each row from what the later log entries record, shows you the table, and you
  correct or add — recommended.** Rows you do not remember are marked "not recalled" rather than guessed.
- (b) You answer all 25 cold in one session; the agent writes your words as given.
- (c) They stay empty, and the retro states that, with the count.

**Q3 — Which rule changes does the retro propose, and who applies them?**
*What:* F4's five candidates (plan Status closes with the PR; backlog done-marker with the PR; the three-engine
result in the reviewer's checklist; `gh pr view` before a push; the owner-question shape), plus whatever Task R1
finds that F4 missed. The first two touch `definition-of-done.md`, the next `build-workflow.md` or the PR
template, the last two AGENTS.md or `governance.md`; all four are Approved documents only you change.
*Why it matters:* a lesson that is only written in the log was already written ten times (F3.1, F3.2).
- (a) **The retro lists each candidate with its evidence; you tick the ones you accept; each accepted one is a
  small pull request to `develop` of its own (`docs(dod): …`) — recommended,** the T-15a/T-15b precedent.
- (b) The agent applies all five in one pull request for you to review.
- (c) Proposals only; no rule document is edited in T-15c.

**Q4 — What do the "specs missed" lessons do for Release 2?**
*What:* the log's spec-side lessons — a prototype omits non-visual requirements, seed-derived figures typed
instead of computed, "check the artefact of every NFR the Goal cites" (NFR-D4) — are about how specs are written.
*Why it matters:* T-15d opens Release 2's spec work next, and you decide its depth then.
- (a) **The retro names them, and a "from T-15c" hand-off is appended to T-15d's backlog row so Release 2's
  specs start from them — recommended.**
- (b) Only named in the retro; T-15d's planning finds them itself.

**Q5 — Does T-15c wait for the first release after T-15b?**
*What:* F5's observations (the check's green on a real release pull request, `develop`'s survival, the merge
method) cannot be read before a release.
*Why it matters:* a retro written now is complete for what happened; written after the release it is complete
for T-15b's mechanism too.
- (a) **Run T-15c now; the retro has a "not yet observed" list with the three items, and the first release's
  process-log entry reads them — recommended.** T-15d is not delayed.
- (b) Wait for the first release, then write the retro.

**Q6 — The 10 audit findings (F6): what happens, and in what order?**
*What:* the critical one in `next` has a plain fix; the nine in dev tooling need an assessment (a commented
`overrides` entry each, or a tool upgrade, or a removal task), as the earlier audit rounds did.
*Why it matters:* a critical advisory on a public repository's production framework is not a retro item, and
the retro's own Review Focus would be read next to a red audit.
- (a) **A separate small pull request to `develop` before T-15c's work starts, for the `next` fix only
  (`npm audit fix` limited to `next`, the full `npm run test:all` result in the description) — recommended —
  and a second one for the nine, each with its reason and a removal task, after you read the assessment.**
  This is the "outside-task defects are fixed in their own pull request first" route you chose before.
- (b) Both in one pull request.
- (c) Not now; T-15c's retro lists it as "found, not fixed" and the next task takes it.
