**Goal:** The Auth API for Release 1 — `POST /api/auth/login`, `POST /api/auth/signup`,
`POST /api/auth/logout`, `GET /api/auth/session`, the `middleware.ts` route matrix, the
iron-session cookie with its sliding re-issue and reset-epoch check, the failed-login rate
limit, and the security headers ADR-0006 names — so T-06 has a real backend to build the auth
UI against and T-07 onward have a session boundary to sit behind.

**Architecture:** `src/server/session.ts` wraps `iron-session`'s stateless seal/unseal around
the `{ sub, iat, resetEpoch }` payload; `src/server/rate-limit.ts` separates the failed-login
window math (a pure function, unit-tested) from the `LoginAttempt` read/write (API-tested);
`src/server/auth.ts` is the one place that knows the login/signup/logout/session behaviour,
called by four thin `app/api/auth/*/route.ts` handlers (ADR-0002: routes parse → call
`src/server` → respond). `middleware.ts` at the repo root is the single place that reads the
wall clock for request-time concerns (ADR-0005 does not reach it — the rule is scoped to
`src/domain` and `src/server`): it builds the route matrix decision, the `X-Request-Id` and
security headers, the sliding cookie re-issue, and the reset-epoch check, passing `now` into
`src/server` functions rather than letting them read it. `src/shared/next-path.ts` is new: the
`next` allow-list regex (SPEC-auth §2.4) is shared between the middleware's redirect and
T-06's client-side navigation, so it is written once, in `src/shared`, not duplicated.

### Q1 — bcrypt package

**Resolved 2026-09-23: `bcryptjs`**, as recommended below.

ADR-0006 says "bcrypt" without naming a package. Two real options:
- **`bcryptjs`** (recommended) — pure JS, no native compile step, works the same in the
  Node.js runtime this route needs (see Q2) and in CI without an `allowScripts` entry.
  Slightly slower per hash than the native binding; irrelevant at one demo account's traffic.
- **`bcrypt`** — native binding (the package `node-gyp`-compiles against libc), needs an
  `allowScripts` entry (`package.json`'s existing block, T-02a precedent) and a matching
  prebuilt binary on Vercel's build image.

Recommendation: `bcryptjs`. This plan uses it unless you say otherwise.

### Q2 — middleware runtime and the reset-epoch check

**Resolved 2026-09-23: option (a)**, as recommended below.

SPEC-auth §2.9 requires the middleware to reject a session whose `resetEpoch` is older than
the latest `ResetLog.at` — on every authenticated request. That is a database read, and
Next.js middleware defaults to the Edge runtime, where the `pg`/Prisma setup this project uses
(ADR-0005/0007) does not run.

Options:
- **(a) Node.js middleware runtime** (recommended) — `export const config = { runtime:
  "nodejs" }` in `middleware.ts` (stable since Next 15.2, and this project is on 16.3.5), so
  the existing `src/server/db.ts` Prisma client works unchanged. Cost: one extra query per
  authenticated navigation. At R1's traffic (a portfolio demo) this is fine.
- **(b) Same, plus an in-memory cache of the latest `ResetLog.at`** with a short TTL (e.g. 5 s)
  inside the middleware module, to cut the per-request query — adds a staleness window bounded
  by the TTL (a session revoked by a reset could work for up to the TTL after it should not).
- **(c) Move the reset-epoch check out of middleware**, into each protected route/page instead
  (middleware only handles the redirect matrix and headers). Spreads the check across every
  future task that adds a protected route, which the spec's wording ("the middleware…") does
  not suggest.

Recommendation: (a) now, with (b) left as a documented follow-up if the extra query is ever
measured to matter (nothing in NFR-P suggests it will at R1's scale).

### Q3 — CSP nonce hand-off to T-06/T-07

**Resolved 2026-09-23: dropped, as tech debt** (see "Owner answers" above) — kept below for
the record of what was considered.

ADR-0006's header list includes a CSP with "scripts self + inline nonce". Emitting the header
(`middleware.ts`, this task) is separate from consuming the nonce (a `<script nonce=…>`
attribute, or Next's own inline scripts reading it — a UI-layer concern that lands with T-06's
and T-07's pages, since T-05 adds no pages itself, only the middleware and API routes touched
here have no inline `<script>` tags to nonce).

This plan: middleware generates one nonce per request (`crypto.randomUUID()`), sets
`Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-<value>'; frame-ancestors
'none'` (and the other ADR-0006 headers) and forwards the nonce to Server Components via a
request header (`x-nonce`) the Next.js middleware pattern reads back with `headers()` — the
documented way to wire a per-request CSP nonce through App Router. T-05's own DoD does not
require any page to actually consume the nonce (T-05 ships no pages); a hand-off note goes in
this task's PR for T-06/T-07 to read `headers().get("x-nonce")` if/when they add an inline
`<script>` (none of T-06's or T-07's current spec text names one, so this may never be
exercised — the header is still correct to emit regardless).

Confirm this is acceptable, or say to drop the nonce machinery until a task actually needs an
inline script (simpler CSP: no `'nonce-…'`, no `x-nonce` header) — SPEC-auth doesn't itself
require a working nonce today, only ADR-0006's header text does.

### Q5 — Login timing-oracle mitigation (backlog v1.12, Minor)

**Resolved 2026-09-23: apply the mitigation**, as recommended below — no change from v0.1.

The 2026-09-23 review finding: closing the body/status oracle (identical 401 for a malformed
body and a wrong password) doesn't close a *timing* one if schema validation fails cheaply
while the bcrypt compare does not. This plan's Task 6 always runs one `bcrypt.compare` call
before answering 401 — even when `LoginSchema` parsing failed — comparing the raw `password`
field (or `""` if the body has none/isn't an object) against `DEMO_PASSWORD_HASH`, discarding
the result. This flattens the two paths to "one schema parse (or none) + one bcrypt compare"
either way. No test asserts the actual timing difference (flaky in CI); the test asserts that
both a malformed body and a wrong password produce the byte-identical 401 body, and a code
comment records the mitigation and its limit (it does not, and cannot cheaply, prove equal
timing — only removes the obvious "skip the expensive step" shortcut). Confirm this is enough,
or say to leave it for a dedicated task (the finding is filed as Minor, not a blocker).

## Review Focus

1. **The `next` allow-list on the middleware's redirect, not just the client's.** SPEC-auth
   §2.10's test list names `//evil.com`, `/api/x`, `/login` as inputs that must fall back to
   `/overview` — an open redirect here is a real vulnerability, not a cosmetic bug, and it's
   easy to implement the allow-list only on the client (T-06) and forget the middleware needs
   the same check on the way *in* (`?next=`) before it ever reaches the client.
2. **The rate limit's boundary, not just its happy path.** §4's cases (10th failure → 401,
   11th → 429, an entry older than 15 minutes ignored, success resets the counter) are exact
   numbers; an off-by-one here either locks out a legitimate 10th attempt or lets an 11th
   through, and both are wrong in opposite directions.
3. **The cookie's sliding re-issue condition, not just its presence.** §2.9 says "more than 1
   hour of its life has elapsed" — a session at exactly 59 minutes must not re-issue, at 61
   minutes must, and a test that only checks "the cookie is set" on every request would pass
   even if re-issue fired every time (defeating the point) or never (silently expiring early).
4. **`GET /api/auth/session` and the back-navigation re-check it feeds (§2.9).** The route
   itself is simple (`{ authenticated: boolean }`), but its correctness for a *reset* session
   (resetEpoch stale) and an *expired* session are both "false" from the same code path the
   resetEpoch check in Task 4 uses — a test that only logs in and checks `true` misses both.
5. **The signup 400 body vs. the login 401 body use different shapes on purpose** (§2.10, the
   two-tier `ErrorEnvelope`) — a shared `errorResponse` helper that always requires a `message`
   (the current `src/server/http.ts` signature) will make it easy to accidentally send a
   `message` on a signup 400 (spec says none) or omit one on a login 401 (spec requires one);
   Task 2 redesigns the helper so each shape is a distinct, correctly-typed call, not a
   parameter that can be gotten wrong silently.

```typescript
// src/server/http.ts
import type { ErrorEnvelope, ErrorIssue } from "@/src/shared/schemas";

export type ApiErrorCode = ErrorEnvelope["error"];

/** Every code with a fixed banner/notice message (401, 404, 409, 429's message half, 500). */
export function errorResponse(status: number, error: ApiErrorCode, message: string): Response {
  const body: ErrorEnvelope = { error, message };
  return Response.json(body, { status });
}

/** SPEC-auth §2.10: a 400 carries `issues`, never `message` — no Zod default strings. */
export function validationErrorResponse(issues: ErrorIssue[]): Response {
  const body: ErrorEnvelope = { error: "validation", issues };
  return Response.json(body, { status: 400 });
}

/** SPEC-auth §4: `Retry-After` header (seconds) alongside the body's `retryAfter`. */
export function rateLimitedResponse(message: string, retryAfter: number): Response {
  const body: ErrorEnvelope = { error: "rate_limited", message, retryAfter };
  return Response.json(body, { status: 429, headers: { "Retry-After": String(retryAfter) } });
}
```

```typescript
// src/shared/next-path.ts
/**
 * SPEC-auth §2.4, §2.10: the only paths a post-login redirect or a middleware `?next=` may
 * send the browser to. Anything else — an open-redirect attempt, an API path, the auth pages
 * themselves, a fragment — falls back to /overview. One function, shared between the

const ALLOWED_NEXT = /^\/(overview|transactions|budgets|pots|recurring-bills)(\?[^#]*)?$/;

export function sanitizeNextPath(next: string | null): string {

}
```

## Task 4: `src/server/session.ts` — iron-session, sliding re-issue, reset-epoch

**Files:**
- Create: `src/server/session.ts`
- Modify: `src/server/reset.ts` (add `latestResetAt`, per Q4)
- Test: `tests/unit/server/session.test.ts`

**Interfaces:**
- Consumes: `iron-session`'s `sealData`/`unsealData`; `SESSION_SECRET` from `process.env`
  (read once, at the call site, matching `src/server/env.ts`'s existing pattern — not
  captured at import).
- Produces:
  - `type SessionPayload = { sub: "demo"; iat: number; resetEpoch: number }`
  - `SESSION_COOKIE_NAME = "pf_session"`
  - `SESSION_TTL_SECONDS = 7 * 24 * 60 * 60`
  - `SESSION_REISSUE_AFTER_SECONDS = 60 * 60`
  - `sealSession(payload: SessionPayload): Promise<string>` — the sealed cookie value.
  - `readSession(cookieValue: string | undefined): Promise<SessionPayload | null>` — `null` on
    a missing cookie or a seal that fails to unseal (tampered/expired secret rotation).
  - `shouldReissue(session: SessionPayload, now: Date): boolean` — pure, `now.getTime() -
    session.iat > SESSION_REISSUE_AFTER_SECONDS * 1000`.
  - `isSessionValid(session: SessionPayload, now: Date, latestReset: Date | null): boolean`
    — pure: age within `SESSION_TTL_SECONDS`, and (`latestReset === null` or
    `session.resetEpoch >= latestReset.getTime()`).
  - `sessionCookieHeader(sealed: string, maxAgeSeconds: number): string` — the `Set-Cookie`
    value (httpOnly, SameSite=Lax, Path=/, Secure outside development).

```typescript
// src/server/session.ts
import { sealData, unsealData } from "iron-session";

export type SessionPayload = { sub: "demo"; iat: number; resetEpoch: number };

export const SESSION_COOKIE_NAME = "pf_session";
export const SESSION_TTL_SECONDS = 7 * 24 * 60 * 60;
export const SESSION_REISSUE_AFTER_SECONDS = 60 * 60;

function sessionSecret(): string {
  const secret = process.env.SESSION_SECRET;
  if (!secret || secret.length < 32) {
    throw new Error("SESSION_SECRET is not set or shorter than 32 chars (.env.example)");
  }
  return secret;
}

/**
 * `resetEpoch` is stamped at login time from the *current* latest reset, not from `now` —
 * a session logged in after the last reset starts valid; the epoch only ever needs to move
 * forward past a *later* reset (isSessionValid below), never past its own creation.
 */
export async function sealSession(payload: SessionPayload): Promise<string> {
  return sealData(payload, { password: sessionSecret(), ttl: SESSION_TTL_SECONDS });
}

export async function readSession(cookieValue: string | undefined): Promise<SessionPayload | null> {
  if (!cookieValue) return null;
  try {
    const data = await unsealData<SessionPayload>(cookieValue, { password: sessionSecret() });
    return data.sub === "demo" ? data : null;
  } catch {
    return null;
  }
}

export function shouldReissue(session: SessionPayload, now: Date): boolean {
  return now.getTime() - session.iat > SESSION_REISSUE_AFTER_SECONDS * 1000;
}

export function isSessionValid(
  session: SessionPayload,
  now: Date,
  latestReset: Date | null,
): boolean {
  const age = now.getTime() - session.iat;
  if (age < 0 || age > SESSION_TTL_SECONDS * 1000) return false;
  if (latestReset !== null && session.resetEpoch < latestReset.getTime()) return false;
  return true;
}

export function sessionCookieHeader(sealed: string, maxAgeSeconds: number): string {
  const secure = process.env.NODE_ENV === "production" ? "; Secure" : "";
  return `${SESSION_COOKIE_NAME}=${sealed}; HttpOnly; SameSite=Lax; Path=/; Max-Age=${maxAgeSeconds}${secure}`;
}
```

```typescript
// src/server/rate-limit.ts
import type { Db } from "./db";

export const RATE_LIMIT_WINDOW_MS = 15 * 60 * 1000;
export const RATE_LIMIT_MAX_FAILURES = 10;

/**
 * SPEC-auth §4: 10 failed logins / 15 min / IP → 429; a success clears the IP's counter (so
 * `recordAttempt(..., success: true, ...)` also deletes the window's failures — Step 3's
 * `recordAttempt` below — rather than this function seeing a mix of old failures and a
 * success and needing to reason about ordering).
 */
export function evaluateAttempts(
  failuresInWindow: number,
  now: Date,
  oldestFailureAt: Date | null,
): { limited: boolean; retryAfter: number } {
  if (failuresInWindow <= RATE_LIMIT_MAX_FAILURES || oldestFailureAt === null) {
    return { limited: false, retryAfter: 0 };
  }
  const clearsAt = oldestFailureAt.getTime() + RATE_LIMIT_WINDOW_MS;
  const retryAfter = Math.max(1, Math.ceil((clearsAt - now.getTime()) / 1000));
  return { limited: true, retryAfter };
}

export async function checkRateLimit(
  db: Db,
  ip: string,
  now: Date,
): Promise<{ limited: boolean; retryAfter: number }> {
  const windowStart = new Date(now.getTime() - RATE_LIMIT_WINDOW_MS);
  const failures = await db.loginAttempt.findMany({
    where: { ip, success: false, at: { gte: windowStart } },
    orderBy: { at: "asc" },
    select: { at: true },
  });
  return evaluateAttempts(failures.length, now, failures[0]?.at ?? null);
}

export async function recordAttempt(
  db: Db,
  ip: string,
  success: boolean,
  now: Date,
): Promise<void> {
  await db.loginAttempt.create({ data: { ip, success, at: now } });
  // "a successful login clears the IP's counter" (SPEC-auth §4) — delete the prior failures
  // so the very next failed attempt starts a fresh window, not one still holding old ones.
  if (success) {
    await db.loginAttempt.deleteMany({ where: { ip, success: false } });
  }
}
```

```typescript
// src/server/auth.ts
import * as bcrypt from "bcryptjs";
import { COPY } from "@/src/shared/copy";
import { LoginSchema, SignupSchema, toErrorIssues } from "@/src/shared/schemas";
import { getDb } from "./db";
import { errorResponse, rateLimitedResponse, validationErrorResponse } from "./http";
import { checkRateLimit, recordAttempt } from "./rate-limit";
import { latestResetAt } from "./reset";
import {
  SESSION_COOKIE_NAME,
  SESSION_TTL_SECONDS,
  isSessionValid,
  readSession,
  sealSession,
  sessionCookieHeader,
} from "./session";

function clientIp(request: Request): string {
  // Vercel and most proxies set this; a direct connection (local dev) has none, so fall
  // back to a constant — the rate limit still works per-process in that case.
  return request.headers.get("x-forwarded-for")?.split(",")[0]?.trim() ?? "local";
}

export async function login(request: Request, now: Date): Promise<Response> {
  const db = getDb();
  const ip = clientIp(request);
  const rate = await checkRateLimit(db, ip, now);
  if (rate.limited) {
    return rateLimitedResponse(COPY.loginRateLimited(Math.max(1, Math.ceil(rate.retryAfter / 60))), rate.retryAfter);
  }

  const rawBody: unknown = await request.json().catch(() => null);
  const parsed = LoginSchema.safeParse(rawBody);

  // SPEC-auth v1.0.3, Q5: run the bcrypt compare on the *submitted* password even when the
  // schema rejected the body, so a malformed body costs the same as a wrong password — the
  // schema-fail path has no expensive step of its own to skip otherwise.
  const passwordToCompare =
    typeof (rawBody as { password?: unknown })?.password === "string"
      ? (rawBody as { password: string }).password
      : "";
  const passwordMatches = await bcrypt.compare(passwordToCompare, process.env.DEMO_PASSWORD_HASH ?? "");
  const emailMatches = parsed.success && parsed.data.email === process.env.DEMO_EMAIL;

  if (!parsed.success || !emailMatches || !passwordMatches) {
    await recordAttempt(db, ip, false, now);
    return errorResponse(401, "invalid_credentials", COPY.loginIncorrect);
  }

  await recordAttempt(db, ip, true, now);
  const resetAt = await latestResetAt(db);
  const sealed = await sealSession({ sub: "demo", iat: now.getTime(), resetEpoch: (resetAt ?? now).getTime() });
  const response = Response.json({ ok: true });
  response.headers.append("Set-Cookie", sessionCookieHeader(sealed, SESSION_TTL_SECONDS));
  return response;
}

export async function signup(request: Request): Promise<Response> {
  const rawBody: unknown = await request.json().catch(() => null);
  const parsed = SignupSchema.safeParse(rawBody);
  if (!parsed.success) {
    return validationErrorResponse(toErrorIssues(parsed.error));
  }
  return Response.json({ code: "demo_instance" });
}

export async function logout(): Promise<Response> {
  const response = new Response(null, { status: 204 });
  response.headers.append("Set-Cookie", `${SESSION_COOKIE_NAME}=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0`);
  return response;
}

export async function session(request: Request, now: Date): Promise<Response> {
  const cookie = request.headers
    .get("cookie")
    ?.split("; ")
    .find((c) => c.startsWith(`${SESSION_COOKIE_NAME}=`))
    ?.slice(SESSION_COOKIE_NAME.length + 1);
  const payload = await readSession(cookie);
  if (!payload) return Response.json({ authenticated: false });
  const resetAt = await latestResetAt(getDb());
  const authenticated = isSessionValid(payload, now, resetAt);
  return Response.json({ authenticated });
}
```

```typescript
// middleware.ts
import { NextResponse, type NextRequest } from "next/server";
import { getDb } from "@/src/server/db";
import { latestResetAt } from "@/src/server/reset";
import {
  SESSION_COOKIE_NAME,
  SESSION_TTL_SECONDS,
  isSessionValid,
  readSession,
  sealSession,
  sessionCookieHeader,
  shouldReissue,
} from "@/src/server/session";
import { sanitizeNextPath } from "@/src/shared/next-path";

// SPEC-auth §2.9: Node.js runtime, not the Edge default — the reset-epoch check needs the
// same Prisma/pg client src/server/db.ts uses elsewhere (plan gate Q2).
export const config = {
  runtime: "nodejs",
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};

const PROTECTED = /^\/(overview|transactions|budgets|pots|recurring-bills)(\/|$)/;
const AUTH_PAGES = /^\/(login|signup)$/;
const PUBLIC_API = /^\/api\/(auth\/(login|signup|session)|meta)$/;
const TEST_API = /^\/api\/test\//;
const ADMIN_API = /^\/api\/admin\//;

export async function middleware(request: NextRequest): Promise<NextResponse> {
  const now = new Date();
  const { pathname, search } = request.nextUrl;
  const requestId = crypto.randomUUID();

  const isApi = pathname.startsWith("/api/");
  const isRoot = pathname === "/";
  const needsSession = isApi
    ? !PUBLIC_API.test(pathname) &&
      !TEST_API.test(pathname) &&
      !ADMIN_API.test(pathname) &&
      pathname !== "/api/auth/logout"
    : isRoot || PROTECTED.test(pathname);

  const cookie = request.cookies.get(SESSION_COOKIE_NAME)?.value;
  const payload = await readSession(cookie);
  const resetAt = payload ? await latestResetAt(getDb()) : null;
  const authenticated = payload !== null && isSessionValid(payload, now, resetAt);

  let response: NextResponse;

  if (isRoot) {
    response = NextResponse.redirect(new URL(authenticated ? "/overview" : "/login", request.url));
  } else if (needsSession && !authenticated) {
    if (isApi) {
      response = NextResponse.json(
        { error: "unauthenticated", message: "Log in to continue" },
        { status: 401 },
      );
    } else {
      const next = sanitizeNextPath(`${pathname}${search}`);
      response = NextResponse.redirect(new URL(`/login?next=${encodeURIComponent(next)}`, request.url));
    }
  } else if (!isApi && AUTH_PAGES.test(pathname) && authenticated) {
    response = NextResponse.redirect(new URL("/overview", request.url));
  } else {
    response = NextResponse.next();
  }

  if (authenticated && payload && shouldReissue(payload, now)) {
    const resealed = await sealSession({ sub: "demo", iat: now.getTime(), resetEpoch: payload.resetEpoch });
    response.headers.append("Set-Cookie", sessionCookieHeader(resealed, SESSION_TTL_SECONDS));
  }

  response.headers.set("X-Request-Id", requestId);
  if (!isApi && authenticated) {
    response.headers.set("Cache-Control", "no-store");
  }
  response.headers.set(
    // ADR-0006, 2026-09-23 amendment: no inline nonce — R1 has no inline <script>.
    "Content-Security-Policy",
    "default-src 'self'; script-src 'self'; frame-ancestors 'none'",
  );
  response.headers.set("Referrer-Policy", "strict-origin-when-cross-origin");
  response.headers.set("X-Content-Type-Options", "nosniff");

  return response;
}
```
