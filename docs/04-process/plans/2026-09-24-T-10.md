## Architecture

**Data flow.** `app/(app)/overview/page.tsx` is an async server component. It calls
`getOverview(getDb(), fixedClock(BUSINESS_TODAY))` directly — the same call
`app/api/overview/route.ts` makes (T-09) — inside a `try`/`catch`. On success it renders the
page's `<h1>` (`PageHeader`, unchanged from T-07) followed by the stat-card row and the
two-column card grid, fed from one `OverviewDto`. On a throw (§2.8) it renders the heading plus
a single `OverviewError` card in place of the grid, and logs the error with the request id the
middleware already forwards on every request (`(await headers()).get("x-request-id")` — the
same header `(app)/layout.tsx` already reads for a different purpose, T-08's
`x-last-reset-at`). No loading state: this is a server component, so the page does not render
until the data (or the error) is ready — SPEC-overview names no skeleton.

**Component tree** (SPEC-overview §6's own list, `src/ui/overview/`):

```
OverviewPage (server)
├── PageHeader (existing, T-07)
├── success:
│   ├── StatCard × 3            "Current Balance" (dark), "Income", "Expenses" (light)
│   └── two-column grid
│       ├── PotsCard            → Donut-free; its own 2×2 item grid
│       ├── TransactionsCard
│       ├── BudgetsCard
│       │   └── Donut
│       └── BillsCard
└── failure: OverviewError (client — the only client component this task adds)
```

`StatCard`, `PotsCard`, `TransactionsCard`, `BudgetsCard`, `Donut`, `BillsCard` are exactly the
six names SPEC-overview §6 Interfaces lists; `OverviewError` is this task's own addition,
needed because §2.8's "Retry" button calls `router.refresh()`, which only a Client Component
can wire to an `onClick` (the same reason `ResetBanner`'s dismiss button and `LogoutButton` are
client components today) — recorded as D1 below, not a deviation from the spec's list.

**Formatting.** All money through `formatMoney`/`formatSignedMoney`
(`src/shared/money.ts`, T-03/T-04, unchanged) and all dates through `formatDate`
(`src/shared/dates.ts`, unchanged). `getOverview` already returns cents and ISO-8601 UTC text
(T-09) — the page performs no arithmetic and no date math of its own (§4.1).

**Theme colours.** Every card that draws a theme bar (pots, budget legend, the donut) needs a
CSS colour for a `Theme` value (`"Green"`, `"Navy Grey"`, …). `tests/unit/shared/enums.test.ts`
(T-04) already pins, for every one of the 15 themes, that `src/ui/tokens.css` has a token named
`--color-<theme, lowercased, spaces to hyphens>` — the exact rule this task's own
`themeVar(theme)` helper applies (`src/ui/overview/theme-color.ts`). This is reusing an
already-tested mapping, not inventing a new one: nothing here needs its own bijection guard the
way T-09's `CATEGORY_LABEL`/`THEME_LABEL` did, because the two ends of this mapping (`Theme`'s
15 members and the 15 `--color-*` tokens) are already held together by that existing test.

**Donut.** SPEC-overview §4.4 gives exact geometry: SVG 240 px, ring width 24 px, segments
proportional to each shown budget's `maximum`, drawn clockwise from 12 o'clock in creation
order, no gaps, with an inner ring at 25 % opacity via `color-mix`. The segment math (which
budget owns which arc of the circle) is a pure function, `donutSegments(items, total)` in
`src/ui/overview/donut-geometry.ts`, returning each segment's `theme` and its
`strokeDasharray`/`strokeDashoffset` pair for an SVG `<circle>` of radius `r = 108` (canvas
120,120 centre; ring spans radius 96–120, flush with the 240 px canvas edge — `r = 240/2 -
24/2`) — kept separate from the `Donut` component itself (T-08's D2/T-09's D7 pure/impure
precedent) so the geometry is unit-tested without rendering anything. `total` is the DTO's own
`budgets.limit` (**all** budgets' maximums, §2.5 "totals always include all budgets"), not the
sum of the `items` shown — see D3 for why this never diverges in Release 1. The centre label
(`$338.00` / "of $975.00 limit") is plain text absolutely positioned over the SVG, not inside
it — simpler than an SVG `<text>` and unaffected by the ring's stroke.

**Avatars.** `<img src={`/avatars/${avatar}.jpg`} alt={name} width={40} height={40} />` — a
bare `<img>`, never `next/image` (`src/ui/README.md`: "No `style` prop and no `next/image`
anywhere" — `next/image` writes an inline `style` attribute the CSP's `style-src` blocks,
ADR-0006). `public/avatars/*.jpg` already holds every seed avatar (T-01).

**Empty states (§2.7).** Each card owns its own empty branch, driven only by its slice of the
`OverviewDto` — no page-level "is anything empty" flag:
- Pots: `items.length === 0` → the tile still shows `$0.00` (from `total`, which is 0 whenever
  there are no pots), the 2×2 grid is replaced by `COPY.potsEmpty` + a `COPY.addPot` link to
  `/pots`.
- Transactions: render exactly `items.length` rows (0–5, already capped server-side); zero rows
  → `COPY.transactionsEmpty`, no link (the copy appendix has none for transactions, and §2.7
  names none).
- Budgets: `items.length === 0` → a single ring in `--color-grey-100` (no segments), centre
  `$0.00` / "of $0.00 limit" (both `spent`/`limit` are 0 whenever there are no budgets), legend
  replaced by `COPY.budgetsEmpty` + `COPY.addBudget` link to `/budgets`.
- Bills: no empty branch — always three rows; `no-recurring` still produces `{paid: 0, upcoming:
  0, dueSoon: 0}` from the domain layer (already true today, unit-tested in T-03/T-09), so
  `BillsCard` just formats whatever it is given.

## Review Focus

1. **The donut's proportions silently use the wrong denominator.** Expected: with the seed's
   four budgets (`maximum` $50/$750/$75/$100, `limit` $975), the largest segment (Bills, $750)
   covers `750/975 ≈ 76.9 %` of the ring — not `750/975` computed a different way if `total`
   were accidentally the sum of only the shown items (which is the same $975 today, D3, so this
   specific mutation is only observable once a 5th budget exists — flagged, not fixed, since R2
   is out of scope). → `donutSegments`' own unit test asserts the exact `strokeDasharray` values
   against a hand-computed circumference for a fixture with a 5th, unlisted budget in its
   `total` but not its `items`, proving the function reads `total` as its own parameter rather
   than summing `items` itself.
2. **A card renders `undefined`/`NaN` instead of `$0.00` when a list is empty.** Expected: the
   Pots tile shows exactly `$0.00` (not blank) when `pots.total` is 0; the Budgets centre shows
   `$0.00` / "of $0.00 limit". → Component tests feed each card an empty-list `OverviewDto`
   slice with `total`/`spent`/`limit` at 0 and assert the exact formatted text, not just "no
   crash".
3. **A transaction's sign or colour is backwards.** Expected: a positive `amount` renders green
   with a `+` prefix, a negative one grey-900 with no extra sign (§2.4; `formatSignedMoney`
   already unit-tested in T-03/T-04, so this specifically checks the *card* applies the colour
   class correctly, not the formatter). → A component test with one positive and one negative
   fixture row, asserting both the text and the CSS class/colour.
4. **The Retry button doesn't actually retry.** Expected: clicking it calls Next's
   `useRouter().refresh()` (not a full page reload, not a no-op). → A component test mocks
   `next/navigation`'s `useRouter` (the existing convention, `tests/unit/README.md`) and asserts
   `refresh` was called once per click.
5. **The empty-pots/-budgets link goes to the wrong route, or is missing its accessible name.**
   Expected: "Add a pot" is an `<a href="/pots">` reachable by role `link` with that exact name;
   same for "Add a budget" → `/budgets`. → Component tests query by role/name, not by CSS
   selector, so a link rendered without an accessible name (e.g. an icon-only link) fails the
   same way a real user or the E2E suite's own locators would.
6. **The card grid's item placement collapses on a real browser at 1024 px**, unlike a jsdom
   component test, which never lays anything out. → Not caught here — this is exactly what the
   E2E suite's 1024 px case and the DoD's 1440/768/375 screenshots are for, not a unit test;
   noted so a reviewer does not expect the component tests to prove layout.

// src/ui/overview/donut-geometry.ts
import type { Theme } from "@/src/shared/enums";

/** SPEC-overview §4.4: SVG 240 px, ring 24 px, flush with the canvas edge. */
export const DONUT_SIZE = 240;
export const DONUT_STROKE = 24;
export const DONUT_RADIUS = DONUT_SIZE / 2 - DONUT_STROKE / 2;

export type DonutSegment = { theme: Theme; strokeDasharray: string; strokeDashoffset: number };

/**
 * SPEC-overview §4.4: segments proportional to each item's `maximum`, clockwise from 12
 * o'clock, no gaps. `total` is the caller's own denominator (T-10 plan D3 — the DTO's
 * `budgets.limit`, all budgets, not necessarily the sum of `items`). An SVG `<circle>`
 * conventionally starts its stroke at 3 o'clock, so the ring itself is rotated -90deg in CSS;
 * this function only computes lengths and offsets along the circle's own circumference.
 */
export function donutSegments(
  items: readonly { theme: Theme; maximum: number }[],
  total: number,
): DonutSegment[] {
  const circumference = 2 * Math.PI * DONUT_RADIUS;
  let offset = 0;
  return items.map(({ theme, maximum }) => {
    const length = total > 0 ? (maximum / total) * circumference : 0;
    const segment: DonutSegment = {
      theme,
      strokeDasharray: `${length} ${circumference}`,
      strokeDashoffset: -offset,
    };
    offset += length;
    return segment;
  });
}
