**Goal:** Give Release 1 its shared contract in `src/shared`: the enums of the data model as the
documents spell them, every user-visible message of the copy appendix in `copy.ts`, the Zod
schemas that the forms, the route handlers and the WebMCP tools all validate with (auth, the
error envelope, the Overview DTO, meta), and a `test-ids.ts` that an ESLint rule makes the only
source of `data-testid` values — each held to its source document by a test that fails on
purpose when the two drift.

**Architecture:** `src/shared` imports nothing from the rest of the codebase (ADR-0002) and
nothing from Prisma (the T-01 lint rule), so the enums are written out by hand and a unit test
holds them to `data-model.md`, to the seed's maps and to the theme colours in `tokens.css`.
`copy.ts` is one `COPY` object; the appendix's placeholders become function parameters, and a
mirror test renders every entry and compares it with the appendix row by row. `schemas.ts`
holds every schema the specs name: request schemas drop unknown keys, response schemas are
strict so that an API test fails on a leaked field, and each field carries exactly one message
(US-31). `src/server/http.ts` stops keeping its own list of error codes and writes the shared
`ErrorEnvelope`.

## Review Focus

The five inputs the specs imply but do not spell out, most likely first. Each has its test in
the task that owns the code.

1. **Blank or padded text** — a name or email of spaces, or one with spaces around it. A reader
   expects "Can't be empty" for blank, and the padding trimmed before any length rule
   (Task 3: "an email that is blank", "measures the email after trimming", "a name of \"   \"",
   "measured after trimming").
2. **A password with spaces** — never trimmed; a login password of three spaces is present and
   goes to the server, which answers 401 (Task 3: "only checks that a password is present").
3. **An email at 254 and 255 characters** — the first is accepted, the second reads "Enter a
   valid email address" (Task 3; question 2).
4. **A DTO that carries more than the spec lists or spells a value the Prisma way** — the domain's
   rows keep `seq`, `category`, `recurring`; Prisma's client says `DiningOut`; the seed stores
   image paths. A strict schema refuses each, so T-09's API test fails rather than ship them
   (Task 4).
5. **Dates and money in the wrong form** — an offset (`+04:00`) or a zone-less time, cents as a
   fraction or a `BigInt` not converted at the repository edge, a `retryAfter` of 0 or 1.5
   (Tasks 3 and 4).

## Questions for the owner (plan gate)

Each question says what it is about, what each answer would mean, and what the agent recommends.
The tasks below are written for the recommended answers; each question says what changes
otherwise.

**1. How does the API spell categories and themes?**
data-model.md writes `Dining Out` and `Navy Grey`; the database stores those names
(`@map("Dining Out")`, T-02 D4); Prisma's client reads them back as `DiningOut` and `NavyGrey`.
The DTO (`OverviewDto`), the WebMCP output (SPEC-webmcp-tools §2.6: "the API DTO unchanged") and
Release 2's `?category=` filter all carry the spelling the API chooses.
- *The documents' names (recommended):* `CATEGORIES`/`THEMES` are data-model.md's lists; the
  schema refuses `DiningOut`. `src/server` maps Prisma identifiers to names; T-09, the first
  route that reads them, writes that mapping, and T-04's test pins the rule it needs (identifier
  = name without spaces). T-02 D4 said `enums.ts` would hold "the display names and the mapping";
  `src/shared` cannot know Prisma's identifiers (the lint rule), so the mapping moves to
  `src/server` — T-02's hand-off already said "the server maps between them".
- *Prisma's identifiers:* no mapping at all, but every consumer (agents, the UI) sees `DiningOut`
  and must translate for display; data-model.md's lists no longer match the API.
- *T-04 also writes the mapping* (`src/server/enums.ts`, typed against Prisma's generated enums):
  as the first answer, one task earlier; T-04 then changes a second `src/server` file.

**2. Copy for the three sign-up maxima**
SPEC-auth §6 limits the name to 60 and the password to 128 characters, §4 the email to 254; the
appendix has no message for any of them, and the DoD forbids copy outside it.
- *Two new rows and one reuse (recommended):* "Sign-up name | > 60 characters | Maximum 60

 * The lists data-model.md writes out: "Enums: `Category` = Entertainment, Bills, … .
 * `Theme` = Green, … ." and `ResetLog`'s "`reason` (`scheduled` \| … )". Throws when either
 * is missing, so a reworded document fails instead of comparing nothing with nothing.

function documentedEnums(markdown: string): Record<string, string[]> {
  const line = markdown.split("\n").find((text) => text.startsWith("Enums:"));
  const reasons = /`reason` \(([^)]*)\)/.exec(markdown)?.[1];
  if (!line || !reasons) throw new Error("No enum lists in data-model.md");
  const lists = [...line.matchAll(/`(\w+)` = ([^.]+)\./g)].map(
    ([, name = "", list = ""]) => [name, list.split(",").map((item) => item.trim())] as const,
  );
  const reset = reasons.split("\\|").map((item) => item.trim().replaceAll("`", ""));
  return { ...Object.fromEntries(lists), ResetReason: reset };
}

import { z } from "zod";
import { COPY } from "./copy";

/**
 * The request and response schemas of docs/02-architecture/data-model.md ("Request/response
 * schemas live in src/shared/schemas.ts and are reused by forms and tools", NFR-Q2). Release 1:
 * auth (SPEC-auth §6), the error envelope (§2.10), the Overview DTO (SPEC-overview §6) and
 * meta (SPEC-app-shell §5). Written by hand: ADR-0002 keeps Prisma's types out of src/shared.
 *
 * Request schemas are `z.object` (unknown keys are dropped); response schemas are
 * `z.strictObject`, so an API test fails when a route leaks a field the spec does not list.
 */

// ---------------------------------------------------------------------------------------
// Auth — SPEC-auth §4, §6; messages from the copy appendix (US-31)

/** SPEC-auth §4: "RFC-5322-lite". */
export const EMAIL_PATTERN = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
export const EMAIL_MAX = 254;
export const NAME_MAX = 60;
export const PASSWORD_MIN = 8;
export const PASSWORD_MAX = 128;

/**
 * A required text field. A missing, non-text or blank value reads "Can't be empty" (appendix,
 * "Any required field"), and the checks stop at the first failure, so a field carries one
 * message — the one US-31 shows under it.
 */
const requiredText = () => z.string({ error: COPY.required });
const stop = (message: string) => ({ message, abort: true });

/** SPEC-auth §4: "Email: trimmed, max 254, RFC-5322-lite regex". */
const email = requiredText()
  .trim()
  .min(1, stop(COPY.required))
  .max(EMAIL_MAX, stop(COPY.emailInvalid))
  .regex(EMAIL_PATTERN, COPY.emailInvalid);

/** SPEC-auth §2.3: "password required"; §4: "login only checks presence". Never trimmed. */
export const LoginSchema = z.object({
  email,
  password: requiredText().min(1, COPY.required),
});
export type LoginInput = z.infer<typeof LoginSchema>;

/** SPEC-auth §6: `SignupSchema { name(1–60), email, password(8–128) }`. */
export const SignupSchema = z.object({
  name: requiredText().trim().min(1, stop(COPY.required)).max(NAME_MAX, COPY.nameTooLong),
  email,
  password: requiredText()
    .min(1, stop(COPY.required))
    .min(PASSWORD_MIN, stop(COPY.passwordTooShort))
    .max(PASSWORD_MAX, COPY.passwordTooLong),
});
