## Goal

The server half of the Transactions page: the pure list rules in `src/domain` (`sortTransactions` with its six
orders and every tie rule, `filterTransactions`, `paginate`), the shared query contract (`parseTransactionsQuery`,
lenient for the page and strict for the API; the sort slugs; `TRANSACTIONS_PAGE_SIZE`), the strict
`TransactionsDtoSchema`, `src/server/transactions.ts` (`getTransactions`, `toTransactionsDto`) and the read route
`GET /api/transactions`, with the seed's figures of `transactions.md` 4.2–4.7 moved into `scripts/seed-figures.ts`
(H11 (3)).

**What T-18 is not:** no page, no component, no `Menu`, no `pageItems`, no `useDebouncedValue`, no copy strings, no
tokens and no tool (all T-19, with H11's other parts). No design question arises: nothing here is drawn.

## Findings — read or run 2026-10-10 on `origin/develop` `6e32af9`

- **F1. The seed's figures still hold.** `figures.ts` of T-15d (`docs/04-process/prompts/2026-10-04-T-15d/
  transactions-figures/`) was re-run on today's `develop`; its output is identical to the recorded `output.txt`
  (`diff` empty). So 4.2–4.7 can move into `scripts/seed-figures.ts` as they are.
- **F2. Two invalid parameters, one `message`.** 2.3 gives the strict 400 one `message` per field ("sort must be one
  of: …", "category must be one of: …", "q must be at most 60 characters") but does not say what the `message` is
  when two or three are wrong at once (`?sort=nope&category=Nope`); `issues` can carry all of them. → **Q1**.
- **F3. The 500 cannot be caused in the API suite.** §7's API row asks for `no-store` on the 500 against the real
  database. Overview and meta cause their 500 by deleting a singleton row (`Balance`, `ResetLog`); `getTransactions`
  reads only `Transaction`, and an empty table is a 200 with `total: 0` (the `empty-all` state), not an error. No
  row the schema accepts makes `findMany()` or the mapping throw. → **Q2**.
- **F4. The inverse of `CATEGORY_LABEL` has no reader.** §6 "Server and API" and the backlog row list "the inverse
  of `CATEGORY_LABEL` for the filter", but 2.4 says `getTransactions` reads every row, maps each category to its
  display name, and only then applies the category filter in the domain on display names (NFR-T1: the rules live in
  tested domain functions, not in SQL). Under 2.4 nothing would call the inverse. → **Q3**.
- **F5. The 400 carries `message` as well as `issues`.** `validationErrorResponse` (`src/server/http.ts`) writes
  `issues` only, following `auth.md` §2.10 ("a validation error carries `issues`, never `message`"); 2.13 asks this
  route's 400 for both, and `ErrorEnvelopeSchema` allows both. `validationErrorResponse` gains an optional
  `message`; the auth routes keep calling it without one.
- **F6. Three ids leave the shrink-only list.** T-18's tests name US-09, US-10 and US-12 (the backlog row's
  stories; US-11, US-36 and US-39 are already named), so under H4 (a) they leave `NOT_YET_BUILT` in
  `scripts/traceability.ts`: **16 ids remain** (US-13–26, 29, 30).
- **F7. The page's `searchParams` and the route's are not the same type.** The route reads a `URLSearchParams`
  (`request.nextUrl.searchParams`); the page (T-19) awaits Next's `Record<string, string | string[] | undefined>`,
  where a repeated parameter is an array. `parseTransactionsQuery` takes either and reads the first value (2.2:
  "a repeated parameter reads as its first value"); both already decode `+` as a space.

## Decisions taken in the plan (the spec leaves them to the build)

- **D1. Domain** (`src/domain/transactions.ts`, pure, generic over the caller's row as `latestTransactions` is):
  `sortTransactions(rows, sort)` — 2.4's six key lists, names with the existing `Intl.Collator("en")`, `id`
  ascending by code-unit order as the last key of every sort; `latest` is `compareLatest` followed by `id`, so Latest
  stays the Release 1 order. `filterTransactions(rows, { q, category })` — category by `===`, the needle with
  `toLowerCase()` on both sides and `includes` (no pattern characters). `paginate(rows, page)` →
  `{ items, page, pageCount, total }`, `pageCount = max(1, ceil(total / 10))`, the page clamped. The domain imports
  `TRANSACTIONS_PAGE_SIZE` and the sort type from `src/shared` (allowed by `eslint.config.mjs`).
- **D2. Shared** (`src/shared/transactions-query.ts`): `TRANSACTIONS_PAGE_SIZE = 10`, `TRANSACTION_SORTS` (the six
  slugs in 2.4's order; their labels are copy and come with T-19, H11 (1)), `TRANSACTIONS_Q_MAX = 60`, and
  `parseTransactionsQuery(params, { strict })` → `{ query, issues, message }`: every row of 2.3, written by hand
  with `invalid_format` and `too_long` (no Zod, so no dependency on `toErrorIssues`); issues in the URL contract's
  order `q`, `category`, `sort`; empty values read as absent; `page` matches `/^[1-9]\d*$/` or reads as 1 (the
  clamp to the last page is `paginate`'s, which knows the total). The `message` for several issues is **Q1**.
- **D3. The DTO** (`src/shared/schemas.ts`): `TransactionsDtoSchema`, a `z.strictObject` with strict items
  (`id` `z.uuid()`, `name` 1–60, `avatar` non-empty, `category` `CategorySchema`, `date` `z.iso.datetime()`, `amount`
  `z.int()`), `items` at most 10, `page` and `pageCount` integers ≥ 1, `pageSize` `z.literal(10)`, `total` integer ≥ 0.
- **D4. Server** (`src/server/transactions.ts`): `getTransactions(db, query)` reads `db.transaction.findMany()` with
  no `where` and no `orderBy` (2.4), maps `BigInt` → `Number` and the category through `categoryLabel` (reused from
  `overview.ts`), then filter → sort → paginate, and returns `toTransactionsDto(...)`, which names every field (the
  `toOverviewDto` pattern), so `recurring`, `seeded` and the timestamps never reach the DTO.
- **D5. The route** (`app/api/transactions/route.ts`): `GET` only; strict parse → 400 via
  `validationErrorResponse(issues, 400, message)`; `getTransactions(getDb(), query)` → `Response.json(dto)` with
  `Cache-Control: no-store`; a throw → `console.error("GET /api/transactions failed", error)` and
  `errorResponse(500, "server_error", "The transactions are unavailable")`. Every answer is `no-store`
  (`http.ts`'s helpers already set it since T-17). The route-table guard of T-17 already holds a `GET` that never
  calls `guardedWrite`.
- **D6. Figures (H11 (3)).** `scripts/seed-figures.ts` gains `seedTransactions()` (the 49 rows from `data.json`
  with the domain's conversions, each with a stable index as its `id`) and `transactionFigures()`, which computes
  every figure of 4.2–4.7 with the domain functions of D1 (counts, pages, per-category counts, the default page,
  each sort's first and last row, the tie groups, the search and filter examples, the Budgets-link views, the
  boundaries). `tests/unit/seed-figures.test.ts` holds 4.3's table cell by cell to the generated one (the Overview
  §4.3 precedent, with one violation fixture), and its existing field-for-field check against `seedRows()` covers
  the transactions' categories too. The prose figures of 4.2 and 4.4–4.7 are read by the tests from
  `transactionFigures()`; the spec's prose is not parsed.
- **D7. Traceability** (F6): US-09, US-10 and US-12 leave `NOT_YET_BUILT`; the unit test that pins the list as a
  subset of the 20 ids of 2026-10-06 still passes; ADR-0003's dated line gets one more sentence with the 16 ids.
- **D8. One pull request** for the whole task, the one that carries this plan, one commit per task A–E below (the
  T-17 precedent; T-18 is about a third of T-17's size).

## Questions for the owner

**Q1. Two wrong values in one API call (F2).** When an agent or a direct call sends two wrong values at once, for
example `?sort=nope&category=Nope`, the API refuses with a 400 that lists both fields in `issues`. The spec gives a
text for each field but not for two at once.
- **(a)** The `message` holds every field's text, joined in the address's order (`q`, `category`, `sort`) with
  "; ", e.g. "category must be one of: Entertainment, …, General; sort must be one of: latest, …, lowest".
  `transactions.md` 2.3 gains one sentence saying so, as an amendment in this task's pull request, approved by your
  merge. **Recommended:** the agent learns every allowed list in one refusal, so its next call can be right (your
  answer to §9 Q3).
- **(b)** The `message` names only the first wrong field; `issues` still lists all. The agent may need a second
  refusal to learn the second list.

**Q2. Testing the "unavailable" answer (F3).** The spec asks the API tests to show that the 500 ("The transactions
are unavailable") is not cached. Against the real database there is no honest way to make the list fail: an empty
table is a normal empty list.
- **(a)** Test the 500 at unit level: the route is called with the database replaced by one that throws, and the test
  checks the 500, its body, `no-store` and the logged line. The API tests check `no-store` on 200 and 400.
  `transactions.md` §7 moves "500" from the API row to the unit row, one sentence in the same amendment as Q1.
  **Recommended:** the 500 path is fully tested, with no change to the app.
- **(b)** Make the route check its own answer against `TransactionsDtoSchema` before sending it, so the API test can
  insert a row the contract cannot carry (a 61-character name) and get the 500. This adds a check on every request
  only to make the test possible, and needs its own spec sentence.

**Q3. The reverse category table (F4).** The spec's file list and the backlog row mention a reverse table (display
name → database name) "for the filter", but the spec's own rule (2.4) filters after every row's category is already
turned into its display name, so nothing would use that table.
- **(a)** Follow 2.4 and do not build the reverse table; `transactions.md` §6 and T-18's backlog row drop those
  words, in the same amendment as Q1 and Q2. **Recommended:** no unused code, and the rule stays in the tested
  domain function.
- **(b)** Build it and filter the category in the database query, then search, sort and page in the domain. 2.4 then
  changes, and the category rule is tested only at API level.
