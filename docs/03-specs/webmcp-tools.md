## 1. Purpose
Expose the app's capabilities to in-browser agents through one adapter, page by page, with the polyfill as baseline, and make it testable without any agent.

## 2. Behaviour
2.1 Configuration: the documented knob is `WEBMCP_MODE` (`native | polyfill | off`, default `polyfill`); `next.config` exposes it to the client as `NEXT_PUBLIC_WEBMCP_MODE`. `native` means *opportunistic native with polyfill fallback* (there is no way to force native). `APP_ENV=test` is exposed as `NEXT_PUBLIC_APP_ENV` for the test hook.
2.2 `src/webmcp/adapter.ts` (names per ADR-0004): `getModelContext()`, `register(tools)`, `unregisterAll()`, `mode()`, `onStatus(cb)`.
  - `off` → `register` no-op; `mode() = "unavailable"`.
  - The polyfill throws `SecurityError` unless `originAgentCluster` is true; the app sends `Origin-Agent-Cluster: ?1` (ADR-0006 (5)) (v1.0.5).
  - Otherwise: if `"modelContext" in document` before the app installs anything → `mode = "native"`; else `await import("@mcp-b/webmcp-polyfill")` once → `mode = "polyfill"`; import failure → `mode = "unavailable"`, `console.warn`.
  - `register(tools)` creates one `AbortController` per generation, awaits the polyfill if needed, then calls `document.modelContext.registerTool(def, { signal })` for each tool with that generation's signal — a still-current generation, since the signal check inside `registerTool` (the runtime's own) rejects a tool whose signal was already aborted, giving "only if the generation is still current" without a separate counter comparison (v1.0.3, T-11 plan Q1). `unregisterAll()` aborts that controller, which cancels any pending registration and removes every already-registered tool of that generation in the one call — there is no name-based `unregisterTool` on the installed runtime.
  - After a completed `register`: set `document.documentElement.dataset.webmcp = "ready"`, dispatch **one** `toolchange` `Event` on `document` and, if `document.modelContext` is an `EventTarget`, on it too (duplicates with runtime-fired events are harmless; tests wait only on the attribute). `unregisterAll` removes the attribute.
  - When any `registerTool` call is rejected the adapter `console.warn`s once per rejected tool (`[webmcp] could not register tool "<name>"`, then the reason object) and sets `document.documentElement.dataset.webmcpError` to `<tool>: <reason>` pairs joined by `; ` (removed by `unregisterAll` and at the next `register`); `<reason>` is the error's `name`, followed by `: ` and its `message` when it has one (`SecurityError`, `Error: duplicate name`), else `String(reason)`. `data-webmcp` is still `ready`. A superseded generation (one whose `AbortSignal` was aborted by a later `register` or by `unregisterAll`) stays silent: no warning and no attribute. While every tool of the current generation was rejected (a page that registers no tools is not a failure), `mode()` — and so `onStatus` and `window.__pf.webmcp.mode()` — reports `"unavailable"` until the next `register` or `unregisterAll` (v1.0.5).
  - Loading: adapter and polyfill chunks load after hydration via `typeof requestIdleCallback === "function" ? requestIdleCallback(cb, { timeout: 2000 }) : setTimeout(cb, 0)` (NFR-P3).
2.3 `src/webmcp/WebMcpProvider.tsx` (client) is mounted once in `app/(app)/layout.tsx` and owns the adapter and the indicator state; each page's own `layout.tsx` renders a no-prop `"use client"` wrapper (`<OverviewTools />`, `src/webmcp/tools/`) that imports the page's registry and renders `<WebMcpTools tools={pageTools}/>` (on Budgets and Pots the wrapper first wraps the `execute` of the mutating tools that call the API, §4, "After an agent's write"; v1.0.10) — a Server Component cannot pass `execute` functions to a Client Component as props (v1.0.4); `<WebMcpTools>`'s effect calls `register(tools)` on mount and `unregisterAll()` on unmount (React remounts it per route segment because it lives in the page's own `layout.tsx`, not the shared one). Pages without tools (R2 placeholders) render no `<WebMcpTools>`, so `mode()` is still reported with 0 tools. Nothing is mounted in `(auth)`.
2.4 `src/webmcp/tools/<page>.ts` exports `ToolDefinition[]` built with `defineTool({ name, title, description, input: ZodSchema, annotations, execute })`; `defineTool` converts Zod → JSON Schema with `z.toJSONSchema(schema, { io: "input" })` (Zod 4; its default `reused: "inline"` behaviour needs no `$refStrategy`-equivalent option), and throws at build time if: name ∉ `^[A-Za-z0-9_.-]{1,128}$`, description > 200 chars, any string property lacks `maxLength`, or annotations are missing.
2.5 `execute({ input, signal })`: validates `input` with the Zod schema → `error("validation")`; calls `src/shared/api-client.ts` (`apiGet`, a fetch wrapper that returns a tagged outcome and never throws) with header `X-Via: webmcp` (the wrapper (`apiGet`) accepts a signal; the Release 1 tools do not pass one (the runtime hands a tool none, T-11 Q2); v1.0.4); Release 2's write tools call the write client instead (`apiSend`, a build task's name, `write-path.md` 2.11 (2)), and only a write can get a 403 or a 415 — the proxy's write rule excludes `GET` (`write-path.md` §6, "API"; v1.0.8); maps responses: 2xx → success; 400 or 415 → `validation`; 401 → `unauthenticated`; 403 → `forbidden`; 404 → `not_found`; 409 → `conflict`; 429 → `rate_limited`; abort → `cancelled`; other → `server_error`. Never throws. (v1.0.7: the 403 and 415 rows are `write-path.md` 2.11 (4) — a write route refuses a cross-site request with 403 `forbidden` and an unsupported `Content-Type` with 415 `validation`, `write-path.md` 2.3–2.6; until v1.0.7 a 403 or a 415 mapped to `server_error`. `TOOL_ERROR_CODES` (`src/webmcp/tool-result.ts`) has neither `forbidden` nor `busy` (§4's delete flow) today; adding both is a build note, `write-path.md` 2.11 (4). Each code also needs a `DEFAULT_TOOL_MESSAGE` entry, the agent-facing text used when the answer carries no message (v1.0.8): `forbidden`'s is the 403 body's own message, "This request must be same-origin" (`write-path.md` 2.6), so no new text is written; `busy` never has an answer from the API, and its fallback belongs to the delete flow's contract, `ui-kit.md` 2.3 item 7, which leaves the text to the build task that adds the code (hand-off H13 (1); v1.0.10). A delete tool calls the bus, not the write client; its confirmed request is the page's own `apiSend` with `X-Via: webmcp` (`ui-kit.md` 2.3 item 5; §4).)
2.6 Result shapes (ADR-0004): success `{ content: [{ type: "text", text: JSON.stringify(data) }], structuredContent: data }` where `data` is the API DTO **unchanged (money in integer cents)** plus `{ currency: "USD", unit: "cents" }` at the top level; error `{ isError: true, code, message, content: [{ type: "text", text: message }] }`; a `validation` error also carries `issues: { path, code }[]` (from `toErrorIssues`, or copied from a 400 or a 415 body — v1.0.7; a 415's body is `issues: [{ path: [], code: "invalid_format" }]`, `write-path.md` 2.6) when the shared contract can name them, and a `rate_limited` error carries `retryAfter` when the API gave one; a tool with no input ignores unknown keys (v1.0.4).
2.7 Indicator `<AgentToolsStatus>` (sidebar footer; compact dot on tablet/mobile with `aria-label` = full text), `role="status"`, `aria-live="polite"`:

| State | When | Text | `title` |
|-------|------|------|---------|
| checking | before the adapter resolves | "Agent tools: checking…" | "Detecting WebMCP support" |
| native | `mode() === "native"` | "Agent tools: native · N" | "WebMCP is supported natively by this browser" |
| polyfill | `mode() === "polyfill"` | "Agent tools: polyfill · N" | "Provided by a polyfill; no built-in agent yet" |
| unavailable | off, import failed, **or every tool registration of the page was rejected (at least one tool)** | "Agent tools: unavailable" | "WebMCP is disabled or could not load" |

N = number of currently registered tools (0 on pages without tools).
2.8 Via-marker observability: every API response carries `X-Request-Id`; requests with `X-Via: webmcp` are logged as `{ requestId, via: "webmcp", method, route }` — `method` is the request's HTTP method as the server receives it (`request.method`; `fetch` does not upper-case `patch`, `write-path.md` §6, "API"), new in Release 2 (v1.0.7, letter case v1.0.8; `write-path.md` 2.12: a write and a read on the same path are otherwise indistinguishable, and US-40 AC3's "via tool" marker is tested per method) — recorded by `proxy.ts` before the session check, so a 401 is on record too; when `APP_ENV=test`, `GET /api/test/log?requestId=` returns that entry (with `method`, `reset-and-test-support.md` v1.8 §2.7), and answers 404 for an unknown, empty or missing `requestId` (SPEC-reset-and-test-support §2.7; v1.0.4).

What every mutating and delete tool shares — `consequentialHint`, `untrustedContentHint` when the output holds user-entered text, `X-Via: webmcp` on every write, the write client, validation with the same schema, the error mapping of §2.5, the record `id` as `z.uuid().max(36)` on every tool that addresses an existing record (R-26; `add_budget` and `add_pot` take none, v1.0.10) — is `write-path.md` 2.11 and its §6 "WebMCP tools"; a page spec cites it and adds only its own tools' rows. The polyfill's `getTools()` drops `consequentialHint`, so the registry unit test asserts it (`write-path.md` 2.11 (6); hand-off H3): on the three mutating Budgets tools (`budgets.md` 2.13) and the five mutating Pots tools (`pots.md` 2.13); a read tool carries none (`transactions.md` 2.14, `recurring-bills.md` 2.12).

**After an agent's write** (US-40 AC3: "visible in the UI immediately (same state as a user action)"; v1.0.10). One mechanism for both pages, stated in `budgets.md` 2.13 and `pots.md` 2.8: a tool's `execute` is a module-level function and cannot call a React hook, so the page's Tools component (§2.3: `BudgetsTools`, `PotsTools`) builds, once per router, the list it hands to `<WebMcpTools>`, with the `execute` of each mutating tool that calls the API itself (`add_budget`, `edit_budget`; `add_pot`, `edit_pot`, `add_money_to_pot`, `withdraw_from_pot`) wrapped so that, after a result without `isError`, it calls `router.refresh()` and returns the result unchanged. The registry keeps the unwrapped definitions, which the registry unit test checks. A delete tool is not wrapped: its confirmed request is the page's own write, which refreshes as a person's does. `src/webmcp/bus.ts` carries only the delete contract below; it is not extended for writes.

**Where the Release 2 acceptance criteria are tested** (v1.0.8; v1.0.10: US-38). Each page spec's Tests table carries, for its own tools: US-38 AC1 (the page registers exactly its tools, in polyfill and off modes; `recurring-bills.md` §7 also checks that leaving the page unregisters them), US-39 AC2–AC4 for its read tool (the data the page shows, the annotations, `unauthenticated` and no data without a session) and US-40 AC1–AC3 for its mutating and delete tools (`budgets.md` §7, `pots.md` §7; AC3: the change is on screen at once). US-38 AC2–AC3 (the modes and the readiness signal) are traced by §7's E2E rows here. `write-path.md` 7.6 tests what every mutating tool shares (the same route, on record with `method`, `validation` with `issues`, 403 → `forbidden`; US-40 AC1, AC3), and §7 here tests the adapter, the mapping and the log. `transactions.md` §7's WebMCP row is the model (US-38 AC1, US-39 AC2–AC4 for `list_transactions`).

**Delete flow** (`delete_budget`, `delete_pot`; ADR-0004, Decision, "Delete flow"; US-40 AC2): ADR-0004's "adapter dispatches an app event" goes through an in-page event bus (`src/webmcp/bus.ts`, the file name this spec has given since its first commit, `32946a9` of 2026-09-20 — `git log -S'src/webmcp/bus.ts' -- docs/03-specs/webmcp-tools.md`; ADR-0004 names no file; it does not exist yet and arrives with hand-off H13 (1)): the tool calls the bus's `requestDelete(kind, id, signal)`, and the page, subscribed with `onDeleteRequest`, opens the same `ConfirmDeleteDialog` the UI uses; the client sends `DELETE` only after the person confirms on screen. The dialog, the bus and every result are specified in `ui-kit.md` 2.3, which owns `ConfirmDeleteDialog`; `budgets.md` 2.13 and `pots.md` 2.13 cite it, and this spec does not repeat it (v1.0.10). The tool resolves `{ deleted: true }`, or one of `ui-kit.md` 2.3's other `DeleteResult` codes — `cancelled`, `busy` or `not_found` before any request (its items 1–3), the confirmed request's answer after it (item 4) — mapped as its item 7 says. `busy` is wider than US-40 AC2's words "a second call while the dialog is open": any modal of the page open, or a write of the page in flight (item 2); `not_found` before a request is an `id` the page does not show (item 3). Cancel is driven through the dialog, not through a signal: the runtime hands a tool no `AbortSignal` (T-11 Q2; hand-off H3). Abort still resolves `cancelled` (US-40 AC2; v1.0.8): since no runtime passes a signal, it is exercised only by tests that pass a synthetic one, as in §2.5; what an abort does to a dialog that is already open is `ui-kit.md` 2.3 item 6 (before a confirm the dialog closes with `cancelled`; after it the abort is ignored), tested in `ui-kit.md` §7.
