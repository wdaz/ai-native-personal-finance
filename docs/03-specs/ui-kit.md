## 1. Purpose

Budgets and Pots are the two pages that change data, and they draw the same controls to do it: a page-header button that opens a form in a modal, a "…" menu on each card with Edit and Delete, a delete confirmation, an amount field, a theme field (and on Budgets a category field) with "Already used" options. `src/ui` has none of them (ADR-0002 and `src/ui/README.md` promise a `Modal`; `write-path.md` §6 "UI" leaves the components to the page specs). This spec states each part once — what it does, its keyboard and accessible names, its states, its look in tokens and its component tests — so `budgets.md` and `pots.md` cite its sections by number, as they cite `write-path.md`, and add only what belongs to their page (which fields a form has, the money rules, the records shown). It also states the contract between the delete dialog and the agent tools `delete_budget` and `delete_pot` (ADR-0004), which `webmcp-tools.md` §4 points to.

**2.2 The modal** (`Modal`; US-15 AC4, US-32 AC2, NFR-A3). One modal is open at a time on a page.
- **One at a time — who holds it** (`ModalSlot`, `src/ui/ModalSlot.tsx`). The page's client container (in `app/`, the one that holds the page's records) provides one `ModalSlot` context for the whole page, so the header button, the cards' "…" menus, Pots' money buttons and the tool handler of 2.3 — which sit in different subtrees — share it. It holds two things in refs, read and written synchronously: whether a modal is open, and how many writes of the page are in flight. `claim()` returns a release function, or `null` when a modal is already open; it checks and sets in one synchronous step, before any `await`, so two calls in the same tick get one modal and the second `null`. `isBusy()` is true while a modal is open or a write is in flight; the page's write function counts its requests in and out (`trackWrite`). Every opener claims before it opens and releases once its modal has closed; a modal stays open while its own request is pending (2.7), so the slot is held until the answer is applied. A person's opener whose claim fails does nothing (the page behind an open modal is `inert`, so this happens only when a tool claimed in the same tick).
- **Props, in plain words:** whether it is open; the title; the description (optional); what to do when the person asks to close it; whether it may be closed now (`dismissible`, false while a request is pending, 2.7); which element gets focus first (optional); which element gets focus back (optional, otherwise the one that had focus when it opened); the body.
- **Roles.** Rendered in a portal on `document.body`: a backdrop element and, above it, a container with `role="dialog"`, `aria-modal="true"`, `aria-labelledby` the title (an `<h2>`) and `aria-describedby` the description when there is one — the design's markup (the designer's changelog §8d: `role="dialog"`, `aria-modal`, `aria-labelledby` the `<h2>`, `aria-describedby` the `<p>`, `tabIndex="-1"` on the container). While it is open every other child of `document.body` gets the `inert` attribute (restored on close), so the page behind can be neither focused nor clicked nor read; the page's scroll is locked (`overflow: hidden` on `<html>` through `element.style`, restored on close).
- **Focus.** On open: the element the page names (a form names its first field; the delete dialog names "No, Go Back", 2.3 — UK-Q6, as the design does: changelog §13b, `data-autofocus` on that button, which the design focuses before its general rule), otherwise the first focusable element after the close button (the design's rule, changelog §8d: "focus moves to the first field (index 1; index 0 is Close)"). **Tab and Shift+Tab wrap** inside the dialog (Tab on the last focusable element goes to the first, Shift+Tab on the first to the last; the list is read at each key press, since an open `Menu` adds elements) — as the design does. On close: focus returns to the element named, else to the one that had focus when the modal opened (the design returns it to the opener when the opener is still on the page); when that element is gone or disabled (the card was deleted), focus goes to `<main>` (`MAIN_CONTENT_ID`, `src/ui/Shell.tsx`), as the reset banner's dismissal does (`app-shell.md` 2.6) — the design leaves this case open. "Gone" is decided when the modal closes, and a record's card may still be on the page at that moment and unmount a moment later (a 204 removes it, a 404's refresh removes it asynchronously); so when the page closes a modal because a record was deleted or no longer exists, it names `<main>` as the element that gets focus back whenever the element it would return to lies inside that record's card (a 204) or inside the list being refreshed (a 404) (2.3, 2.7). Focus is never left on `<body>`.
- **Closing.** Escape, the close button and a click on the backdrop each ask to close, when `dismissible`. Escape while a `Menu` inside the modal is open closes only the menu — the design's order too (changelog §8e: Escape closes the open dropdown first and returns focus to its trigger): the `Menu` of `transactions.md` 2.8 stops the key there (`stopPropagation` on the Escape it handles), so the modal never sees it — a change to that component (§6), carried to its build by H13 (1). A backdrop click counts only when the press also started on the backdrop, so selecting text in a field and releasing outside the panel does not close the form. While a request is pending (`dismissible` false) all three do nothing.
- **Close button.** A `<button type="button">` named "Close" (the design's `aria-label`) holding `CloseCircleIcon` (`src/ui/icons`, 32 px, decorative), grey-500, grey-900 on hover (`--duration-hover`), the project's focus ring (`app/globals.css`, `--focus-ring-*`: 2 px grey-900, offset 2 px — the values of the design's `:focus-visible` rule, changelog §8b). It sits at the end of the title row, `--spacing-200` from the title.
- **Look** (the design's, in tokens): the backdrop `var(--color-backdrop)` (black at 50 %; UK-Q4); the panel white, `--radius-150`, padding `--spacing-400` (`--spacing-300` `--spacing-250` below 768 px), its parts `--spacing-250` apart, as wide as the viewport allows up to `var(--modal-max-width)` (560 px; UK-Q4 — never `--auth-card-max-width`, which holds the same number for the login card), centred, kept `--spacing-500` from the viewport's edges (`--spacing-200` below 768 px; the design's overlay padding, 40 / 16 px). When the panel is taller than the space, the full-screen layer that holds the backdrop and the panel scrolls (`overflow-y: auto`, the panel starting at the top gap rather than centred, so its top is never cut off), and the panel itself never scrolls or clips (`overflow: visible`): an options panel of 2.6 that reaches past the modal's bottom is part of the layer's scrolling area and is reached by scrolling the layer, where a scrolling panel would cut it off at the panel's bottom edge. The design draws the same since the designer's changelog §16b ("Modal scroll: spec wins"; **UK-Q10**, answered there): the backdrop has `overflow-y: auto` and `overscroll-behavior: contain` — the layer here takes the same `overscroll-behavior: contain` — and the panel has no maximum height and no overflow, centred with `margin: auto 0` when it fits and starting at the top padding when it does not; **no shadow** (`transactions.md` §9 Q2: the backdrop sets a modal apart). The title is `--text-preset-1` (`--text-preset-2` below 768 px) and wraps, an unbroken word too (`overflow-wrap: anywhere`), so a 30-character pot name in "Delete ‘…’?" never overflows the panel; the description is `--text-preset-4`, grey-500. It fades in over `var(--duration-modal)` (200 ms; UK-Q4), rising `--spacing-100` (the design's `fadeIn`: from opacity 0 and 8 px lower), and does not animate under `prefers-reduced-motion: reduce`.

**2.3 The delete confirmation and its contract with the agent tools** (`ConfirmDeleteDialog`; US-17 AC1, AC3, US-24 AC1, AC2, US-40 AC2, NFR-W5, ADR-0004). One component for both pages and for both ways in — a person's "Delete" in the "…" menu (2.4) and an agent's `delete_budget` / `delete_pot`. `webmcp-tools.md` §4's delete-flow sentence points here (S6).
- **What it shows** (a `Modal`): the title "Delete ‘{name}’?" (the design's words and curly quotes, U+2018 and U+2019; `{name}` is the budget's category or the pot's name), the description (`COPY.deleteBudgetConfirm` or `COPY.deletePotConfirm`, the appendix's), the error area of 2.7 when a request failed, then two buttons, `--spacing-250` apart: **"Yes, Confirm Deletion"** — full width, red, white `--text-preset-4-bold`, padding `--spacing-200`, `--radius-100`, the tokens' "destroy" button; on hover its background stays full red and its text is underlined (`text-decoration: underline`, `text-underline-offset: 3px`, the design's; no opacity change — UK-Q5, the designer's changelog §11 and the style guide's Button/Destroy; no hover with `[aria-disabled="true"]`, 2.7) — and **"No, Go Back"** — a text button, `--text-preset-4`, grey-500, grey-900 on hover (none with `[aria-disabled="true"]`, 2.7), at least `var(--tap-target-min)` (44 px) tall (`min-height`), as the design draws it (the designer's changelog §13b: "Its hit area is at least 44px tall").
- **Focus.** It opens on "No, Go Back", the action that loses nothing (a person who presses Enter at once keeps the record) — **UK-Q6**, answered (a) by the owner, and the design does the same since the designer's changelog §13b (`data-autofocus` on "No, Go Back"; the delete confirmation is the only modal with this exception to §8d's rule). Go Back, Escape, the close button and the backdrop all cancel.
- **Confirming.** The page's delete (`apiSend("DELETE", …)`, `write-path.md` 2.11 (2)) runs; meanwhile the confirm button reads "Deleting…" (approved, UK-Q1) and has `aria-disabled="true"` (it keeps focus; a click or Enter does nothing), **"No, Go Back" has `aria-disabled="true"` too and does nothing** (a cancel cannot recall a request already sent), and the dialog is not dismissible. Then, by answer (`write-path.md` §3): **204** — the dialog closes, the record leaves the page with no reload, and focus goes where 2.2 says: the page names `<main>` when the element focus would return to is inside the deleted record's card (after a person's delete, the "…" button that opened it), so focus never follows a button that is about to unmount; **404** — the dialog closes with `<main>` named the same way (the element is inside the list being refreshed), the notice of 2.9 says the record no longer exists and the list refreshes (US-17 AC3, US-24 AC2); **409** — the error area says "Data was reset — reloading" and the page reloads; **401** — the page reloads (the proxy's redirect to the login page); **429, 403, 415, 500, no response** — the error area shows `write-path.md` §3's message, the dialog stays open and both buttons work again.
- **The contract with the tools** (`src/webmcp/bus.ts`, imports `src/shared` only; the page — `app/` may import both layers — joins it to the dialog, and `src/ui` never imports `src/webmcp`):

```
type DeleteKind = "budget" | "pot";
type DeleteResult = "deleted" | "cancelled" | "busy" | "not_found" | "conflict" | "unauthenticated"
  | "rate_limited" | "forbidden" | "validation" | "server_error";   // the last four: only after an unmount, item 4
requestDelete(kind, id, signal?: AbortSignal): Promise<DeleteResult>            // called by delete_budget / delete_pot
onDeleteRequest(kind, handler: (id, signal?: AbortSignal) => Promise<DeleteResult>): () => void   // the page subscribes; returns its unsubscribe
```

  1. The page subscribes on mount and unsubscribes on unmount, as its tools register and unregister (`webmcp-tools.md` 2.3); one handler per kind, the latest subscription wins. A request with no handler resolves `"cancelled"` at once (nothing was shown or deleted) and the tool's message says the page's dialog is not available.
  2. **`busy`** — at once, nothing opened, when the page's `ModalSlot` (2.2) is busy: any modal of the page is open (this dialog, a form, a money modal) or a write of the page is in flight. A second call while the dialog is open (US-40 AC2) and a call while a person is editing are refused the same way, so two modals never stack. The handler checks `isBusy()` and calls `claim()` synchronously, before its first `await`, so two calls in the same tick open one dialog and the second gets `busy`.
  3. **`not_found`** — at once, no dialog and no request, when the `id` is not one of the records the page shows (`write-path.md` §6: "`cancelled`, `busy`, `not_found` before any request"). A well-formed `id` from before a reset is such an `id` (`write-path.md` 2.8).
  4. Otherwise the **same dialog** opens with that record's title. The tool's result is the dialog's **final** outcome: Go Back, Escape, the close button, the backdrop, or the page unmounting while the dialog is open **and no confirm has been sent** → `"cancelled"`; a confirm answered 204 → `"deleted"`, and the tool returns `{ deleted: true }` (`write-path.md` §6); 404 → `"not_found"`; 409 → `"conflict"` and 401 → `"unauthenticated"`, each resolved before the page reloads. A 429, 403, 415, 500 or no response leaves the dialog open with its message, as for a person (the same list as above); the tool waits for the person's next choice. **Once a confirm is sent, the result is that request's answer**: unmounting does not abort the request and does not resolve `"cancelled"` (the record may already be gone); the bus keeps the pending promise and resolves it from the answer — the codes above, or, when the dialog is no longer there to stay open in, the failure's own code by `write-path.md` 2.11 (4) (429 `"rate_limited"`, 403 `"forbidden"`, 415 `"validation"`, 500 or no response `"server_error"`).
  5. The delete that a confirm triggers is the **same function** the "…" path uses, with `X-Via: webmcp` added for a tool's request (`write-path.md` 2.11 (2)), so the request is on record (US-40 AC3) and the page changes exactly as after a person's delete.
  6. Nothing reaches the server before the confirm (R-16). The runtime hands a tool no `AbortSignal` today (H3; `webmcp-tools.md` 2.5), so the tool passes its `signal` to `requestDelete` when it has one (US-40 AC2: "Cancel or abort (`signal`) → structured `cancelled`"): a signal already aborted → `"cancelled"` at once, no dialog; a signal that aborts while the dialog is open and before a confirm → the dialog closes and the result is `"cancelled"`; an abort after the confirm is ignored, and the result is the request's answer (item 4).
  7. The result maps to the tool's answer as `write-path.md` 2.11 (4) says, plus `busy` (the build note there: `TOOL_ERROR_CODES` has neither `busy` nor `forbidden` today and gains both — `forbidden` is one of item 4's results — and `DEFAULT_TOOL_MESSAGE`, a `Record` over every code, gains their agent-read fallbacks; H13 (1)). The tool tables are `budgets.md`'s and `pots.md`'s.

**2.4 The "…" action menu** (`ActionMenu`; US-32 AC1 names the pot "…" menu; NFR-A4: "listbox or menu semantics"). A menu of actions on one record — not the one-value `Menu` of `transactions.md` 2.8, which has a current value and options. Its items are the page's: on Budgets "Edit Budget", "Delete Budget"; on Pots "Edit Pot", "Delete Pot" (the design's words).
- **Roles.** The trigger is a `<button type="button">` with `aria-haspopup="menu"`, `aria-expanded` and `aria-controls`; its accessible name is "{label}: {name}" — "Budget options: Entertainment", "Pot options: Savings" (the design names every trigger "Budget options" or "Pot options"; the record's name after it is approved, UK-Q1). The design gives the trigger `aria-haspopup="menu"` and `aria-expanded` (changelog §8e) but no roles to the popup or its items and no `aria-controls`; the spec adds them: the popup is a `role="menu"` with `aria-labelledby` the trigger; each item is a `<button type="button" role="menuitem" tabindex="-1">`. The icon (`dots-three-outline`, Phosphor, 16 px) is decorative.
- **Keys on the trigger:** Enter, Space and ArrowDown open the menu and focus the first item; ArrowUp opens it and focuses the last. **In the open menu** (focus moves onto the items): ArrowDown and ArrowUp move (no wrap, as `transactions.md` 2.8's listbox); Home and End go to the first and last item; Enter and Space activate the focused item; Escape closes and returns focus to the trigger (as the design does, changelog §8e; the arrow keys, Home, End and Tab are the spec's — the design has none); Tab and Shift+Tab close, put focus back on the trigger and let the browser move on from it (`transactions.md` 2.8's rule, so focus is never lost when the menu unmounts). Type-ahead is not required (two items).
- **Pointer:** a click on the trigger opens or closes; a click that opens the menu focuses the first item, as Enter does (in WebKit, and in Firefox on macOS, a press does not focus a button, so the items' keys need focus put on them), and a click that closes it returns focus to the trigger; a click on an item activates it; a click anywhere else closes; opening one "…" menu closes any other menu on the page.
- **Activating** an item closes the menu; Edit opens the page's form modal and Delete the dialog of 2.3, each given the trigger as the element to return focus to (2.2).
- **Look** (the design's): the icon grey-500 (5.55:1 on white; the designer's changelog §8a #2 moved it from grey-300), grey-900 on hover. Its hit area: the design widens it from the 16 px icon to 24 × 24 px with `padding: 4px; margin: -4px`, so the layout does not shift (changelog §8e); the spec makes it at least `--tap-target-min` (44 px, `app-shell.md` §4 "Minimum tap target 44 px") the same way — an invisible box around the 16 px icon, so the card's layout stays as drawn. The panel: white, `--radius-100`, padding `--spacing-150` `--spacing-250`, `var(--action-menu-width)` wide (134 px; UK-Q4), its top `--spacing-150` below the icon and its right edge on the icon's, `var(--shadow-popover)` (`transactions.md` 2.8, H11 (2); the designer's changelog §5 names this menu as one of its uses), fading in over `var(--duration-popover)` (150 ms; UK-Q4 — never `--duration-hover`, which holds the same number for colour changes) and rising `--spacing-100`, as the modal and as every `Menu` (`transactions.md` 2.8, v1.0.15), none under `prefers-reduced-motion`. Items: `--text-preset-4`, padding `--spacing-150` 0, a 1 px grey-100 divider between them; the Edit item grey-900, grey-500 on hover; the Delete item red, and on hover still full red and underlined (`text-underline-offset: 3px`, no opacity change — UK-Q5, the designer's changelog §11 and the style guide's Menu/Delete). Positioned by CSS alone (a positioned wrapper), as `transactions.md` 2.8's panels are.

**2.5 The amount field** (`AmountField`; US-15 AC2, US-22 AC2 "limits as US-15", US-25 AC2, US-26 AC2, US-31). The existing `Field` (`src/ui/Field.tsx`: label, input, helper, error, `aria-describedby`, `aria-invalid`, a polite live region) with a leading "$". `Field` gains four props (a build note): a leading adornment, a `placeholder`, an `inputMode` and a `defaultValue` (the input stays uncontrolled, `Field.tsx`'s rule since T-06; an edit form's pre-fill is its `defaultValue`).
- **The input** is `type="text"` with `inputMode="decimal"`, `autocomplete="off"` and `maxLength` 32 (the longest text that reads as an amount, `$999,999,999.99`, has 15 characters; 32 leaves room for spaces, a sign and leading zeros, so such an input still reaches its message, and bounds the parse) — not the design's `type="number"`, which cannot hold "$" or "," (2.11). The "$" is drawn inside the field's start edge, `--spacing-250` from it, `--text-preset-4`, grey-500, and is `aria-hidden` (the label names the field) — as the design draws it: the modal's "$" is grey-500 and `aria-hidden` (`Finance App.dc.html`, the amount field; the designer's changelog §8a #4 moved it from beige-500), and the style guide's "Field With Prefix" sample is grey-500 too (changelog §13d). The placeholder is the page's (the design: "e.g. 2000"), grey-500 (the designer's changelog §8a #3, the design's `input::placeholder` rule; H11 (6)).
- **What it accepts** — the spec's reading of US-15 AC2 ("an optional leading `$` and thousands separators, which are stripped"; R-17), one pure function `parseAmountInput(text)` in `src/shared/money.ts` (which has formatters only today), returning integer cents or one of `write-path.md` 2.7's codes. In this order: (1) surrounding white space is trimmed; nothing left → `required`; (2) one leading `-` is noted and removed, then one leading `$`; (3) the rest must be ASCII digits, either plain (`1234`) or grouped by commas in threes after a first group of one to three digits that does not start with `0` (`1,234`, `12,345,678`; `0,500` and `01,234` are refused, since a person who writes a decimal comma means half a dollar by `0,500`), optionally followed by `.` and one or two digits, or `.` and one or two digits alone (`.5`), with at least one digit → otherwise `invalid_format`; (4) the value in cents is computed from the digits as an integer (no floating point, so a 20-digit input loses nothing); a `-` or a value of 0 → `too_small`; more than 99,999,999,999 → `too_large`; (5) otherwise the cents. 4.1 lists the worked examples. Reading a comma only as a thousands separator in groups of three — where US-15 AC2 says only that separators "are stripped" — is a choice that story leaves open, so it was **UK-Q8**, answered (a) by the owner: strict, as written. The messages are `write-path.md` 2.7's table ("Can't be empty", "Enter an amount with up to two decimals", "Amount must be greater than 0", "Amount is too large"); the page adds its own rules after these (Pots' `exceeds_balance`, `exceeds_total`). The design uses the same copy for an amount not above 0 since the designer's changelog §15a ("Amount must be greater than 0", replacing §13a's "Enter an amount above 0").
- **When a message shows and when it goes** (US-31 AC1, AC2) — **Release 1's rule, unchanged** (**UK-Q9**, answered (a) by the owner on 2026-10-05). A message **appears** on blur once the field has been touched (focused and left) and on submit, when every field is checked and the first invalid field of the form gets focus (US-31 AC1: "on submit and on blur after first interaction"; `auth.md`, "Timing (US-31 AC1)": "a field validates on blur once it has been touched (focused and left), and every field validates on submit"). Once shown, it **stays until the field is checked again** — at its next blur or at submit — when it is replaced by the new result or removed. **Typing does not clear a message and never shows one.** (US-25 AC2's "Given Current Balance is $0.00, the field shows that message on any input" is read under this rule for its timing only: whenever the field is checked, at its blur or at submit — not at each keystroke. Which message a check shows follows the order above: at a $0.00 balance an empty field still shows "Can't be empty", a malformed one "Enter an amount with up to two decimals", 0 or a negative amount "Amount must be greater than 0" and one above the largest "Amount is too large", and every value that passes these checks shows "Amount exceeds your current balance". Whether US-25 AC2 means that message also replaces these four is not this spec's to decide: `pots.md` must state it for its field, and ask the owner if it reads the criterion otherwise (§7's table gives US-25 AC2 to `pots.md`).) That is what Release 1's login and sign-up forms do (`Field` is uncontrolled and holds no rule of its own; `LoginForm` and `SignupForm` check a field in its `onBlur` and every field on submit), so every form in the app keeps one rule. The design first checked on submit only and cleared a field's message as soon as the person typed in it (the designer's changelog §13a, and §16a as first written); the owner kept Release 1's rule and recorded that clearing as tech debt **TD-24** (`tech-debt.md`), fixed after all releases are finished. The designer has since redrawn §16a, now titled "Release 1 behaviour" (re-read 2026-10-05 for v0.8.3 and v0.8.4): a message stays while the person types (`updateModal()` keeps the errors), and `blurField()` re-checks the Pot Name and amount fields on blur — but only a field that already shows a message (it returns at once when the field has none). So the difference left is the blur check of a field that shows no message: the design gives it none on blur — on its first blur, or on a later one after a blur found it valid — until submit, where Release 1's rule shows it (2.11). The rule holds for every field of these forms — the amount fields here, the select fields of 2.6 (where a choice is not a check, and a blur is focus leaving the field as a whole: a `focusout` whose `relatedTarget` is outside the wrapper holding the trigger and its listbox — opening the menu, moving the highlight, choosing by key or by click, Escape and closing the menu by a click on its trigger are not a blur) and `pots.md`'s Pot Name. A server `validation` answer puts each `issues` entry under its field the same way (`write-path.md` §3); it too stays until the field is checked again. The message is linked by `aria-describedby` and announced by `Field`'s live region (NFR-A5); when a check finds the field valid, the field loses `aria-invalid` and the message, and the region is emptied.
- **Pre-filled** (an edit form; US-16 AC1, US-23 AC1): `Field`'s `defaultValue` is `formatAmountInput(cents)` — whole dollars as digits only ("750"), otherwise two decimals ("75.50"); no "$" and no separators, so every seed value shows as the design shows it and `parseAmountInput` reads it back to the same cents (4.1).
- **Look:** `Field`'s (Release 1, `Field.module.css`): beige-500 border, grey-500 on hover, grey-900 when focused, plus the focus ring; the error in red under the field. Its box is 47 px tall on every form — **UK-Q7**, answered (a) by the owner — as the design draws these forms' boxes since the designer's changelog §13c (form fields 47 px, "as in `Field.module.css`", the login and sign-up fields included).

**2.6 The select field — Theme, and Budget Category** (`SelectField`; US-15 AC1, US-16 AC1, US-22 AC1, US-23 AC1, US-32 AC1, NFR-A4). A form field built on `transactions.md` 2.8's `Menu` (listbox semantics, its keys, its `aria-disabled` options, its focus return); this section adds the label, the error wiring (`transactions.md` 2.8: "a form adds its own label and error wiring, US-31") and the option rows. The page passes the options and which are used. What `SelectField` needs from `Menu` beyond `transactions.md` 2.8 is a change to `Menu` (§6, H13 (1)), drawn only through options a use passes, so the Transactions menus stay as `transactions.md` 2.8 draws them: a panel as wide as the trigger (`transactions.md` 2.8 gives each use its own width); an option's content beyond its label (the swatch, "Already used", the check icon); and the pointer's focus rules of the last bullet below (a click that closes the menu leaves focus on the trigger, as `transactions.md` 2.8 asks of the keys). Escape stopping there (2.2) holds for every use: no Transactions menu sits in a modal, so nothing on that page changes. The panel's `var(--duration-popover)` fade is the `Menu`'s own for every use as well (`transactions.md` 2.8, v1.0.15, the designer's changelog §10), so `SelectField` inherits it and passes nothing for it. The pointer's focus rules would change where focus is after a click on a Transactions menu, so they too are an option `SelectField` passes, and the Approved behaviour of `transactions.md` 2.8 stays as it is (a Transactions menu takes them only through an amendment of that spec, which the owner approves by merging).
- **Label and name.** A visible label above the trigger (`--text-preset-5-bold`, grey-500, as `Field`'s): "Theme", "Budget Category" (the design's). The trigger's accessible name is `transactions.md` 2.8's "{label}: {current}" — "Theme: Green", "Budget Category: Groceries"; with no value (no free option, below) it is the label alone, "Budget Category", never "Budget Category: ". With an error, the trigger has `aria-invalid="true"` and `aria-describedby` the message, shown under it like `Field`'s. The trigger's `aria-haspopup="listbox"` and `aria-expanded` are the design's too (changelog §8e); the design's options are plain buttons with no roles and no arrow keys, which `transactions.md` 2.8's `Menu` adds.
- **The trigger** looks like an input: `Field`'s box, border and hover, the current value (and its swatch, 2.10, for a theme) on the left, a 16 px caret-down icon on the right.
- **The options** fill the field's width, in a panel whose top is `--spacing-100` under the trigger's box — **UK-Q7**, answered (a), and the design's since the designer's changelog §13c (the trigger and its panel share a `position: relative` wrapper and the panel has `top: calc(100% + 8px)`; in code `top: calc(100% + var(--spacing-100))`) — drawn as 2.4's (white, `--radius-100`, padding `--spacing-150` `--spacing-250`, `var(--shadow-popover)`, the same `var(--duration-popover)` fade, the `Menu`'s own): `--text-preset-4`, padding `--spacing-150` 0, a 1 px grey-100 divider; at most `var(--field-menu-max-height)` tall (300 px; UK-Q4 — never `--sidebar-width`), then scrolling. The current option is bold and `aria-selected` (`transactions.md` 2.8); the Theme list also draws a green `check-circle` icon at its end (decorative; the design's). A theme option starts with its swatch.
- **"Already used."** An option another record holds — another budget's category or theme on Budgets, another pot's theme on Pots (`write-path.md` 4.1: a budget and a pot may share a theme) — is shown, has `aria-disabled="true"`, is skipped by the arrow keys and cannot be chosen (`transactions.md` 2.8); its label is grey-500, its swatch — the swatch alone — at `var(--opacity-unavailable)` (0.25; UK-Q4, the designer's changelog §12a), it has no hover (US-34 AC2), and the text "Already used" (`--text-preset-5`, grey-500; US-15 AC1, the design) sits at its end, inside the option, so a screen reader reads "Bills, Already used" and the state is never told by colour alone (NFR-A7). **The record being edited never counts against itself** (US-16 AC1, US-23 AC1, R-18). With the seed, 4.2 lists what each form disables.
- **No free option.** When every option is used (all ten categories have a budget; fifteen pots hold the fifteen themes), the trigger shows no value and the page shows its message under the field (Budgets: `COPY.budgetCategoriesUsed`, "All categories already have a budget"); the page decides whether the form opens at all.
- **A server `taken`** (another tab used the value meanwhile) shows "Already used" under the field (`write-path.md` 2.7, §9 Q5) and the option list is refreshed from the page's data.
- **A choice is not a check** (2.5's rule, UK-Q9 (a)). **A select field's blur is focus leaving the field as a whole:** a `focusout` whose `relatedTarget` is outside the wrapper holding the trigger and its listbox (the `position: relative` wrapper above; no `relatedTarget`, when focus goes nowhere, is outside too). The trigger's own blur is not the field's: while the menu is open the listbox holds focus (`transactions.md` 2.8: `aria-activedescendant` "on the listbox, which holds focus while the menu is open"). By the keyboard, a choice (Enter, Space), Escape and Tab return focus to the trigger first (`transactions.md` 2.8). By the pointer, `transactions.md` 2.8 says only that a click on the trigger opens or closes the menu and a click on an option chooses it, with no focus return; so `Menu` gains two things, as an option `SelectField` passes (§6, H13 (1)): while the menu is open, a press on the trigger or on an option does not move focus (its `mousedown` default is prevented there — in WebKit, and in Firefox on macOS, pressing a button does not focus it, so the listbox would otherwise lose focus to nothing, a `focusout` with no `relatedTarget`), and a click on an option, or on the trigger when it closes the menu, returns focus to the trigger, as Enter, Space and Escape do. So opening the menu, moving the highlight, choosing by key or by click, Escape and closing the menu by a click on its trigger are not a blur; Tab or Shift+Tab from the open menu is one once the browser moves focus on from the trigger, and so is a click outside that moves focus off the field. The field is touched (2.5: "focused and left") at its first such blur. **What a select field's check covers:** no value (the page's message, as on submit), and a value the page's data shows another record holding ("Already used", the `taken` message — after a server `taken` the option list is refreshed, above, so the taken value is such a value); a `taken` therefore stays until the person chooses a free option and the field is checked again. A select field's message — no value on submit, or a server `taken` — stays when the person chooses an option, a valid one included, and opening or closing the menu neither shows nor clears it. The field is checked again at its next blur or at submit, and the message is then replaced by the new result or removed, with `aria-invalid`.
