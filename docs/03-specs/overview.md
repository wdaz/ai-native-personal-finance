## 1. Purpose
Everything at a glance, computed by the backend from the current dataset, with links into each page. Read-only.

## 2. Behaviour
2.1 `app/(app)/overview/page.tsx` is a server component that calls `getOverview(db, clock)` from `src/server/overview.ts` directly (no HTTP self-call). The same function backs `GET /api/overview` for tools and tests. Title "Overview".
2.2 Stat cards: "Current Balance" (grey-900 card, white text), "Income", "Expenses" (white cards); values `$4,836.00`, `$3,814.25`, `$1,700.50`.
2.3 Pots card: title "Pots", link "See Details ›" → `/pots`; left tile: jar icon, "Total Saved", `$920.00` (sum of **all** pots); right: the first four pots in creation order as "name / `$159.00`" in a 2×2 grid, each with a 4 px bar in its theme colour. With 1–3 pots the grid keeps its cells and the empty cells stay blank.
2.4 Transactions card: title "Transactions", link "View All ›" → `/transactions`; five rows: avatar (40 px round, `alt` = name), name (preset 4 bold), amount (green `+$75.50` if positive, grey-900 `-$55.50` if negative, preset 4 bold), date (`19 Aug 2026`, preset 5 grey-500); 1 px grey-100 dividers.
2.5 Budgets card: title "Budgets", link "See Details ›" → `/budgets`; donut (§4.4) with centre `$338.00` (preset 1) and "of $975.00 limit" (preset 5 grey-500); legend: first four budgets in creation order, each a 4 px theme bar, category (preset 5 grey-500) and maximum `$50.00` (preset 4 bold). Totals include all budgets.
2.6 Recurring Bills card: title "Recurring Bills", link "See Details ›" → `/recurring-bills`; three beige-100 rows with a 4 px left border: "Paid Bills" (green) `$190.00`, "Total Upcoming" (yellow) `$194.98`, "Due Soon" (cyan) `$59.98`.
2.7 Empty states: no pots → tile `$0.00`, grid replaced by text "No pots yet" and link "Add a pot" → `/pots`; no budgets → single beige-100 ring (v1.3; was grey-100; §4.4), centre `$0.00` / "of $0.00 limit", legend replaced by "No budgets yet" + "Add a budget" → `/budgets`; fewer than five transactions → available rows; none → "No transactions yet"; no recurring → three rows at `$0.00`.
2.8 Error: if `getOverview` throws, the page renders inside the shell a single card (in place of the grid) "Couldn't load your overview" with a "Retry" button (`router.refresh()`); the error is logged with the request id.

Up to v1.2 this paragraph named no radius (the code's 108 px came from v0.2 S-13); it now names 96 px. *Build note* (Release 1's code, `develop`): in `donut-geometry.ts`, `DONUT_RADIUS` is today derived as `DONUT_SIZE / 2 - DONUT_STROKE / 2` (= 108, the flush ring); it becomes the design's number, `96`, written as such (the 12 px clearance is the design's, not something the canvas implies), and the comment "flush with the canvas edge" goes. `DONUT_SIZE` (240) and `DONUT_STROKE` (24) do not change, so neither do the SVG's `width` and `height` (240), its `viewBox` (`0 0 240 240`), the centre (120, 120), `Donut.module.css`'s 240 × 240 px `.wrapper` or the outer stroke width: the box stays, the ring moves inwards. What follows from `DONUT_RADIUS` with no edit of its own: `donutSegments`' circumference `2 * Math.PI * DONUT_RADIUS` (about 678.58 → about 603.19), and with it every segment's `stroke-dasharray` (length and gap) and `stroke-dashoffset`, each 96/108 = 8/9 of today's, the shares and angles unchanged; the `r` of the ring under the segments and of each outer segment (`r={DONUT_RADIUS}`); and `Donut.tsx`'s `INNER_SCALE` (`INNER_RADIUS / DONUT_RADIUS`, which scales the inner segments' dash values). `INNER_RADIUS` does need an edit of its own in `Donut.tsx`: it is `DONUT_RADIUS - DONUT_STROKE / 2 - 4` today (the `4` is half of the 8 px inner stroke; 92 px), and with H18's 12 px inner stroke the `- 4` becomes `- INNER_STROKE / 2`, so it is 96 − 12 − 6 = **78** (changing only `DONUT_RADIUS` and `INNER_STROKE` would leave 80), and `INNER_SCALE` = 78/96 = 0.8125. The comments in `Donut.tsx` and `Donut.module.css` that name 8 px, 25 % or "flush with the canvas edge" change with it. `tests/unit/ui/overview/donut-geometry.test.ts` computes its circumference from the exported `DONUT_RADIUS`, so it passes unchanged and does not pin the radius; §7's `Donut` row does. The design animates the segments of this same donut on both screens (0.4 s). That animation is S45-4 (`budgets.md` §9 BU-Q7, `pots.md` PO-Q6; pull requests #98 and #97), answered by the owner on 2026-10-06 with the recommended option (a); the designer is told and records it in the changelog (governance v1.10). Under (a) each segment's `stroke-dasharray` and `stroke-dashoffset` move with a CSS transition over `--duration-progress` (400 ms; a token `budgets.md` 2.3 introduces — `tokens.css` on `develop` has none yet — its name to be confirmed in the designer's changelog), and not at all under `prefers-reduced-motion: reduce`. The rule is the component's own, added by the first Budgets build task (`budgets.md` 2.3), so it holds on Overview too; Overview's figures do not change while the page is open, so nothing moves there. The inner ring's, the empty ring's and the outer radius's change is a hand-off to hotfix 2 (`release-2-handoffs.md` H18); the transition is not: it comes with the first Budgets build task.
4.5 Card links are `<a>` elements with visible focus; avatars resolve to `/avatars/<key>.jpg` where `key` is the seed's basename (`emma-richardson`); files copied to `public/avatars/` in T-01.
