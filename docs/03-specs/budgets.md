## 1. Purpose

The user sees every budget of the demo account — one per spending category — with what was spent against it in the current month (August 2026), what remains, a bar that fills as the money goes, and the three latest transactions of its category, beside a donut and a list that sum all budgets up. The user creates a budget, changes its category, maximum or theme, and deletes it, in the modal and with the controls `ui-kit.md` specifies; "See All" opens the Transactions page filtered to the budget's category. Budgets never touch the balance (`write-path.md` 2.8). An AI agent reads the same budgets with `list_budgets` and changes them with `add_budget`, `edit_budget` and `delete_budget`, through the same routes, with the deletion confirmed by the person on screen.

## 2. Behaviour

**2.1 Where things run** (ADR-0001: a spec states which components are client components).
- **Server:** `app/(app)/budgets/page.tsx` is an async Server Component. It calls `getBudgets(getDb(), fixedClock(BUSINESS_TODAY))` from `src/server/budgets.ts` **directly** (no HTTP self-call, the Overview pattern, `overview.md` 2.1) and renders either the page's client container with the answer (below) or, when the call throws, the error state of 2.12. The same `getBudgets` backs `GET /api/budgets` (2.11).
- **Client** (`"use client"`): `BudgetsView` (`app/(app)/budgets/BudgetsView.tsx`, in `app/` because it joins `src/ui` and `src/webmcp`'s bus, `ui-kit.md` 2.3) is the page's client container: it receives the `BudgetsDto` as a prop and renders the page header with its primary action (`ui-kit.md` 2.8), the two columns of 2.2, the modal (`ui-kit.md` 2.2) and the notice (`ui-kit.md` 2.9); it provides the page's `ModalSlot` (`ui-kit.md` 2.2), owns the page's write function (2.9), subscribes the page to the delete bus (`ui-kit.md` 2.3) and refreshes the page after a write. Under it, in `src/ui/budgets/`: `SpendingSummary` (2.3), `BudgetCard` (2.4), `BudgetBar` (2.4), `LatestSpending` (2.5), `BudgetForm` (2.6, 2.7), `BudgetsEmpty` (2.12) and `BudgetsError` (2.12; it calls `router.refresh()`); the shared parts are `ui-kit.md`'s and `transactions.md` 2.9's `TruncatedText`, and the donut is the app's one `Donut` (`src/ui/overview/Donut.tsx`, 2.3; drawn as §9 BU-Q3 decides). `app/(app)/budgets/layout.tsx` renders `children` and `<BudgetsTools />` (`src/webmcp/tools/`, the Overview pattern, `webmcp-tools.md` 2.3; it also refreshes the page after an agent's add or edit, 2.13).
- **Domain** (pure, `src/domain/budgets.ts`, today `budgetSpent` only): `latestSpending(category, transactions, 3)` (the name `data-model.md`'s "Derived values" gives it), `budgetRemaining(maximum, spent)` and `budgetsSummary(input, clock)`, which returns the budgets in creation order (`seq`), each with its `spent`, `remaining` and `latest`, and the totals `spent` and `limit` over all budgets — the shape `overviewSummary` already gives Overview (`src/domain/overview.ts`), so the two pages read the same numbers (US-20 AC1). **Shared** (`src/shared`): the request schemas and DTO schemas of 2.10–2.11 (`schemas.ts`), `budgetFillPercent(spent, maximum)` (4.1; the bar is a `ui` component, which may import only `ui` and `shared`), `COPY` entries (2.17).
- **The page performs no money arithmetic** (as `overview.md` 4.1): every amount comes from the domain through `getBudgets`; the one number the client computes is the bar's width, with the shared, unit-tested `budgetFillPercent`.

On the right, filling the rest (`min-width: 0`), the budget cards (2.4) in a column, `--spacing-300` apart.

Inside the summary card the donut and the title-and-list sit **side by side in a row** (each half the width, `--spacing-400` apart) or one above the other in a column (the designer's changelog §14: "On Budgets and Recurring Bills the summary card lays out its parts in a row, as on tablet. **2.9 After a write — the page's write function** (`write-path.md` §3, `ui-kit.md` 2.3, 2.7).
- `BudgetsView` owns one write function used by the add form, the edit form and the delete dialog: it counts its requests in and out of the `ModalSlot` (`trackWrite`, `ui-kit.md` 2.2), sends through `apiSend` (`write-path.md` 2.11 (2); with `X-Via: webmcp` only when the delete was a tool's, `ui-kit.md` 2.3 item 5) and maps the answer.
- **Success** (201, 200, 204): the modal closes (focus as `ui-kit.md` 2.2 says: the header button after an add, the card's "…" button after an edit, `<main>` after a delete), any "no longer exists" notice is cleared (`ui-kit.md` 2.9), and the page calls `router.refresh()` inside `startTransition`, so the Server Component reads the database again and the cards, the summary and the "Already used" options show the new state **with no reload** (US-15 AC3, US-16 AC2, US-17 AC2). While that refresh is pending the cards' column carries `aria-busy="true"`; the previous state stays until the new one arrives (no skeleton). Overview reads the database on each request — its page calls `getOverview` directly (`overview.md` 2.1) and renders dynamically, as every page under ADR-0006's per-request nonce does — so its Budgets card shows the change the next time it is opened (US-15 AC3, US-16 AC2, US-17 AC2: "and Overview").
- **A field error** (400 `validation`): each `issues` entry under its field (`ui-kit.md` 2.5, 2.6); a `taken` on `category` or `theme` shows "Already used" under it and the page refreshes its data, so the option list marks the value as used (`ui-kit.md` 2.6). A `validation` with a path the form has no field for (`[]`, `id`) is shown as the server error message in the error area (it cannot come from this form).
- **404** (an edit or a delete of a budget deleted meanwhile): the modal closes with `<main>` named for focus, the notice "This budget no longer exists" (`ui-kit.md` 2.9), and the list refreshes (US-17 AC3).
- **409, 401, 429, 403, 415, 500, no answer:** as `ui-kit.md` 2.3 and 2.7 say (`write-path.md` §3).

**2.10 The write routes** (`write-path.md` 2.1's three Budgets rows; every rule of `write-path.md` 2.2–2.12 applies and is not repeated: the cross-site and content-type checks in the proxy, the rate limit, validation, one transaction, the threshold check, the answers, `no-store`, the via log). The handlers are `guardedWrite` handlers (`write-path.md` §6) in `app/api/budgets/route.ts` (`POST`, beside the `GET` of 2.11) and `app/api/budgets/[id]/route.ts` (`PATCH`, `DELETE`).

| Request | Body (`src/shared/schemas.ts`; unknown keys stripped, `write-path.md` 2.7) | Success | Business rules (step 7 of `write-path.md` 2.2, inside the transaction) |
|---|---|---|---|
| `POST /api/budgets` | `BudgetCreateSchema`: `category` (one of the ten), `maximum` (integer cents, 1 ≤ x ≤ 99,999,999,999), `theme` (one of the fifteen) — all required | **201** `{ budget: BudgetItemDto }` (2.11) | `category` held by another budget → `taken` on `category`; `theme` held by another budget → `taken` on `theme` (both are reported when both apply) |
| `PATCH /api/budgets/:id` | `BudgetEditSchema`: the same three fields, **all required**, as the edit form sends them (2.7) — an absent or `null` field is `required` (`write-path.md` 2.7's table), and `{}` is `required` on each of the three (`write-path.md` 4.4); partial edits are out of scope (§8), as on Pots (`pots.md`, PR #97) | **200** `{ budget: BudgetItemDto }` | no budget with that `id` → **404**; a `category` or `theme` held by **another** budget → `taken` (the budget's own values never count against it, R-18) |
| `DELETE /api/budgets/:id` | none | **204** | no budget with that `id` → **404** |

- **The limits** (H1; `write-path.md` 4.1, NFR-S3): a budget has no name; its category and theme come from their enums; at most ten budgets exist, one per category — the unique `category` makes an eleventh impossible, so no separate count check exists: posting a category that already has a budget is `taken`. A budget's theme is unique among budgets; a pot may share it.
- **The unique constraints** `Budget.category` and `Budget.theme` (`data-model.md`) are the last line of defence: a violation caught from the database maps to the same 400 `taken` on that field (`write-path.md` 2.8), so two requests racing for the same category cannot both succeed.
- **The new budget's `seq`** is assigned by the database (`data-model.md` v1.1), so it is listed last (US-14 AC4). An edit keeps `seq`.
- **The balance is never written** by these routes (US-04 AC3; H6). A budget write is checked by the storage threshold like any write (`write-path.md` 2.9), and a reset answers 409.
- **The answer's shape.** `write-path.md` 2.2 step 9 answers "with the record" and leaves the shape to the page spec; a write's record is wrapped under its noun, `{ budget }`, as `pots.md` 2.12 wraps `{ pot }` (its deposit and withdrawal answer `{ pot, balance }`, which needs the wrapper), so both pages' writes answer one way. The schemas are named noun first, as `src/shared/schemas.ts` names its own (`LoginSchema`, `AdminResetSchema`, `OverviewDtoSchema`), with the tools' verbs: `BudgetCreateSchema`, `BudgetEditSchema` (`edit_budget`, "Edit Budget").
- **The answer's DTO is computed after the commit** from the database, with the same `budgetsSummary` as `GET`, so the budget comes back with its August spent, remaining and latest three (US-15 AC3: "computed immediately").

**2.11 `GET /api/budgets`** (the route for the tool and the tests; the page calls `getBudgets` directly). It takes no parameters (any query is ignored), calls `getBudgets(getDb(), fixedClock(BUSINESS_TODAY))` and answers 200 with a `BudgetsDto` (a `z.strictObject`, so a leaked field fails an API test) and `Cache-Control: no-store`; 401 `unauthenticated` from the proxy; 500 `server_error` `{ message: "The budgets are unavailable" }` after a `console.error("GET /api/budgets failed", error)`, also with `no-store` (the route sets it itself, as `transactions.md` 2.13). It never changes data (`write-path.md` 2.1, 7.2).

```
BudgetItemDto = {
  id: uuid,
  category: one of the ten,
  theme: one of the fifteen,
  maximum: integer cents ≥ 1,
  spent: integer cents ≥ 0,        // budgetSpent: August 2026, negative rows only (R-11)
  remaining: integer cents ≥ 0,    // max(0, maximum − spent)
  latest: { id: uuid, name: string (1–60), avatar: key, date: UTC ISO-8601, amount: integer cents (signed) }[]   // 0–3, US-11 Latest
}
BudgetsDto = {
  items: BudgetItemDto[],   // 0–10, creation order (seq)
  spent: integer cents ≥ 0, // Σ items.spent
  limit: integer cents ≥ 0  // Σ items.maximum
}
```

The item carries what the card shows plus the ids (US-39 AC2: "including ids") and the avatar key; it has no `seq` (the order of `items` is the order) and no bar percentage (the client's, 2.1). `spent` and `limit` equal Overview's `budgets.spent` and `budgets.limit` for the same data (US-20 AC1: "totals match the Overview card"; 4.2).

**2.12 Loading, empty, error.**
- **Loading.** The page is rendered on the server with its data; there is no loading route and no skeleton (as Transactions). After a write, 2.9's refresh marks the cards' column `aria-busy="true"` until the new state arrives.
- **No budgets** (US-14 AC3, US-20 AC2; the `empty-budgets` and `empty-all` variants). The Spending Summary card shows the empty donut ("$0.00", "of $0.00 limit") and its title with no list (2.3). In place of the cards the page shows an empty state that **the design does not draw**: what it holds, and whether it repeats the "Add New Budget" action that US-14 AC3 names, is **§9 BU-Q2** (= S45-2, asked with `pots.md` PO-Q3); the recommended answer (a) is one white card with "No budgets yet" (`COPY.budgetsEmpty`, the approved Overview text), centred, in 14 px body text in mid-grey (`--text-preset-4`, grey-500), its look confirmed by the designer in the changelog. Whatever the answer, the header's "+ Add New Budget" stays.
- **Error.** If `getBudgets` throws, the page logs `Budgets: getBudgets failed requestId=<id>` (the id from `x-request-id`) and renders, under the page header, one white card in place of both columns: "Couldn't load your budgets" (a new string, **§9 BU-Q1** #1) and a "Retry" button (`COPY.retry`; `router.refresh()`) — the Overview pattern (`overview.md` 2.8), drawn as `OverviewError` is. No `error.tsx`: any other error falls to Next's default handling. **Whether the header keeps "+ Add New Budget" in this state is §9 BU-Q6** (= S45-3, asked with `pots.md` PO-Q9): `ui-kit.md` §3 (merged) says the header button is "always on Budgets and Pots", while the form has no data to check a new budget's category and theme against. Under the recommended answer (a) the header has no primary action in this state only, and `ui-kit.md` §3's row gains "except the page's error state" — a one-line amendment in its own pull request, shared with `pots.md` (H15 (6)); under (b) the button stays and its form marks nothing "Already used", so a used category or theme comes back as the server's `taken` (2.9).
- **Notice.** The "no longer exists" notice of `ui-kit.md` 2.9 sits under the page header and above both columns, at the content's full width (in one column, above the summary card); its live region is in the page from the start, empty (`ui-kit.md` 2.9).
- **Session ended.** A page request without a session meets the proxy's redirect to `/login?next=/budgets`; the API and the tools answer 401 `unauthenticated` (US-39 AC4); a write's 401 reloads the page (`write-path.md` §3).

- **Same rules as the UI** (US-40 AC1): the tools validate with the same shared schemas before any request and the server validates again; a refusal is a `validation` tool error with the server's `issues` (`taken`, `too_small`, …), never thrown (NFR-W6). The schemas list the enums and bounds, so the input schema shows an agent the allowed categories, themes and the cents range (`toolInputJsonSchema`).
- **Visible at once** (US-40 AC3: "the same state as a user action"). A tool's `execute` is a module-level function (`PAGE_TOOLS`, `src/webmcp/tools/registry.ts`) and cannot call a React hook, so the refresh is added where a hook runs: `BudgetsTools` (the client component the layout renders, as `OverviewTools` is) calls `useRouter()` and builds, once per router (`useMemo`), the list it hands to `WebMcpTools` — `PAGE_TOOLS.budgets` with the `execute` of `add_budget` and `edit_budget` wrapped so that, after a result without `isError`, it calls `router.refresh()` and returns the result unchanged; `list_budgets` and `delete_budget` are passed as they are. The registry keeps the unwrapped definitions, so `tests/unit/webmcp/registry.test.ts` checks the same names, schemas and annotations; the memoised list keeps `WebMcpTools`' effect (`[tools]`) from registering again on every render. The refresh makes the Server Component read `getBudgets` again and `BudgetsView` renders the new props, as after its own write; it runs outside `BudgetsView`'s transition, so the cards' column is not marked `aria-busy` for an agent's write (2.9's `aria-busy` is the page's own writes'). This is the mechanism `pots.md` 2.8 states for Pots (`PotsTools`, `router.refresh()` after a tool's 2xx); `src/webmcp/bus.ts` stays as `ui-kit.md` 2.3 defines it, with no `notifyWrite`/`onWrite` (v0.2 had added them, which `ui-kit.md` 2.3 and §6 do not define; cross-spec review B1). `delete_budget` needs none of this: it goes through the page's own dialog and write function (`ui-kit.md` 2.3 item 5). Until the refresh has landed, the page does not show a budget an agent has just added, so a `delete_budget` of its id in that moment answers `not_found` (`ui-kit.md` 2.3: an id the page does not show), with no dialog and no request; once the card is shown, the same call opens the dialog. A tool write is not counted by the page's `ModalSlot` (it is not the page's write function): a person's form stays open while an agent adds a budget, and the refresh updates its "Already used" options; a person's submit that then collides answers `taken` (2.9).
- **On record:** every call sends `X-Via: webmcp` and is logged with its `method` (`write-path.md` 2.12; US-40 AC3).
- **`delete_budget`** returns `{ deleted: true }`, or one of `ui-kit.md` 2.3's other `DeleteResult` codes, mapped as its item 7 says: `cancelled`, `busy`, `not_found` before any request (for an id the page does not show); after a confirm `not_found` (404), `conflict` (409), `unauthenticated` (401), and, when the page unmounted meanwhile, `rate_limited`, `forbidden`, `validation`, `server_error` (`ui-kit.md` 2.3 item 4) — the list `pots.md` 2.13 gives `delete_pot`; nothing reaches the server before the person confirms (R-16, NFR-W5). The runtime hands no `AbortSignal` today, so "cancel" is driven through the dialog (H3).
- **Safety rule** (NFR-S7, R-24): transaction names are returned as JSON strings, never as HTML; a budget has no name of its own; the registry test asserts `consequentialHint` on the three mutating tools (the polyfill's `getTools()` drops it, H3) and `untrustedContentHint` on `list_budgets`, `add_budget` and `edit_budget`.

## 5. Data

Reads `Budget` (`id`, `seq`, `category`, `maximum`, `theme`) and `Transaction` (`id`, `name`, `avatar`, `category`, `date`, `amount`); writes `Budget` only (create, update `category`/`maximum`/`theme`, delete) and, through `write-path.md`, the write-limiter rows and, on a threshold reset, `ResetLog`. Never `Balance`, `Pot` or `Transaction` (US-04 AC3). The source of truth is the database; `data.json` is only the seed (US-36 AC2). Money is `BigInt` in the database and integer cents in every body and DTO; it becomes text only at the edge (`formatMoney`, `formatSignedMoney`). Spent, remaining and the latest three are computed on every read, never stored (`data-model.md`: "spent/remaining are computed, not stored").

BU-Q1 = S45-1 = PO-Q1; BU-Q2 = S45-2 = PO-Q3; BU-Q3 = S45-5 (the donut's look; Budgets only); BU-Q4 = S45-6 = PO-Q10; BU-Q5 = S45-7 = PO-Q11; BU-Q6 = S45-3 = PO-Q9; BU-Q7 = S45-4 = PO-Q6 (it also holds the donut's animation, which v0.3 asked as BU-Q3's third part); BU-Q8 = S45-8 = PO-Q7. S45-9 to S45-12 are asked only in `pots.md` (PO-Q8, PO-Q2, PO-Q4, PO-Q5); S45-9 (PO-Q8) also covers this page's two-decimal donut centre (2.3, 2.16), which this spec does not ask again.

**Who decides** is under each question (governance v1.10). The owner: BU-Q1, BU-Q2, BU-Q3, BU-Q6 and BU-Q8 — new texts, the reading of an acceptance criterion, or an amendment of an approved document; where one has a design part, the owner takes it to the designer, whose changelog entry fixes the look. The designer, through the owner: BU-Q4, BU-Q5 and BU-Q7 — the design itself; the designer's changelog entry is the answer, and this spec then applies it, citing the section. Each can be answered by its letter. Until it is, this spec is written to the recommended answer and says what another answer changes.

**BU-Q1** (= S45-1; same as `pots.md` PO-Q1)

*Question:* May Budgets and Pots use six new texts that no approved list has yet? (1) "Couldn't load your budgets" and (2) "Couldn't load your pots" - seen, on each page's error card with Retry; (3) "See All {category} transactions" - heard, the name a screen reader says for each budget card's "See All" link; (4) "Add Money to {name}" and (5) "Withdraw from {name}" - heard, the names of each pot card's two money buttons; (6) "1 character left" - seen, the Pot Name counter at one character (the design writes "1 characters left"). Without 1-2 the error cards have no text; without 3-5 every card's links/buttons sound the same to a screen reader or voice-control user.

- (a) Approve all six as written.
- (b) Change the wording of some (say which numbers and the new words).
- (c) Approve only the seen texts (1, 2, 6); keep the design's plain names "See All", "Add Money" and "Withdraw" for 3-5.

*Recommendation:* (a). The heard names follow NFR-A1 (WCAG 2.4.6, 2.5.3) and the owner's own UK-Q1 precedent ("Budget options: {name}"); #1-2 follow the approved Overview/Transactions error pattern; #6 follows the approved message table's rule that a count of 1 is singular. One answer approves each pattern for both pages.

Who decides: the owner

**BU-Q2** (= S45-2; same as `pots.md` PO-Q3)

*Question:* What does the Budgets page show in place of its cards when there are no budgets, and the Pots page in place of its grid when there are no pots? US-14 AC3 and US-21 AC2 ask for 'an empty state with Add New Budget / Add New Pot'; the design draws neither (the area is just empty). Each page header already has its '+ Add New ...' button whenever the data has loaded, and the approved texts 'No budgets yet' / 'No pots yet' exist (Overview uses them).

- (a) One white card in place of the records with the approved text ('No budgets yet' / 'No pots yet'), centred, 14 px body text in mid-grey; the header's add button is the action the story names, so each page keeps one button of that name.
- (b) The same card plus a second add button under the text that opens the same form (two buttons with one name and one job on the page).
- (c) Nothing in place of the records: the header button alone.
- (d) The designer draws a different empty state (e.g. an illustration with a sentence); its new words come back to the owner as a text question.

*Recommendation:* (a). No new text; one accessible name per action (voice control, NFR-A1, and unambiguous test locators); it reads both ACs as met by the header button. (c) arguably fails the ACs' 'an empty state'. The card's look is still the designer's to confirm in the changelog.

Who decides: the owner

**BU-Q3** (= S45-5; asked only here, no `pots.md` question — v0.3's third part, the donut's animation, is now BU-Q7)

*Question:* Does the Budgets page reuse Overview's donut exactly as Release 1 built it, or draw the design's donut? The design's donut differs from Release 1's in two drawn ways: the inner ring is 12 px wide at 75 % opacity (Release 1: 8 px, a 25 % tint), and the empty ring (no budgets) is beige-100 (Release 1: grey-100). The animation is S45-4; the centre's two-decimal money is S45-9. Release 1's donut is fixed by the approved overview.md 4.4.

- (a) Reuse Release 1's donut unchanged on Budgets (one donut in the app, as overview.md 4.4 approved it); the designer is told and records it.
- (b) Draw both pages' donuts as the design does (12 px inner ring at 75 %, beige-100 empty ring): overview.md is amended in its own pull request and the code change ships in 'hotfix 2', as the designer's other changes to Release 1 screens do (H12, H17).

*Recommendation:* (b). On a design question the designer's current drawing wins, and no NFR is at stake (the donut has an aria-label and the legend is its accessible detail); it keeps one donut in the app and follows the project's route for designer changes to Release 1 (overview.md v1.2 from changelog §14/§16c). (a) is the smaller-scope fallback if the owner or designer prefers to keep Release 1 as is.

Who decides: the owner

**BU-Q4** (= S45-6; same as `pots.md` PO-Q10)

*Question:* Four values the two pages draw have no design token. Budgets: (1) the line between 'Latest Spending' rows, grey-500 at 15 % (rgba(105,104,104,0.15)) on the beige panel; (2) the 4 px corner rounding of each card's progress bar and fill (radius tokens start at 8 px). Pots: (3) a 13 px gap between a bar and the text under it (spacing tokens have 12 and 16); (4) a 2 px gap between the preview bar's two segments (smallest spacing token is 4). What does the build write for them?

- (a) Each gets a new token with the design's value, named by the designer (e.g. --color-divider-on-beige, --radius-50: 4px, and 13 px and 2 px spacing tokens), added to design-tokens.md and src/ui/tokens.css together in the page's first build task.
- (b) Each takes the nearest existing token (grey-100 line, 8 px radius, 12 px, 4 px), changing the look slightly; the designer is told.
- (c) Each is written as the design's number in the style file with a comment naming the design (as Overview's 4 px theme bar and 608 px column are today).
- (d) Value by value (say which value takes which of (a)-(c)).

*Recommendation:* (a). It is the designer's own recorded rule ('prefer separate tokens over reuse', changelog §10), it keeps the look as drawn, and it keeps every value under the test that holds design-tokens.md and tokens.css equal (docs/02-architecture/README.md: the tokens are 'the only source for UI values').

Who decides: the designer, through the owner (governance v1.10)

**BU-Q5** (= S45-7; same as `pots.md` PO-Q11)

*Question:* At the narrowest widths, what happens to content that does not fit on its line? Budgets: a very large maximum (up to $999,999,999.99) on a 320 px phone does not fit in a Spending Summary row ('$X of $Y' beside the category) or in a card's Spent/Remaining halves (about 96 px each). Pots: a card's '+ Add Money' and 'Withdraw' buttons are only 116 px wide at 320 px and 123 px at a 1024 px window with the sidebar expanded, and the label may not fit. The design draws everything on one line and has no rule; US-33 requires nothing cut off and no sideways scroll.

- (a) What does not fit moves to the next line, whole: a summary row's amounts go to a second line under the category, right-aligned; a card amount breaks only after a comma ('$999,999,' / '999.99'); the two pot buttons stack, each full width, only where their labels do not fit side by side. Everything else stays as drawn.
- (b) Whatever does not fit is drawn in a smaller text size so it stays on one line / side by side.
- (c) The designer draws a different layout for these cases; it comes back as a changelog entry.

*Recommendation:* (a). Every digit group and label stays whole (US-33), no new size token is needed, and nothing changes at ordinary amounts and widths (the seed's largest is $750.00). One rule answers both pages.

Who decides: the designer, through the owner (governance v1.10)

**BU-Q6** (= S45-3; same as `pots.md` PO-Q9)

*Question:* When a page's records cannot be loaded (the 'Couldn't load your ...' card with Retry), does the header still show '+ Add New Budget' / '+ Add New Pot'? The merged shared-parts spec (ui-kit.md §3) says the header button is 'always on Budgets and Pots', but with nothing loaded the add form cannot tell which categories, names and themes are already taken.

- (a) No add button in the error state only; ui-kit.md §3's row gains 'except the page's error state' - a one-line amendment in its own pull request shared by both specs, approved by merging.
- (b) The button stays and opens the form; with no data the form marks nothing 'Already used' and skips the name check, and the server's answer ('Already used', 'A pot with this name already exists') shows after submit.

*Recommendation:* (a). A form that cannot check its own fields is not offered; Retry is the one action. Without an answer the two specs would contradict a merged spec.

Who decides: the owner

**BU-Q7** (= S45-4; same as `pots.md` PO-Q6, and v0.3's BU-Q3 part 3, the donut's animation)

*Question:* Do the progress bars (and the Budgets donut's segments) animate when their numbers change? The design animates each budget card's and pot card's bar width over 0.4 s, the Budgets donut's segments over 0.4 s, and the Pots money modal's preview bar over 0.3 s while typing. No duration token exists for these; Release 1 has no moving bar.

- (a) Animate as drawn: the card bars and the donut segments over a new token --duration-progress: 400ms, the preview bar over a new token --duration-preview: 300ms (names confirmed by the designer, added to design-tokens.md and src/ui/tokens.css in the first Budgets or Pots build task); nothing animates when the person's device asks for reduced motion.
- (b) Nothing animates on either page and no token is added; the designer is told and records it.

*Recommendation:* (a). The design draws the animation and the designer's sources win on a design question; no NFR is against it, because (a) keeps the approved reduced-motion rule the sidebar (app-shell.md 2.3) and the modal (ui-kit.md 2.2) already follow, and the designer already named motion tokens of this kind (changelog §10, UK-Q4). This resolves the specs' contradiction: BU-Q7 (a) recommended animating, PO-Q6 (a) and BU-Q3 (a) recommended none.

Who decides: the designer, through the owner (governance v1.10)

**BU-Q8** (= S45-8; same as `pots.md` PO-Q7)

*Question:* The design switches two layouts by the window at 768 px: the Budgets Spending Summary card (donut beside the list from 768 px, stacked below) and the Pots grid (two columns from 768 px, one below). The approved shell rule (app-shell.md §2.9, v1.5, PR #96) says two-column layouts change by the content width (window minus sidebar and padding) 'and never by the window width'. No content width reproduces the design's switch (content is 735 px at a 767 px window, 688 px at 768, 644 px at 1024 with the sidebar expanded). Which rule do these layouts follow?

- (a) Both switch at a content width of 644 px (the narrowest content at which the design draws them side by side); windows from 676 to 767 px get the side-by-side layout where the design draws a column. The designer records the threshold in the changelog.
- (b) Keep the design's 768 px window switch for both; app-shell.md §2.9 is amended to say it does not cover these layouts - an amendment approved by merging its pull request.
- (c) Another content width, which the designer names in the changelog.

*Recommendation:* (a). It follows the approved app-shell.md §2.9, which itself came from the designer's recorded decision (changelog §14, §16c) and which overview.md v1.2 already applies; no card gets narrower than the design's own narrowest side-by-side case (310 px pot card), and one rule covers both pages. Note the counter-precedent: Overview's stat-card row still switches at a 768 px window.

Who decides: the owner
