## 1. Purpose

The user sees every budget of the demo account — one per spending category — with what was spent against it in the current month (August 2026), what remains, a bar that fills as the money goes, and the three latest transactions of its category, beside a donut and a list that sum all budgets up. The user creates a budget, changes its category, maximum or theme, and deletes it, in the modal and with the controls `ui-kit.md` specifies; "See All" opens the Transactions page filtered to the budget's category. Budgets never touch the balance (`write-path.md` 2.8). An AI agent reads the same budgets with `list_budgets` and changes them with `add_budget`, `edit_budget` and `delete_budget`, through the same routes, with the deletion confirmed by the person on screen.

## 2. Behaviour

**2.1 Where things run** (ADR-0001: a spec states which components are client components).
- **Server:** `app/(app)/budgets/page.tsx` is an async Server Component. It calls `getBudgets(getDb(), fixedClock(BUSINESS_TODAY))` from `src/server/budgets.ts` **directly** (no HTTP self-call, the Overview pattern, `overview.md` 2.1) and renders either the page's client container with the answer (below) or, when the call throws, the error state of 2.12. The same `getBudgets` backs `GET /api/budgets` (2.11).
- **Client** (`"use client"`): `BudgetsView` (`app/(app)/budgets/BudgetsView.tsx`, in `app/` because it joins `src/ui` and `src/webmcp`'s bus, `ui-kit.md` 2.3) is the page's client container: it receives the `BudgetsDto` as a prop and renders the page header with its primary action (`ui-kit.md` 2.8), the two columns of 2.2, the modal (`ui-kit.md` 2.2) and the notice (`ui-kit.md` 2.9); it provides the page's `ModalSlot` (`ui-kit.md` 2.2), owns the page's write function (2.9), subscribes the page to the delete bus (`ui-kit.md` 2.3) and refreshes the page after a write. Under it, in `src/ui/budgets/`: `SpendingSummary` (2.3), `BudgetCard` (2.4), `BudgetBar` (2.4), `LatestSpending` (2.5), `BudgetForm` (2.6, 2.7), `BudgetsEmpty` (2.12) and `BudgetsError` (2.12; it calls `router.refresh()`); the shared parts are `ui-kit.md`'s and `transactions.md` 2.9's `TruncatedText`, and the donut is Release 1's `Donut` (`src/ui/overview/Donut.tsx`, 2.3). `app/(app)/budgets/layout.tsx` renders `children` and `<BudgetsTools />` (`src/webmcp/tools/`, the Overview pattern, `webmcp-tools.md` 2.3).
- **Domain** (pure, `src/domain/budgets.ts`, today `budgetSpent` only): `latestSpending(category, transactions, 3)` (the name `data-model.md`'s "Derived values" gives it), `budgetRemaining(maximum, spent)` and `budgetsSummary(input, clock)`, which returns the budgets in creation order (`seq`), each with its `spent`, `remaining` and `latest`, and the totals `spent` and `limit` over all budgets — the shape `overviewSummary` already gives Overview (`src/domain/overview.ts`), so the two pages read the same numbers (US-20 AC1). **Shared** (`src/shared`): the request schemas and DTO schemas of 2.10–2.11 (`schemas.ts`), `budgetFillPercent(spent, maximum)` (4.1; the bar is a `ui` component, which may import only `ui` and `shared`), `COPY` entries (2.17).
- **The page performs no money arithmetic** (as `overview.md` 4.1): every amount comes from the domain through `getBudgets`; the one number the client computes is the bar's width, with the shared, unit-tested `budgetFillPercent`.

**2.9 After a write — the page's write function** (`write-path.md` §3, `ui-kit.md` 2.3, 2.7).
- `BudgetsView` owns one write function used by the add form, the edit form and the delete dialog: it counts its requests in and out of the `ModalSlot` (`trackWrite`, `ui-kit.md` 2.2), sends through `apiSend` (`write-path.md` 2.11 (2); with `X-Via: webmcp` only when the delete was a tool's, `ui-kit.md` 2.3 item 5) and maps the answer.
- **Success** (201, 200, 204): the modal closes (focus as `ui-kit.md` 2.2 says: the header button after an add, the card's "…" button after an edit, `<main>` after a delete), any "no longer exists" notice is cleared (`ui-kit.md` 2.9), and the page calls `router.refresh()` inside `startTransition`, so the Server Component reads the database again and the cards, the summary and the "Already used" options show the new state **with no reload** (US-15 AC3, US-16 AC2, US-17 AC2). While that refresh is pending the cards' column carries `aria-busy="true"`; the previous state stays until the new one arrives (no skeleton). Overview reads the database on each request (`overview.md` 2.1), so its Budgets card shows the change the next time it is opened (US-15 AC3, US-16 AC2, US-17 AC2: "and Overview").
- **A field error** (400 `validation`): each `issues` entry under its field (`ui-kit.md` 2.5, 2.6); a `taken` on `category` or `theme` shows "Already used" under it and the page refreshes its data, so the option list marks the value as used (`ui-kit.md` 2.6). A `validation` with a path the form has no field for (`[]`, `id`) is shown as the server error message in the error area (it cannot come from this form).
- **404** (an edit or a delete of a budget deleted meanwhile): the modal closes with `<main>` named for focus, the notice "This budget no longer exists" (`ui-kit.md` 2.9), and the list refreshes (US-17 AC3).
- **409, 401, 429, 403, 415, 500, no answer:** as `ui-kit.md` 2.3 and 2.7 say (`write-path.md` §3).

**2.10 The write routes** (`write-path.md` 2.1's three Budgets rows; every rule of `write-path.md` 2.2–2.12 applies and is not repeated: the cross-site and content-type checks in the proxy, the rate limit, validation, one transaction, the threshold check, the answers, `no-store`, the via log). The handlers are `guardedWrite` handlers (`write-path.md` §6) in `app/api/budgets/route.ts` (`POST`, beside the `GET` of 2.11) and `app/api/budgets/[id]/route.ts` (`PATCH`, `DELETE`).

|---|---|---|---|
| `POST /api/budgets` | `BudgetCreateSchema`: `category` (one of the ten), `maximum` (integer cents, 1 ≤ x ≤ 99,999,999,999), `theme` (one of the fifteen) — all required | **201** with the new budget as a `BudgetItemDto` (2.11) | `category` held by another budget → `taken` on `category`; `theme` held by another budget → `taken` on `theme` (both are reported when both apply) |

- **The limits** (H1; `write-path.md` 4.1, NFR-S3): a budget has no name; its category and theme come from their enums; at most ten budgets exist, one per category — the unique `category` makes an eleventh impossible, so no separate count check exists: posting a category that already has a budget is `taken`. A budget's theme is unique among budgets; a pot may share it.
- **The unique constraints** `Budget.category` and `Budget.theme` (`data-model.md`) are the last line of defence: a violation caught from the database maps to the same 400 `taken` on that field (`write-path.md` 2.8), so two requests racing for the same category cannot both succeed.
- **The new budget's `seq`** is assigned by the database (`data-model.md` v1.1), so it is listed last (US-14 AC4). An edit keeps `seq`.
- **The balance is never written** by these routes (US-04 AC3; H6). A budget write is checked by the storage threshold like any write (`write-path.md` 2.9), and a reset answers 409.
- **The answer's DTO is computed after the commit** from the database, with the same `budgetsSummary` as `GET`, so the budget comes back with its August spent, remaining and latest three (US-15 AC3: "computed immediately").

**2.11 `GET /api/budgets`** (the route for the tool and the tests; the page calls `getBudgets` directly). It takes no parameters (any query is ignored), calls `getBudgets(getDb(), fixedClock(BUSINESS_TODAY))` and answers 200 with a `BudgetsDto` (a `z.strictObject`, so a leaked field fails an API test) and `Cache-Control: no-store`; 401 `unauthenticated` from the proxy; 500 `server_error` `{ message: "The budgets are unavailable" }` after a `console.error("GET /api/budgets failed", error)`, also with `no-store` (the route sets it itself, as `transactions.md` 2.13). It never changes data (`write-path.md` 2.1, 7.2).

```
BudgetItemDto = {
  id: uuid,
  category: one of the ten,
  theme: one of the fifteen,
  maximum: integer cents ≥ 1,
  spent: integer cents ≥ 0,        // budgetSpent: August 2026, negative rows only (R-11)
  remaining: integer cents ≥ 0,    // max(0, maximum − spent)
  latest: { id: uuid, name: string (1–60), avatar: key, date: UTC ISO-8601, amount: integer cents (signed) }[]   // 0–3, US-11 Latest
}
BudgetsDto = {
  items: BudgetItemDto[],   // 0–10, creation order (seq)
  spent: integer cents ≥ 0, // Σ items.spent
  limit: integer cents ≥ 0  // Σ items.maximum
}
```

The item carries what the card shows plus the ids (US-39 AC2: "including ids") and the avatar key; it has no `seq` (the order of `items` is the order) and no bar percentage (the client's, 2.1). `spent` and `limit` equal Overview's `budgets.spent` and `budgets.limit` for the same data (US-20 AC1: "totals match the Overview card"; 4.2).

**2.12 Loading, empty, error.**
- **Loading.** The page is rendered on the server with its data; there is no loading route and no skeleton (as Transactions). After a write, 2.9's refresh marks the cards' column `aria-busy="true"` until the new state arrives.
- **No budgets** (US-14 AC3, US-20 AC2; the `empty-budgets` and `empty-all` variants). The Spending Summary card shows the empty donut ("$0.00", "of $0.00 limit") and its title with no list (2.3). In place of the cards the page shows an empty state that **the design does not draw**: what it holds, and whether it repeats the "Add New Budget" action that US-14 AC3 names, is **§9 BU-Q2**. Whatever the answer, the header's "+ Add New Budget" stays.
- **Error.** If `getBudgets` throws, the page logs `Budgets: getBudgets failed requestId=<id>` (the id from `x-request-id`) and renders, under the page header (with no primary action, since the page has no data to check a new budget against), one white card in place of both columns: "Couldn't load your budgets" (a new string, **§9 BU-Q1** #1) and a "Retry" button (`COPY.retry`; `router.refresh()`) — the Overview pattern (`overview.md` 2.8), drawn as `OverviewError` is. No `error.tsx`: any other error falls to Next's default handling.
- **Session ended.** A page request without a session meets the proxy's redirect to `/login?next=/budgets`; the API and the tools answer 401 `unauthenticated` (US-39 AC4); a write's 401 reloads the page (`write-path.md` §3).

## 5. Data

Reads `Budget` (`id`, `seq`, `category`, `maximum`, `theme`) and `Transaction` (`id`, `name`, `avatar`, `category`, `date`, `amount`); writes `Budget` only (create, update `category`/`maximum`/`theme`, delete) and, through `write-path.md`, the write-limiter rows and, on a threshold reset, `ResetLog`. Never `Balance`, `Pot` or `Transaction` (US-04 AC3). The source of truth is the database; `data.json` is only the seed (US-36 AC2). Money is `BigInt` in the database and integer cents in every body and DTO; it becomes text only at the edge (`formatMoney`, `formatSignedMoney`). Spent, remaining and the latest three are computed on every read, never stored (`data-model.md`: "spent/remaining are computed, not stored").

## 8. Out of scope

A budget period other than the current month; a budget with a name; budgets over several categories; alerts when a budget is exceeded (the design has none; the bar caps at 100 %); sorting or filtering budgets; reordering them; editing `seq`; a "See All" that keeps a search or sort; opening the add form from a URL (Overview's "Add a budget" link opens the page, `overview.md` 2.7); a success toast after a write (the modal closing and the refreshed card are the feedback, `ui-kit.md` §8); undo; animation of the bar or the donut unless §9 BU-Q3 decides otherwise; a skeleton or a loading route. The shared parts themselves (`ui-kit.md`), the write pipeline (`write-path.md`) and Transactions' receiving side of "See All" (`transactions.md` 2.2, 2.10).

## 9. Open questions

Four questions, BU-Q1 to BU-Q4 (prefixed so an answer cannot be taken for another spec's question, plan D13). BU-Q1 is a question about new texts (the owner's); BU-Q2 to BU-Q4 are about the design (governance v1.10: the owner discusses them with the designer, the designer records the decision in the designer's changelog, and this spec then applies it, citing the section). Each can be answered by its letter.

**BU-Q1 — May the Budgets page use these two new texts?** *What:* the page needs two short English texts that no approved list has yet. Every text the app shows or reads aloud must first be in the message table at the end of `user-stories.md`, which you approve; the code may use only texts from that table. One is seen on the screen; the other is never seen — it is what a **screen reader** (software that reads the page aloud for a person who cannot see it) says, or what a person using **voice control** (operating the page by speaking the names of its links and buttons) says to follow the link.

| # | Text | Where it is used | Seen or heard |
|---|---|---|---|
| 1 | Couldn't load your budgets | the card shown when the budgets cannot be loaded, with a Retry button (as Overview's "Couldn't load your overview" and Transactions' "Couldn't load your transactions") | seen |
| 2 | See All {category} transactions — e.g. "See All Dining Out transactions" | the name of the "See All" link on each budget card. The design shows only "See All" on every card, so on a page with four budgets a screen reader's list of links reads "See All" four times and a voice-control user cannot say which one; adding the category tells them apart, and the visible "See All" stays at the start of the name | heard |

*Why it matters:* without 1 the error card has no text; without 2 the four "See All" links sound the same. Once approved, both go into the table and into the code together, in the first Budgets build task (H15 (1)).
- (a) **Approve both as written — recommended.**
- (b) Change the wording of some (say which numbers and the new words).
- (c) Approve 1; keep the design's name "See All" for 2.

**BU-Q2 — What does the page show where the budget cards would be, when there are no budgets?** *What:* US-14 AC3 says: "Given no budgets, Then an empty state with 'Add New Budget'". The design draws no such state: with no budgets the right-hand column is simply empty, while the Spending Summary card shows an empty donut ("$0.00 of $0.00 limit") and its title (US-20 AC2). The page's header always has the "+ Add New Budget" button. A text already approved for Overview fits: "No budgets yet" (`COPY.budgetsEmpty`, used today on Overview's Budgets card with the link "Add a budget").
*Why it matters:* it is a drawn state of the page — what a person sees on a fresh or emptied account — so the designer decides its look; and option (b) puts a second control with the same job on the page.
- (a) **One white card in the cards' column with "No budgets yet" (the approved Overview text), centred, `--text-preset-4` grey-500; the header's "+ Add New Budget" is the action the story names — recommended** (no new text, one control per action, the story's "Add New Budget" is the header button's own label).
- (b) The same card with "No budgets yet" and, under it, a second "+ Add New Budget" button that opens the same form (two buttons with one name and one job on the page).
- (c) The designer draws a different empty state (for example an illustration with a sentence); its new words come back to you as a text question.

**BU-Q3 — May the Budgets page reuse Overview's donut as Release 1 built it, and draw the donut and the bars without the design's animation?** *What:* the Budgets screen of the design draws the same donut as Overview, and Release 1 already built Overview's donut (`overview.md` 4.4, approved). Three things in the design's drawing differ from what Release 1 built: (1) the inner ring is 12 px wide at 75 % opacity in the design, 8 px wide as a 25 % tint in Release 1; (2) with no budgets the design's empty ring is beige-100, Release 1's is grey-100; (3) the design animates the donut's segments and each budget card's bar over 0.4 s when the numbers change, and Release 1 has no animation (Overview's numbers never change while it is open; on Budgets they change after each write). The centre's amounts are not part of this question: the stories write money with two decimals ("$338.00"), where the design writes "$338". **Opacity** is how see-through a colour is drawn; a **tint** mixes the colour with white instead.
*Why it matters:* option (a) keeps one donut in the app, the same on both pages; option (b) changes Overview's approved donut too (an amendment of `overview.md`) or gives the app two different donuts.
- (a) **Reuse Release 1's donut unchanged on Budgets, and no animation on either the donut or the bars; the designer is told and records it — recommended.**
- (b) Draw both pages' donuts as the design does (inner ring 12 px at 75 %, beige-100 empty ring) and animate the donut and the bars over 0.4 s (turned off under the reduced-motion setting); `overview.md` is amended in this pull request.
- (c) Reuse the donut as in (a), but animate the bars as the design does.

**BU-Q4 — Two values the Budgets screen draws have no design token: may they get tokens?** *What:* the project's rule is that every colour, size and radius in the code comes from a named **token** (`design-tokens.md` and `src/ui/tokens.css`; `docs/02-architecture/README.md`: the tokens are "the only source for UI values"). Two values on the Budgets screen have none: (1) the thin line between the rows of "Latest Spending" is grey-500 at 15 % opacity (`rgba(105, 104, 104, 0.15)`), drawn on the beige panel, where the cards' grey-100 lines would be nearly invisible; (2) the corners of each budget card's 32 px progress bar and of its fill are rounded by 4 px, while the radius tokens start at 8 px.
*Why it matters:* without a token the build would write a raw value, which the token rule forbids; with the wrong token the screen would not look as drawn.
- (a) **Two new tokens with the design's values, named by the designer (for example `--color-divider-on-beige: rgba(105, 104, 104, 0.15)` and `--radius-50: 4px`), added to `design-tokens.md` and `src/ui/tokens.css` together in the first Budgets build task — recommended** (the look stays as drawn; the designer records the names in the changelog, as for the tokens of `ui-kit.md` UK-Q4).
- (b) The designer replaces them with existing tokens (for example grey-100 lines and an 8 px radius), changing the look.
