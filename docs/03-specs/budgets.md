## 1. Purpose

The user sees every budget of the demo account — one per spending category — with what was spent against it in the current month (August 2026), what remains, a bar that fills as the money goes, and the three latest transactions of its category, beside a donut and a list that sum all budgets up. The user creates a budget, changes its category, maximum or theme, and deletes it, in the modal and with the controls `ui-kit.md` specifies; "See All" opens the Transactions page filtered to the budget's category. Budgets never touch the balance (`write-path.md` 2.8). An AI agent reads the same budgets with `list_budgets` and changes them with `add_budget`, `edit_budget` and `delete_budget`, through the same routes, with the deletion confirmed by the person on screen.

## 2. Behaviour

**2.1 Where things run** (ADR-0001: a spec states which components are client components).
- **Server:** `app/(app)/budgets/page.tsx` is an async Server Component. It calls `getBudgets(getDb(), fixedClock(BUSINESS_TODAY))` from `src/server/budgets.ts` **directly** (no HTTP self-call, the Overview pattern, `overview.md` 2.1) and renders either the page's client container with the answer (below) or, when the call throws, the error state of 2.12. The same `getBudgets` backs `GET /api/budgets` (2.11).
- **Client** (`"use client"`): `BudgetsView` (`app/(app)/budgets/BudgetsView.tsx`, in `app/` because it joins `src/ui` and `src/webmcp`'s bus, `ui-kit.md` 2.3) is the page's client container: it receives the `BudgetsDto` as a prop and renders the page header with its primary action (`ui-kit.md` 2.8), the two columns of 2.2, the modal (`ui-kit.md` 2.2) and the notice (`ui-kit.md` 2.9); it provides the page's `ModalSlot` (`ui-kit.md` 2.2), owns the page's write function (2.9), subscribes the page to the delete bus (`ui-kit.md` 2.3) and refreshes the page after a write. Under it, in `src/ui/budgets/`: `SpendingSummary` (2.3), `BudgetCard` (2.4), `BudgetBar` (2.4), `LatestSpending` (2.5), `BudgetForm` (2.6, 2.7), `BudgetsEmpty` (2.12) and `BudgetsError` (2.12; it calls `router.refresh()`); the shared parts are `ui-kit.md`'s and `transactions.md` 2.9's `TruncatedText`, and the donut is the app's one `Donut` (`src/ui/overview/Donut.tsx`, 2.3; drawn as the design draws it, on both pages — its inner ring and empty ring by §9 BU-Q3 (b), its outer ring's radius 96 px by `overview.md` §9 OV-Q1 (a)). `app/(app)/budgets/layout.tsx` renders `children` and `<BudgetsTools />` (`src/webmcp/tools/`, the Overview pattern, `webmcp-tools.md` 2.3; it also refreshes the page after an agent's add or edit, 2.13).
- **Domain** (pure, `src/domain/budgets.ts`, today `budgetSpent` only): `latestSpending(category, transactions, 3)` (the name `data-model.md`'s "Derived values" gives it), `budgetRemaining(maximum, spent)` and `budgetsSummary(input, clock)`, which returns the budgets in creation order (`seq`), each with its `spent`, `remaining` and `latest`, and the totals `spent` and `limit` over all budgets — the shape `overviewSummary` already gives Overview (`src/domain/overview.ts`), so the two pages read the same numbers (US-20 AC1). **Shared** (`src/shared`): the request schemas and DTO schemas of 2.10–2.11 (`schemas.ts`), `budgetFillPercent(spent, maximum)` (4.1; the bar is a `ui` component, which may import only `ui` and `shared`), `COPY` entries (2.17).
- **The page performs no money arithmetic** (as `overview.md` 4.1): every amount comes from the domain through `getBudgets`; the one number the client computes is the bar's width, with the shared, unit-tested `budgetFillPercent`.

- **The limits** (H1; `write-path.md` 4.1, NFR-S3): a budget has no name; its category and theme come from their enums; at most ten budgets exist, one per category — the unique `category` makes an eleventh impossible, so no separate count check exists: posting a category that already has a budget is `taken`. A budget's theme is unique among budgets; a pot may share it.
- **The unique constraints** `Budget.category` and `Budget.theme` (`data-model.md`) are the last line of defence: a violation caught from the database maps to the same 400 `taken` on that field (`write-path.md` 2.8), so two requests racing for the same category cannot both succeed.
- **The new budget's `seq`** is assigned by the database (`data-model.md` v1.1), so it is listed last (US-14 AC4). An edit keeps `seq`.
- **The balance is never written** by these routes (US-04 AC3; H6). A budget write is checked by the storage threshold like any write (`write-path.md` 2.9), and a reset answers 409.
- **The answer's shape.** `write-path.md` 2.2 step 9 answers "with the record" and leaves the shape to the page spec; a write's record is wrapped under its noun, `{ budget }`, as `pots.md` 2.12 wraps `{ pot }` (its deposit and withdrawal answer `{ pot, balance }`, which needs the wrapper), so both pages' writes answer one way. - **The answer's DTO is computed after the commit** from the database, with the same `budgetsSummary` as `GET`, so the budget comes back with its August spent, remaining and latest three (US-15 AC3: "computed immediately").

**2.11 `GET /api/budgets`** (the route for the tool and the tests; the page calls `getBudgets` directly). It takes no parameters (any query is ignored), calls `getBudgets(getDb(), fixedClock(BUSINESS_TODAY))` and answers 200 with a `BudgetsDto` (a `z.strictObject`, so a leaked field fails an API test) and `Cache-Control: no-store`; 401 `unauthenticated` from the proxy; 500 `server_error` `{ message: "The budgets are unavailable" }` after a `console.error("GET /api/budgets failed", error)`, also with `no-store` (the route sets it itself, as `transactions.md` 2.13). It never changes data (`write-path.md` 2.1, 7.2).

```
BudgetItemDto = {
  id: uuid,
  category: one of the ten,
  theme: one of the fifteen,
  maximum: integer cents ≥ 1,
  spent: integer cents ≥ 0,        // budgetSpent: August 2026, negative rows only (R-11)
  remaining: integer cents ≥ 0,    // max(0, maximum − spent)
  latest: { id: uuid, name: string (1–60), avatar: key, date: UTC ISO-8601, amount: integer cents (signed) }[]   // 0–3, US-11 Latest
}
BudgetsDto = {
  items: BudgetItemDto[],   // 0–10, creation order (seq)
  spent: integer cents ≥ 0, // Σ items.spent
  limit: integer cents ≥ 0  // Σ items.maximum
}
```

The item carries what the card shows plus the ids (US-39 AC2: "including ids") and the avatar key; it has no `seq` (the order of `items` is the order) and no bar percentage (the client's, 2.1). `spent` and `limit` equal Overview's `budgets.spent` and `budgets.limit` for the same data (US-20 AC1: "totals match the Overview card"; 4.2).

A tool's `execute` is a module-level function (`PAGE_TOOLS`, `src/webmcp/tools/registry.ts`) and cannot call a React hook, so the refresh is added where a hook runs: `BudgetsTools` (the client component the layout renders, as `OverviewTools` is) calls `useRouter()` and builds, once per router (`useMemo`), the list it hands to `WebMcpTools` — `PAGE_TOOLS.budgets` with the `execute` of `add_budget` and `edit_budget` wrapped so that, after a result without `isError`, it calls `router.refresh()` and returns the result unchanged; `list_budgets` and `delete_budget` are passed as they are. The registry keeps the unwrapped definitions, so `tests/unit/webmcp/registry.test.ts` checks the same names, schemas and annotations; the memoised list keeps `WebMcpTools`' effect (`[tools]`) from registering again on every render. The refresh makes the Server Component read `getBudgets` again and `BudgetsView` renders the new props, as after its own write; it runs outside `BudgetsView`'s transition, so the cards' column is not marked `aria-busy` for an agent's write (2.9's `aria-busy` is the page's own writes'). **One mechanism for both pages** (the same statement as `pots.md` 2.8 and §6): after an agent's add, edit, delete or money move, the page refreshes by `router.refresh()`, called from the page's Tools component (`BudgetsTools`, `PotsTools`), which wraps the `execute` of each mutating tool that calls the API itself; a delete tool's confirmed request is the page's own write, which refreshes as the page's write function does. `src/webmcp/bus.ts` is not extended — no `notifyWrite`/`onWrite` (v0.2 had added them; cross-spec review B1) — and `ui-kit.md` 2.3 needs no amendment. So `delete_budget` is not wrapped: it goes through the page's own dialog and write function (`ui-kit.md` 2.3 item 5), whose success runs 2.9's refresh. Until the refresh has landed, the page does not show a budget an agent has just added, so a `delete_budget` of its id in that moment answers `not_found` (`ui-kit.md` 2.3: an id the page does not show), with no dialog and no request; once the card is shown, the same call opens the dialog. A tool write is not counted by the page's `ModalSlot` (it is not the page's write function): a person's form stays open while an agent adds a budget, and the refresh updates its "Already used" options; a person's submit that then collides answers `taken` (2.9).
- **On record:** every call sends `X-Via: webmcp` and is logged with its `method` (`write-path.md` 2.12; US-40 AC3).
- **`delete_budget`** returns `{ deleted: true }`, or one of `ui-kit.md` 2.3's other `DeleteResult` codes, mapped as its item 7 says: `cancelled`, `busy`, `not_found` before any request (for an id the page does not show); after a confirm `not_found` (404), `conflict` (409), `unauthenticated` (401), and, when the page unmounted meanwhile, `rate_limited`, `forbidden`, `validation`, `server_error` (`ui-kit.md` 2.3 item 4) — the list `pots.md` 2.13 gives `delete_pot`; nothing reaches the server before the person confirms (R-16, NFR-W5). The runtime hands no `AbortSignal` today, so "cancel" is driven through the dialog (H3).
- **Safety rule** (NFR-S7, R-24): transaction names are returned as JSON strings, never as HTML; a budget has no name of its own; the registry test asserts `consequentialHint` on the three mutating tools (the polyfill's `getTools()` drops it, H3) and `untrustedContentHint` on `list_budgets`, `add_budget` and `edit_budget`.

## 5. Data

Reads `Budget` (`id`, `seq`, `category`, `maximum`, `theme`) and `Transaction` (`id`, `name`, `avatar`, `category`, `date`, `amount`); writes `Budget` only (create, update `category`/`maximum`/`theme`, delete) and, through `write-path.md`, the write-limiter rows and, on a threshold reset, `ResetLog`. Never `Balance`, `Pot` or `Transaction` (US-04 AC3). The source of truth is the database; `data.json` is only the seed (US-36 AC2). Money is `BigInt` in the database and integer cents in every body and DTO; it becomes text only at the edge (`formatMoney`, `formatSignedMoney`). Spent, remaining and the latest three are computed on every read, never stored (`data-model.md`: "spent/remaining are computed, not stored").

**BU-Q9** (v0.8; asked only here)

*Question:* On the Budgets page the donut's centre must never cut an amount: the spent figure takes the largest of five text sizes (32, 20, 16, 14 or 12 px) whose width fits 128 px, and "of {limit} limit" breaks before "limit" when it does not fit (the designer's changelog §24a, approved by the owner on 2026-10-10). The designer left to the spec **how the page knows a text's width**. Two ways exist, and they differ in when the size is chosen and whether the page can jump:

- (a) **A table, chosen on the server.** The build task works out once, against the app's font, the widest a formatted amount of each length can be at each size (an amount is only "$", digits, commas and a point), and writes it as a small table in `src/shared`; the page picks the size from the amount's text while the server renders it. No script runs in the browser, nothing moves after the page appears (NFR-P2, layout shift), and a unit test checks the table's rows. Its risk: the table is computed for one font, so a fallback font while the web font loads or a font change makes it wrong — the E2E of §7 catches that in the real browsers.
- (b) **A measurement, in the browser.** A client effect measures the rendered text against 128 px and steps the size down until it fits, again on resize and when the font has loaded. It is exact for any font, but the server renders 32 px first, so a large amount shows at 32 px and then shrinks after the page loads (a visible jump, NFR-P2), and the centre needs a client effect, where today its text is in the page's server-rendered HTML as it is.

*Recommendation:* (a). Amounts change only by a write, which renders the page again on the server (2.9), so a size chosen there is always current; no layout shift; a pure, unit-tested function in `src/shared`, as `budgetFillPercent` is; the E2E checks the result in every engine. (b) is the fallback if the table proves wrong in a browser.

Who decides: the owner (a trade-off with NFR-P2's layout shift, not a look: §24a fixes the look either way)

**Answered by the owner on 2026-10-10: (a)** — "BU-Q9 a": a table from the amount's length to a text size, chosen while the server renders the page, so nothing moves after load (NFR-P2) (2.3, 4.7, §6, §7).
